## 自分のプロフィール

### 仕様

- アイコンタップでアイコン写真拡大
- フォロー中、フォロワーボタン
  - タップすると自分がフォローしているユーザの一覧に飛べる（フォロワーも同様）
- 右上の三点リーダーから詳細設定画面に遷移する
- ユーザ情報の表示
  - ユーザ名、性別、身長などを表示
  - 右上の詳細設定画面からユーザ情報の入力が行える
- タブで表示する投稿の内容を変更できる
  - 自分の投稿、お気に入りに登録した投稿で切り替えができる
  - 投稿の写真を押すと、投稿の詳細画面へ移る（`post.md`「投稿の詳細画面」。ホームの一覧と同じ）
- 投稿の表示列の変更ができる
  - 1, 2, 3列まで変更が可能
  - 3列の場合はユーザの詳細情報は表示されず写真のみ（スマホの場合、文字が小さく見えづらい状況を避けるため）
- 投稿に三点リーダをつける
  - 自分の投稿の場合、編集画面に遷移できる（**まだ作っていない**。今は投稿の詳細画面の「…」から編集する。`post.md`「投稿の編集」）

## プロフィール編集

### 仕様

画面上部の「保存」ボタンで保存する。

| 項目 | 必須 | 補足 |
| --- | --- | --- |
| プロフィール画像 | 任意 | 「変更」から設定 |
| 名前 | **必須** | |
| 性別 | 任意 | 未設定あり。選択肢は下記 |
| 身長 | 任意 | 未設定あり |
| 年代 | 任意 | 未設定あり。選択肢は下記 |
| 骨格タイプ | 任意 | 未設定あり。選択肢は下記 |
| パーソナルカラー | 任意 | 未設定あり。選択肢は下記 |

- 入力変更が完了したら保存ボタンを押し保存
- 身長は 100〜250cm の整数（**暫定**）
- 「名前」は `@ユーザ名` とは別の、自由に付けられる表示名
  - 新規会員登録では名前を聞かないため、登録時はユーザ名を初期値にする（**暫定**）。プロフィール編集で変更できる

### 選択肢

| 項目 | 選択肢 | 管理方法 |
| --- | --- | --- |
| 性別 | 男性 / 女性 / その他 | アプリ内で固定 |
| 年代 | 10代 / 20代前半 / 20代後半 / 30代前半 / 30代後半 / 40代 / 50代以上 | アプリ内で固定 |
| 骨格タイプ | ストレート / ウェーブ / ナチュラル | DBのマスタテーブル |
| パーソナルカラー | イエベ春 / ブルベ夏 / イエベ秋 / ブルベ冬 | DBのマスタテーブル |

- いずれも任意で、未設定を選べる
- 年齢は数値ではなく年代で保存する（年齢の数値だと、時間が経つと古くなるため）
- 年代の区分は検索の「年代」と共通（`search.md` 参照）
- 骨格タイプ・パーソナルカラーは、後から選択肢を追加できる。使わなくなった選択肢は削除せず非表示にする（設定済みのプロフィールが壊れないようにするため）

> **画面画像との違い**
> `design/EditProfile.png` では「年齢」と表示しているが、実装では「年代」の選択式になる。画面画像の作り直しが必要。

## フォロー中一覧

### 仕様

- 自分がフォローしているユーザの一覧が見れる
- 画面上部に「フォロー中」という文字とフォロー数を設置
- 「フォロー中」という文字の下にユーザの検索欄を設置する
- 相手ユーザの表示情報
  - ユーザ名、身長、性別など、相手ユーザがプロフィールに登録した情報の一部が表示される
  - フォローしたタイミングが簡単に分かる（2時間前、3日前、1ヶ月前、1年前など）
- フォロー解除ボタンの設置
  - 押すと「フォロー」という文字に変わる
- 相談するボタンの設置
  - 押すと「申請済み」に変わる
- 並び替え機能
  - フォローの新しい順、古い順で並び替えが行える
- 検索欄は、ユーザー名・表示名の部分一致（大文字小文字を区別しない）。画面上部の件数は検索で絞り込む前の件数
- フォロワー一覧は、仕様が決まるまでフォロー中一覧と同じ画面にしている（下記「未確定・要確認」）

### フォロー解除の扱い（重要）

- フォロー関係のテーブルに「解除日時」を持つ
- フォロー中一覧は、有効なフォローと「解除から5分以内」のものを返す
- 解除から5分以内の再フォローは通知を飛ばさない

> 押し間違いで消えてしまうのを防ぐための仕様。フォロー関係は物理削除せず、解除日時を持たせて論理的に扱う。

実装での扱い（`follows` テーブル）

- 解除から5分以内のものを一覧に含めるのは、本人が自分のフォロー中一覧を見る場合だけ（他の人の一覧・フォロワー一覧は有効なフォローのみ）
- フォロー数・フォロワー数は有効なフォローのみ数える
- 解除から5分以内の再フォローは、新しい行を作らず解除した行を有効に戻す。フォローした日時は元のまま（一覧の位置と「〇日前」の表示が押し間違いの前と同じになる）。戻した日時を `restored_at` に記録する
- 通知機能を作るときは、**新しい行を作ったときだけ**フォローの通知を作る（戻した場合は作らない）

## ブロック

ほかのユーザーをブロックできる。画面画像はないため、見た目は暫定。通報は別の操作（`admin.md`「5. 通報」。通報しても自動ではブロックしない）。

### ブロックすると起きること（効果は両方向）

A さんが B さんをブロックした場合、**A から B も、B から A も**、お互いが見えなくなる（ブロックは困らせる相手から身を守るためのもので、片方向では守りにならないため）。

| 対象 | 起きること |
| --- | --- |
| 投稿 | お互いの投稿が、ホーム（新着・フォロー中・おすすめ）・検索・プロフィールの「フォロー中の投稿」・お気に入りの一覧に出なくなる。投稿の詳細は「投稿が見つかりません」（404） |
| プロフィール | A が B を開くと「ブロック中のユーザーです」と「ブロックを解除」を出す（投稿・フォロー数・ボタンは出さない）。B が A を開くと「ユーザーが見つかりません」（404。存在しないユーザーと同じ） |
| 検索 | ユーザーの検索にお互いが出ない |
| フォロー | ブロックした時点で、両方向のフォローを削除する（解除と違って行を残さない）。ブロック中はお互いにフォローできない（404） |
| ほかの人の一覧 | 第三者のフォロー中・フォロワー一覧にも出さない。**フォロー中・フォロワーの件数も、見ている人から見えない相手を数えない**（一覧と件数を合わせる。下記「条件の書き忘れを防ぐ仕組み」の共通の条件を、件数の SQL にも使っている） |
| いいね・お気に入り | ブロックした時点で、2人の間のもの（A が B の投稿に、B が A の投稿に付けたもの）を削除する。ブロック中はお互いの投稿にいいね・お気に入りできない（404） |
| 通知 | ブロックした時点で、2人の間の通知（受け取る人と、した人が A と B のもの）を削除する |
| 相談（DM） | ブロックした時点で、申請中・進行中の相談を終了にする（`dm.md`「ブロック」）。ブロック中はお互いに相談を申し込めない（404） |

- **ブロックを解除しても、削除したフォロー・いいね・お気に入り・通知、終了した相談は戻らない**
- B が A をブロックすることもできる（行は別）。どちらかの行が残っている間は見えないまま（A が解除しても、B のブロックが残っていれば見えない）
- 解除できるのは、ブロックした本人だけ

### ブロックされたことは相手に分かるか

- 相手には通知しない。B から見た A は「存在しないユーザー」と同じに見える（プロフィール・投稿は 404、一覧からは消える、フォロー・相談・いいねの操作も 404）
- **分かりにくくしているだけで、分からなくはできない**
  - 別のアカウントから見れば、A のプロフィール・投稿は見えるため、ブロックされたことが分かる
  - 急に投稿が一覧から消える・フォローが外れる、といった変化からも推測できる
- **ブロックしても、相手（B）の DM 一覧には、自分（A）の名前とアイコンが残る**（相談は終了するが、過去の会話は両方から読めるまま残すため。`dm.md`「ブロック」）。
  B がそこから A の名前を押すと、プロフィールは「ユーザーが見つかりません」になる

### 非表示（ミュート）は作っていない

- 当初の設計（上記「相手のプロフィール」）では、⋮に「通報・非表示・ブロック」を並べる想定だった
- ブロックの段階では**ブロックだけ**を作った。その後、通報を作ったため、今の⋮は「通報」「ブロック」（非表示はない）
- 非表示（ミュート）は「相手との関係は切らずに、相手の投稿を自分の一覧に出さないだけ」の片方向の機能として考えていた。困らせる相手から身を守るのはブロックで足りるため、今回は作らない
  - 作る場合は、下記の共通の条件（`VisibilityConditions`）を「自分が見たくない相手」にも広げれば、投稿の一覧から除く仕組みはそのまま使える

### 画面

- ブロックする場所
  - 相手のプロフィールの右上の⋮ →「ブロック」
  - チャット画面の右上のメニュー →「ブロック」（会話の状態に関係なく出す。「会話を終了する」は進行中のときだけ）
  - 他人の投稿の詳細画面の「…」→「ブロック」（「通報」と並べて置く。ブロックしたら、その投稿は見えなくなるため、ホームへ移る）
- ブロックの前に、画面の中で確かめる（ブラウザの確認ダイアログは使わない。最初は「キャンセル」を選んだ状態）
  - 「@◯◯ さんをブロックしますか？」「お互いの投稿・プロフィールが見えなくなり、フォローは解除され、進行中の相談は終了します。相手には通知されません。」
- ブロックしたら、その場で「ブロック中のユーザーです」の表示に変える（チャット画面では会話の状態を取り直し、終了の表示になる）
- ブロック中のアカウント（`/settings/blocks`）
  - 詳細設定の「ブロック中のアカウント」から開く（画面画像にはない項目）
  - ブロックした新しい順に、アイコン・@ユーザー名・ブロックした日を出す。20件ずつ、続きは下までスクロールで読む
  - 「解除」で、画面の中で確かめてから解除する（「元に戻りません」と書く）。解除したら一覧から外す
  - 名前を押すと、その人のプロフィール（「ブロック中のユーザーです」と解除のボタン）

### 条件の書き忘れを防ぐ仕組み（重要）

ブロックは「見えない相手を除く」条件が多くの API に要る。1か所でも書き忘れると、ブロックした相手が見えてしまう（投稿の削除で「消したことにして残す案」を採らなかったのと同じ問題）。次の4つで防ぐ。

1. **ブロックした時点で切れるものは切る**（読むときの条件を減らす）
   - フォロー・いいね・お気に入り・通知は削除し、相談は終了する。これらは読むときに条件を書かなくても漏れない
2. **一覧・件数の条件は1か所に定義する**（`block/VisibilityConditions`。措置を作ったときに `BlockConditions` から改名した）
   - 「見ている人とブロックの間柄にある相手を除く」JPQL の条件を定数にし、一覧・件数の SQL はそれを `+` でつなぐ（自分で書かない）
   - 両方向の判定を1つの `NOT EXISTS` にしているため、件数に関係なく SQL の本数は増えない
   - 使っている SQL：ホームの3つのタブ・投稿の検索（件数も）・ユーザーの検索（件数も）・プロフィールの投稿一覧と投稿数・プロフィールの「フォロー中の投稿」・お気に入り・フォロー中／フォロワー一覧・フォロー中／フォロワーの件数・通知の一覧と未読の件数
   - ブロックのほかに、利用停止中のユーザーと、管理者が非公開にした投稿も、同じ条件で除く（`admin.md`「6. 措置」）。利用停止の期限と比べるため、アプリの今の時刻（`:now`）も渡す
   - 他人のプロフィールの投稿一覧と投稿数は、以前はこの条件を使っていなかった。措置で非公開の投稿を除く必要ができたため、この条件を使うように直した
3. **1人の相手を対象にする API は1か所を通す**（`block/UserVisibility`）
   - プロフィール・投稿の詳細・投稿の編集と削除・フォロー・いいね・お気に入り・相談は、ここで確かめ、見えない相手は存在しないものと同じ 404 にする
   - 利用停止中のユーザー・非公開の投稿（投稿者本人以外）も、ここで同じ 404 にする（`admin.md`「6. 措置」）
   - 自分のもの以外を断る API（投稿の編集・削除の 403 など）では、**403 より先に**見えるかを確かめる。先に 403 を返すと「その投稿は存在する」ことが伝わり、ブロックした相手が投稿 ID を順に試すと、まだ投稿していることが分かってしまうため
4. **API の棚卸しテスト**（`VisibilityInventoryTest`）
   - アプリにあるすべての利用者向け API（管理者向けを除く）を、テストの登録表と突き合わせる。**登録していない API があるとテストが失敗する**
   - GET の API は、A が B をブロックした状態で A と B のそれぞれで呼び、相手のユーザー名・投稿の題名が応答に1つも含まれないことを確かめる
   - GET 以外は「1人の相手を対象にする操作（`BlockApiTest` で確かめる）」「自分のデータだけを扱う」「確かめない（理由を書く）」のどれかで登録する
   - **API を新しく作ったら、このテストに登録すること**。登録するときに、ブロックした相手が漏れないかを必ず考える
   - 条件を1か所外すと、このテストが API の名前と向き（A から・B から）を挙げて失敗することを確かめてある

### テーブル `blocks`

| 項目 | 列 | 内容 |
| --- | --- | --- |
| ブロックした人 | `blocker_id` | ユーザーを削除すると一緒に削除する（`ON DELETE CASCADE`） |
| ブロックされた人 | `blocked_id` | 同上 |
| ブロックした日時 | `blocked_at` | ブロック中の一覧の並び順 |

- 同じ組み合わせは1行まで（一意制約）。自分自身はブロックできない（検査制約）
- 解除は行を削除する

### API

| API | 内容 |
| --- | --- |
| `POST /api/users/{id}/block` | ブロックする（204）。すでにブロックしていても 204。自分自身は 400（「自分自身はブロックできません。」）、存在しないユーザーは 404 |
| `DELETE /api/users/{id}/block` | 解除する（204）。ブロックしていなくても 204 |
| `GET /api/blocks?page=&size=` | 自分がブロックしている人の一覧（ブロックした新しい順）。1件は `userId`・`username`・`displayName`・`profileImageUrl`・`blockedAt` |

- プロフィール（`GET /api/users/{id}`）に `blockedByMe`（ログイン中のユーザーがブロックしているか）を足した
- ブロックしたことはログに残す（ブロックした人・された人の ID と、削除・終了した件数）

### 既知の限界

- ブロックされた側の DM 一覧には、ブロックした人の名前とアイコンが残る（上記「ブロックされたことは相手に分かるか」）
