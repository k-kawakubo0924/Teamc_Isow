## 仕様

### DM一覧

- 上部に「メッセージリクエスト」への導線を設置し、件数を表示する
- 上部の検索欄からユーザの検索が行える
- やり取り中のユーザは、上からやり取りを最後に行った順に並べる
- 未読のメッセージ数がメッセージ一覧の一番右側に表示される
- 各行に表示する内容
  - ユーザ名
  - 経過時間（例：3分前、1時間前、昨日、2日前、5日前、2週間前）
  - 最新メッセージの本文（省略表示）
  - 状態ラベル（「終了」など）
- 下の「送信したリクエスト」から、自分が申請したリクエストの一覧が表示される

#### DM一覧の見出し

- 見出しは中央のロゴ「ISHO」のみとする
- 設計では、見出しの左上に**ピン留めした相談の一覧を開くマーク**があった（`design/DMlist.png`）
  - ホーム画面左上の通知ベルとは別のもので、通知一覧にはつなげない（通知ベルはホーム画面のみ。`notification.md`）
  - `design/DMlist.png` でマークに付いているバッジ「3」は、未読件数ではなく**ピン留めの件数**
- ピン留め機能が未実装の間は、このマークをいったん削除していた（21647d6）。**ピン留めを作ったため、マークを戻した**（下記「ピン留め」）
  - 押すと、ピン留めした相談の一覧（`/dm/pinned`）へ移る。バッジはピン留めの件数（0件なら出さない）。読み上げは「ピン留めした相談（3件）」
  - マークを削除していた間は「見出しはロゴだけで、押せるものがない」ことをテスト（`DmListPage.test.tsx`）で確かめていた。マークを戻したため、そのテストは役目を終え、マークがピン留めの一覧へのリンクであることを確かめるテストに置き換えた（意図した変更）

#### 設計画像と変えた点：ピン留めの件数のバッジを未読と違う見た目にした

- `design/DMlist.png` では、マークのバッジ「3」は、行の未読のバッジと同じ色（塗りつぶし）
- **未読と違う見た目にした**（塗りつぶさず、枠と控えめな文字色のバッジ）
- 理由：未読のバッジは「対応が必要」の合図で、ピン留めの件数は変わらない数字のため。同じ色だと、ピン留めの件数を未読と見間違える

### チャット画面

- 画面上部に相手のユーザ名とアイコンを表示する
- メッセージを入力して送信できる
- ＋ボタンから画像の送信が行える
- 各メッセージに送信時刻を表示する
- 右上のハンバーガーメニューから以下が行える
  - 通報は、メニューではなく相手のメッセージを押して行う（下記「通報」）
  - ブロック（下記「ブロック」。`profile.md`「ブロック」）
  - 会話終了
- 送信できるメッセージは、テキストと画像（JPEG・PNG、1件につき1枚、10MBまで）
  - 送った画像は、会話の当事者2人にだけ見せる（下記「画像」）
- 会話終了後は閲覧のみ。会話を再開することはできず、もう一度相談する場合は新しく申し込む（新しい会話になる）

### 相談の申し込み

- 相手のプロフィールの「相談する」ボタンから申し込む
- 押すと「申請済み」に変わる（`profile.md` 参照）
- 相談が届くと、相手に通知が飛ぶ（下記「通知」・`notification.md` 参照）
- 「相談を申し込む」を押すと、相手にリクエスト（メッセージリクエスト）が送られる。相手が承認して初めて会話できる
- 申し込むときに一言メッセージを添えられる。添えたメッセージは、会話の最初のメッセージとして保存する
- 同じ2人の間で「申請中」または「進行中」の会話は1つまで

### 拒否と再申請

- 拒否された場合、同じ相手には24時間申請を送れない
- 再申請は新しい会話レコードを作る。拒否された会話のレコードは残す（拒否の履歴として扱う）
- 拒否されたことは、申し込んだ側に通知で知らせる（「@◯◯ さんへの相談は承認されませんでした」。`notification.md`）
  - 通知をタップすると、拒否された会話のチャットを開く（当事者は読める）
  - DM一覧・送信したリクエストには、拒否された申請を出さない（これまでどおり）
  - 拒否から24時間以内は、相手のプロフィールの「相談を申し込む」ボタンの下にも理由が出る

### 通知

相談・メッセージでは次の通知を作る（詳しくは `notification.md`）。

- 相談が届いた（申し込まれた人へ）・承認された／拒否された（申し込んだ人へ）
- メッセージが届いた（相手へ。会話ごとに1件にまとめ、既読の後に届いたら未読に戻す）
- 会話の終了は通知しない

### 会話の状態

会話は1つのテーブルで管理し、状態で区別する。

| 状態 | 意味 | この状態になる条件 |
| --- | --- | --- |
| 申請中 | 相手の承認待ち | 相談を申し込んだとき |
| 進行中 | 会話できる | 申請中の会話を相手が承認したとき |
| 拒否 | 申請が断られた | 申請中の会話を相手が拒否したとき |
| 終了 | 会話が終わった | ハンバーガーメニューの「会話終了」、または30日やり取りがなかったとき（下記「30日やり取りがない相談の自動終了」）。ブロック・利用停止でも終了になる（下記「ブロック」「利用停止」） |

### 相談を受けられる件数の上限

- 相談を受けている「進行中」の会話は、1人あたり3件まで
  - 自分から申し込んだ会話は数えない
  - 申請中の会話は数えない。承認した時点で1件として数える
- 上限の件数は設定ファイルで変更できるようにする
- 上限に達している相手には「現在、新しい相談を受け付けていません」と表示し、「相談する」ボタンを押せなくする

### 実装での扱い（`conversations` / `messages` テーブル）

- 相談の申込は `POST /api/conversations`、申し込めるかの確認は `GET /api/users/{id}/consultation-status`
- 申し込めない理由（`reason`）は次のとおり。複数に当てはまる場合は上のものを返す

| reason | 条件 |
| --- | --- |
| `SELF` | 自分自身に申し込んだ（400） |
| `ALREADY_REQUESTED` | 自分の申請が申請中（409） |
| `REQUEST_RECEIVED` | 相手からの申請が申請中（409） |
| `IN_PROGRESS` | 進行中の会話がある（409） |
| `REJECTED_RECENTLY` | 自分の申請が拒否されてから24時間以内（409）。再度申し込める日時を `availableAt` で返す |
| `LIMIT_REACHED` | 相手が受けている進行中の会話が上限に達している（409） |

- 24時間の制限は、拒否された申請を出した本人だけにかける（断った側から申し込むことは止めない）
- 一言メッセージは任意（1000文字まで）。空白だけの場合は保存しない
- 上限の件数は `app.dm.max-received-active-conversations`（環境変数 `DM_MAX_RECEIVED_ACTIVE_CONVERSATIONS`、既定は3）
- 申請中は上限に数えないため、承認の時点でもう一度上限を確認する

#### 承認・拒否・終了

- 承認は `POST /api/conversations/{id}/accept`、拒否は `.../reject`、終了は `.../end`
- 承認・拒否は申し込まれた側だけ、終了は当事者のどちらでもできる
- 拒否・終了から先へは進めない（再申請は新しい会話になる）
- 終了したときは、終了日時と同時に終了した人（`ended_by_id`）を記録する（会話の終了を通知することになった場合に「誰が終了したか」に使う想定。今は通知しない。`notification.md` の未確定）。利用停止・30日やり取りがない相談の自動終了では NULL にする
- あわせて終了の理由（`end_reason`：`USER`・`BLOCK`・`SUSPENSION`・`INACTIVITY`）を記録する。この列ができる前に終了した相談は NULL
  - **API には理由そのものを返さない。返すのは「自動終了かどうか」（`endedByInactivity`）だけ**（下記「30日やり取りがない相談の自動終了」）

| HTTP | reason | 条件 |
| --- | --- | --- |
| 404 | なし | 会話が存在しない、または当事者でない（会話の有無が分からないよう、どちらも同じ応答） |
| 403 | `NOT_RECIPIENT` | 申し込んだ本人が承認・拒否しようとした |
| 409 | `INVALID_STATUS` | 状態が合わない（終了した会話を承認するなど） |
| 409 | `LIMIT_REACHED` | 承認する時点で、自分が受けている進行中の会話が上限に達している |

#### メッセージ・DM一覧

- 送信は `POST /api/conversations/{id}/messages`（multipart/form-data。`body` と `image` のどちらか一方は必須）。進行中の会話だけ送れる
- 取得は `GET /api/conversations/{id}/messages`。古い順で、最初は最新の30件を返す。さらに古いものは `before`（先頭のメッセージの ID）を付けて読む
  - チャット画面は最新から表示し、上にスクロールして過去を読むため、ページ番号ではなく ID で区切る
- 取得したときに、相手から届いた未読メッセージをすべて既読にする（取得した範囲に関係なく）
- 当事者なら、終了・拒否した会話のメッセージも読める
- 既読は、メッセージごとに相手が最初に読んだ日時（`read_at`）を記録する。もう一度開いても日時は変わらない。画面には表示していない（下記「未確定・要確認」）
- DM一覧は `GET /api/conversations`。最終メッセージの新しい順（メッセージがない会話は申込日時）
  - `status` で `requested`（申請中）・`active`（進行中）・`ended`（終了）・`chats`（進行中と終了）・`received`（受け取った申請）・`sent`（送った申請）に絞り込める。指定しなければ申請中・進行中・終了のすべて
  - `q` で相手のユーザー名・表示名の部分一致、`unread=true` で相手から届いた未読がある会話だけに絞り込める
  - 拒否された会話は一覧に出さない
  - `requestedByMe` で「メッセージリクエスト」（届いた申請）と「送信したリクエスト」を分けられる
- 会話・メッセージの操作は、当事者でなければ会話が存在しない場合と同じ 404 にする

#### 「相談を申し込む」ボタン（相手のプロフィール・フォロー中一覧）

| 状態 | ボタン |
| --- | --- |
| 申し込める | 押すと一言メッセージ（任意）の入力ダイアログを出す。申し込んだら「送信したリクエスト」（`/dm/sent`）へ移る |
| 申請済み（`ALREADY_REQUESTED`） | 「申請済み」と表示し、押せない |
| 上限に達している（`LIMIT_REACHED`） | 押せない。「現在、新しい相談を受け付けていません。」と表示する |
| 拒否から24時間以内（`REJECTED_RECENTLY`） | 押せない。理由を表示する |
| 相談中（`IN_PROGRESS`） | 「相談中」と表示し、押すとチャット画面へ移る |
| 相手から届いている（`REQUEST_RECEIVED`） | 「リクエストあり」と表示し、押すとメッセージリクエストの画面へ移る |

- プロフィールは `GET /api/users/{id}/consultation-status` で1人分を読む
- フォロー中一覧は、1人ずつ読むと人数分の通信になるため、`GET /api/users/consultation-statuses?ids=1,2,3`（最大50人）でページごとにまとめて読む。判定は1人分の API と同じ
- 申込が 409 で失敗したら（すでに申し込んでいた・上限に達したなど）、エラーを表示して状態を取り直す

#### 画面（`/dm`・`/dm/requests`・`/dm/sent`）

- DM一覧（`/dm`）には、やり取り中の会話（進行中・終了）だけを出す（`status=chats`）。検索欄は相手のユーザー名・表示名の部分一致（`q`）
- 申請中の会話は、受け取ったものを「メッセージリクエスト」（`/dm/requests`、`status=received`）、送ったものを「送信したリクエスト」（`/dm/sent`、`status=sent`）に出す
- 承認・拒否のボタンは、押した時点でその行の両方を無効にする（同じ申請に2回送ると2回目が 409 になるため）
  - 上限に達しているなど、やり直せる失敗のときだけ押せる状態に戻す
- チャット画面（`/dm/{id}`）の上部の相手は `GET /api/conversations/{id}` で読む
- 経過時間は、1日前を「昨日」と表示する
- 件数は `GET /api/conversations/summary` で読む（やり取り中の未読メッセージ・受け取った申請・送った申請）

#### チャット画面（`/dm/{id}`）

- 画面を開いたときは、最新のメッセージが見える一番下を表示する。上端までスクロールすると、さらに古いメッセージを読む
- 新しいメッセージが届いたときは、一番下付近を見ているとき（または自分が送ったとき）だけ一番下までスクロールする
- 送信時刻は、今日なら「14:02」、それより前なら「10/4 14:02」と表示する
- ＋で画像を選ぶと入力欄の上にプレビューし、送信ボタンで本文と一緒に送る（選んだ時点では送らない）
- 右上のメニューは「会話を終了する」（進行中のときだけ）と「ブロック」（会話の状態に関係なく出す）。どちらも取り消せないため、確認ダイアログを出す
- 相手のメッセージを押すと、その下に「このメッセージを通報」を出す（自分のメッセージには出さない。下記「通報」）
- 送れるのは進行中の会話だけ。申請中・終了・拒否では入力欄の代わりに理由を表示する

新しいメッセージの取得

- リアルタイムに届く仕組みがまだないため、画面を開いている間は5秒ごとに、最後のメッセージより新しいもの（`after`）と会話の状態を取り直す
- タブが裏にある間は止め、戻ってきたらすぐに取り直す
- 終了・拒否した会話は新しいメッセージが来ないため、取り直さない
- 取り直すたびに相手のメッセージは既読になる（開いている間は読んでいるものとする）
- 通知の仕組み（WebSocket など）ができたら、5秒ごとの取り直しを置き換える

#### 下部ナビの DM のバッジ

- やり取り中の会話の未読メッセージ数と、受け取った申請の件数の合計を出す
  - 通知をオフにした相談の未読は数えない（下記「通知オフ」）
- リアルタイムに届く仕組みがまだないため、次のタイミングで取り直す（遅れても最大1分）
  - 下部ナビのある画面を開いたとき・画面を移動したとき
  - ブラウザのタブに戻ってきたとき
  - 画面を開いている間は60秒ごと（タブが裏にある間は取り直さない）
  - 承認・拒否の直後
- 通知の仕組み（WebSocket など）ができたら、60秒ごとの取り直しを置き換える

### 30日やり取りがない相談の自動終了

- **最後のやり取りから30日**たった相談を、自動で終了にする（暦の1か月ではなく30日。月によって長さが変わらないように）
  - 進行中：「最終メッセージ日時」と「承認日時」の遅いほうから数える
    - 始まったときから数えないのは、仕様が「連絡を取っていなかったら」で、続いている相談を途中で切らないため
    - 承認日時も見るのは、申し込みの一言も最初のメッセージとして保存されるため（承認の後に誰も書かなくても、承認から30日は待つ）
  - 申請中：申込日時から30日（放置された申請で、申し込んだ側がずっと「申請済み」のまま申し込み直せなくならないように）
    - 「拒否」ではなく「終了」にする（拒否の通知と24時間の再申請の制限で、相手の意図のように見えるため。ブロックと同じ考え方）
- 終了した人は記録しない（NULL。利用停止と同じく、どちらの当事者が終えたのでもないため）。理由は `INACTIVITY`
- **通知はしない**（会話の終了はもともと通知しない。1回の実行で大量の通知を作らないためでもある）
  - その代わり、チャット画面の入力欄の代わりに「30日間やり取りがなかったため、自動で終了しました（閲覧のみ）」と出す（相手が終えたように見えないように）
  - 自動終了でなければ、今までどおり「この会話は終了しました（閲覧のみ）」とだけ出す
- **画面・API に返すのは「自動終了かどうか」（`GET /api/conversations/{id}` の `endedByInactivity`）だけ**。終了の理由そのもの（`end_reason`）は返さない
  - ブロック・利用停止が理由だと相手に伝わると、ブロックで隠した意味がなくなるため（相手からは「相手が終了した」のと同じに見せる）
  - テスト（`InactiveConversationTest`）で、本人・ブロック・利用停止で終了した相談の応答（詳細・一覧）に理由が含まれないことを確かめている
- 管理操作のログには残さない（管理者の操作ではないため）。アプリのログには件数だけを出す
- 終了したため、受けている相談の上限の件数（進行中3件）からも外れる

#### 定期実行（`InactiveConversationJob`・`InactiveConversationCloser`）

- **1時間ごと**（毎時15分。`app.dm.inactive-close-cron`）。終了が最大1時間遅れる程度で済み、受けられる相談の枠を早く空けるため（SQL は軽い）。テストでは「-」にして動かさない
- 作りは通報の証拠を消す定期実行（`EvidencePurgeJob`）と同じ。予期しない失敗でも例外を外に投げない（次の実行を止めない）
- **二重に処理しない**：対象の ID を探した後、1件ずつ別のトランザクションで行をロックしてから読み直し、まだ条件に合うときだけ終了する
  - すでに終了した相談は条件に合わないため、何度動いても同じ結果になる
  - メッセージの送信も同じ行をロックするため、同時に動いても、ちょうどメッセージが届いた相談は終了しない
  - 1件の失敗で、ほかの相談を止めない
- **時刻の扱い（重要）**：基準の時刻（今の30日前）は、アプリの `Clock` から読んだ今の時刻から計算し、SQL に `:cutoff` として渡す。**DB の現在時刻（`CURRENT_TIMESTAMP` など）に置き換えないこと**
  - このアプリは日時を日本時間で保存し、DB は UTC として扱うため、DB の現在時刻と比べると9時間ずれる（`admin.md`「時刻の扱い」。措置の実装で同じ問題を踏んでいる）
  - 終了日時にも、同じ `Clock` の今の時刻を引数で渡す（テストで時刻を固定できる）
- 30日は `InactiveConversationCloser.INACTIVE_PERIOD` の定数（設定では変えられない。画面の文言「30日」と食い違わないように。変えるときは画面の文言も直すこと）

#### 直すべき課題：時刻の取り方が2系統ある

- `Conversation`（申込・承認・拒否・終了の日時）と `Message`（送信・既読の日時）は、日時を `LocalDateTime.now()` で直接取っていて、アプリの `Clock` を通っていない
- 一方、措置・通報・お問い合わせ・この自動終了は `Clock` から読む。**時刻の取り方が2系統あると、いずれ食い違う**（例：`Clock` をサーバーの既定のタイムゾーン以外にした・テストで `Clock` を固定したときに、片方だけがずれる）
- 今は `Clock` がサーバーの既定のタイムゾーン（`Clock.systemDefaultZone()`）のため、どちらも同じ時刻になり、比べても食い違わない
- 今回の自動終了は `Clock` を使う方針とし、既存の `LocalDateTime.now()` はそのままにした。**`Conversation`・`Message` も `Clock` を通すように直すこと**（下記「未確定・要確認」）

### ピン留め

- ピン留めは**相談（会話）単位**で、1人ごとの設定（`conversation_user_settings` の `pinned_at`）
- **相手には分からない**：相手への応答に含めず、通知もしない
- **上限は10件**（「ピン留め」が全部の一覧と変わらなくならないように）。超えると 409（`PIN_LIMIT_REACHED`、「ピン留めできるのは10件までです。」）
  - すでにピン留めしたものをもう一度ピン留めするのは、上限でも成功する。外せば、またピン留めできる
  - 同時に押しても10件を超えないよう、自分のユーザーの行をロックしてから数える（承認の上限と同じ）
- ピン留めできるのは、DM一覧に出るやり取り中の相談（進行中・**終了**）。申請中・拒否は 409（`INVALID_STATUS`）
  - 終了した相談もピン留めできる（終わった相談の助言を後から見返す使い方のため）
- **DM一覧の並び順は変えない**。ピン留めした相談は、見出しの左上のマークから開く別の一覧（`/dm/pinned`）に、DM一覧と同じく最後のメッセージの新しい順で出す
  - 設計画像では、マークから別の一覧を開く作りで、一覧の上に固定する区切りはない。一覧の上にも固定すると、同じものが二重に出るため
  - DM一覧・ピン留めの一覧の行には、ピンの印を出す
- 操作はチャット画面のメニューの「ピン留めする」「ピン留めを外す」。取り消せる自分の設定のため、確認ダイアログは出さない。失敗（上限など）は見出しの下に出す
  - DM一覧の各行には長押し・スワイプの仕組みがなく、ボタンを並べると行が窮屈になるため、行には印だけを出す

| API | 内容 |
| --- | --- |
| `POST /api/conversations/{id}/pin` | ピン留めする。応答 `{"conversationId", "pinned", "muted"}`（自分の設定だけ） |
| `DELETE /api/conversations/{id}/pin` | ピン留めを外す（していなくても成功する） |
| `GET /api/conversations?status=chats&pinned=true` | ピン留めした相談の一覧 |

- 一覧の各行・`GET /api/conversations/{id}` に、自分の `pinned`・`muted` を足した。`GET /api/conversations/summary` に、自分のピン留めの件数 `pinnedCount` を足した
- 当事者でなければ 404（存在しない会話と同じ）

### 通知オフ

- 相談ごとに、1人ごとの設定（`conversation_user_settings` の `muted_at`）
- **メッセージは届く。知らせないだけ**（会話は普通に続けられる。DM一覧の行の未読の数も出る）
- 通知をオフにした相談は
  - **下部ナビの DM のバッジに数えない**（未読メッセージの合計 `unreadMessageCount` から除く）
  - **ホームの新着メッセージに出さない**
  - **メッセージの通知を作らず、既読にした通知も未読に戻さない**。すでにある通知はそのまま残す
  - ベルのバッジは変わらない（メッセージの通知はもともとベルに数えていない。`notification.md`）
  - 受け取った申請の件数はバッジに残す（通知オフは相談ごとの設定で、申請はその前の段階のため）
- オンに戻すと、次のメッセージから通知とバッジが戻る。オフの間に届いて読んでいないメッセージは未読のままなので、オンに戻すとバッジに数えられる
- **相手には分からない**：相手への応答に含めず、通知もしない。既読の記録は今までどおり開いたときだけ付く（既読は画面にも出していない）
- オフにできるのは進行中だけ（終了・申請中は 409 `INVALID_STATUS`）。オンに戻すのは、会話の状態に関係なくできる
- 操作はチャット画面のメニューの「通知をオフにする」「通知をオンにする」（確認ダイアログは出さない）。DM一覧・ピン留めの一覧の行には、通知オフの印を出す
- ピン留めと通知オフは1つの行で持ち、別々に外せる。どちらもなくなったら行を消す

| API | 内容 |
| --- | --- |
| `POST /api/conversations/{id}/mute` | 通知をオフにする。応答はピン留めと同じ形 |
| `DELETE /api/conversations/{id}/mute` | 通知をオンに戻す（オフでなくても成功する） |

### 3つの機能で共通のこと

- どれも**相手に通知しない**。相手への応答にも、1人ごとの設定（ピン留め・通知オフ）は含めない
- 新しい API は、API の棚卸し（`VisibilityInventoryTest`）に「自分の設定だけを扱う」として登録した。利用停止中は今までどおり 403
- テーブル `conversation_user_settings`（1人・1つの相談につき1行。`user_id`・`conversation_id` に一意制約）は `ddl-auto=update` で自動で入る。`conversations` に足した `end_reason` 列も同じ（DB の作り直しは要らない）
  - テストの後片付けで `conversations` を消すときは、先に `conversation_user_settings` を消すこと（会話とユーザーを参照しているため）

### ブロック

ブロックの全体（何が見えなくなるか・相手に分かるか・条件の書き忘れを防ぐ仕組み）は `profile.md`「ブロック」。ここでは相談（DM）での扱いだけを書く。

- ブロックした時点で、2人の間の**申請中・進行中の相談を終了にする**（終了した人は、ブロックした人）
  - 申請中の相談も「拒否」ではなく「終了」にする。拒否にすると、拒否の通知（「承認されませんでした」）と24時間の再申請の制限で、相手にブロックが分かるため
  - 終了の通知は作らない（会話の終了はもともと通知しない）
  - 終了したため、受けている相談の上限の件数からも外れる
- **過去のメッセージは、両方から読めるまま残す**（会話は消さない）
  - 次の段階で作る通報で、やり取りを確かめる必要があるため
  - 相手から見ると「相手が会話を終了した」のと同じに見える
  - 終了した会話のため、新しいメッセージは送れない
- **ブロックしても、相手の DM 一覧には自分の名前とアイコンが残る**。相手がそこから名前を押すと、プロフィールは「ユーザーが見つかりません」になる（既知の限界。`profile.md`「ブロック」）
- ブロック中は、お互いに相談を申し込めない（申込・申し込めるかの確認は、存在しないユーザーと同じ 404）
  - フォロー中一覧の「相談する」ボタンのためにまとめて確かめる API（`GET /api/users/consultation-statuses`）では、存在しないユーザーと同じく結果に含めない
- 会話の一覧・チャット画面・未読の件数は、ブロックの間柄でも条件で除かない（過去の会話を読めるまま残すため）

### 利用停止

利用停止の全体は `admin.md`「6. 措置」。ここでは相談（DM）での扱いだけを書く。

- 利用停止にした時点で、その人の**申請中・進行中の相談をすべて終了にする**（相手が申し込んだものも、その人が申し込んだものも）
  - 終了した人は記録しない（どちらの当事者が終えたのでもないため）。終了の通知は作らない（ブロックと同じ）
  - 過去のメッセージは、相手からは今までの終了と同じく読める。利用停止中の本人は、そもそもアプリを使えない
- **利用停止を解除しても、終了した相談は戻らない**
  - 戻すと、利用停止の間に相手が受けた相談と合わせて、相手の受付の上限（進行中は3件まで）を超えることがあるため
  - 続けたい場合は、もう一度申し込んでもらう
- 利用停止中の人には、相談を申し込めない（存在しないユーザーと同じ 404）

### 画像（2026-10-20 修正）

以前は、DM の画像も投稿の写真と同じく `/uploads/**` から認証なしで配っていて、URL を知っていれば当事者でなくても誰でも見られた（守りは、ファイル名が推測できない乱数であることだけ。URL は画面の共有・転送・ブラウザの履歴などから当事者の外に出うる）。このアプリは1対1で服の相談をするもので、DM の写真は公開の投稿より私的なものになりやすい（自分の姿・部屋・持ち物など）。非公開にした投稿の写真の穴（`admin.md`「非公開にした投稿の写真」）より重いと考えて直した。

- **規則は1文：「DM の画像は、会話の当事者2人にだけ配る」**。利用停止・ブロックは、この規則に出てこない
  - 終了した会話・ブロックで終わった会話・相手が利用停止中の会話でも、当事者は過去のメッセージを読める（上記「ブロック」「利用停止」）。画像も同じく、当事者2人には配る。アプリで見えていることと、サーバーが配る相手が、そのまま一致する
  - 利用停止中の本人は、そもそも API を使えない（403）
- 配り方：認証付きの API `GET /api/conversations/{conversationId}/messages/{messageId}/image` だけが配る
  - `<img>` のタグは認証のヘッダーを付けられず、`/uploads/**` では誰が見に来たか分からない。そのため、画面はこの API から中身を取得し、その場限りの URL（`URL.createObjectURL`）にして表示する
  - 当事者でない人・会話のメッセージでない・画像がない・ファイルが読めない、のどれも、会話が存在しない場合と同じ 404（会話やメッセージがあることを探れないように）。ログインしていなければ 401
  - 画像を取得しても、既読にはしない（既読はメッセージの一覧を読んだとき）
- **管理者にも見せない（404）**
  - 理由：通報されたものは証拠として写しがある（`admin.md`「5. 通報」の「証拠」）ので、それ以上の閲覧は必要がない。「管理者なら見られる」と分かった時点で、DM が私的な場でなくなる
- **ブラウザには残さない（`Cache-Control: no-store`）。その代わり、画面を開いている間だけメモリに控える**（`frontend/src/hooks/authorizedImageCache.ts`）
  - 理由：借りた端末や共用の端末に DM の写真が残るのは、まさに今回なくしたい状態のため
  - 控えがあるため、5秒ごとの取り直しで一覧が作り直されても、チャットを開き直しても、同じ画像は取りに行き直さない。控えは、ログアウト（ほかのタブでのログアウトも）・別の人のログイン（トークンが変わったとき）・再読み込みで消える。100枚を超えたら、長く使っていないものから捨てる
  - 読み込み中は、画像の場所に枠を出す（読み込み後に画面が大きく動かないように。読み込んだら、今までどおり一番下にいるときは一番下へ動かす）。読めなければ「画像を読み込めませんでした」
  - 通報の証拠の写真（管理画面）も、同じ部品（`useAuthorizedImage`）で表示する。あわせて、証拠の写真の取得も、ほかの API と同じく 401 でログアウトするようにした（以前は、期限切れでも画像だけが失敗し続けた）
- メッセージの応答は、画像があるか（`hasImage`）だけを返す。**保存先（ファイル名）は応答に出さない**（以前の `imageUrl` はなくした）
- **保存先**
  - **画像は、公開の画像（投稿の写真・プロフィール画像）と同じ置き場（`app.image.local.dir`）に置いたまま。`/uploads/**` から取れないのは、配ってよい画像の許可リスト（`PublicImageAccess`）に DM の画像を入れていないことだけによる**。この 404 は、テスト（`MessageImageApiTest`「DMの画像は_ファイル名が分かっても_uploadsからは誰も取得できない」・`PublicImageAccessTest`）で固定している。画像を置いたままにする以上、ここが唯一の防波堤
  - **クラウドの保管場所（公開の入れ物）に移すなら、DM の画像には非公開の置き場が必要**（公開の入れ物の画像は、このアプリを通らずに配られ、許可リストが働かないため）
  - 置き場を移さなかったため、すでにある画像を移す作業はない。変える前の DM の画像の URL（`/uploads/...`）は、変えた時点から開けなくなる
- 速さ：画像1枚ごとに、トークンの確認・ユーザーと会話の確認（SQL 2本）・ファイルの読み込みをする。DM の一覧・ホームの新着メッセージには DM の画像は出ない（「画像が送信されました」の文字だけ）ため、取りに行くのはチャット画面だけ
- テスト：`MessageImageApiTest`（配る相手・`/uploads` からは取れない・応答に保存先を出さない）、`DmChatImage.test.tsx`（画面）、`authorizedImageCache.test.ts`（控え）

### 通報

通報の全体（理由・証拠・管理者の画面）は `admin.md`「5. 通報」。ここでは DM での扱いだけを書く。

- 通報できるのは、会話の当事者が、相手のメッセージを1件ずつ。チャット画面で相手のメッセージを押し、「このメッセージを通報」から
- 管理者が見られるのは、**通報されたメッセージと、その前後5件ずつ（最大11件）だけ**。通報した時点でコピーし、通報の後に送られたメッセージは含めない
  - 管理者の画面では、11件のうちどれが通報されたメッセージかを示す
  - 管理者が DM の通報の詳細を開いたことは、操作ログに残る
- 通報しても相手には伝わらない。会話はそのまま続けられる（自動でブロックも、会話の終了もしない。通報の完了の画面でブロックを案内する）
- ブロックの間柄でも、過去の会話は読めるため、相手のメッセージを通報できる
