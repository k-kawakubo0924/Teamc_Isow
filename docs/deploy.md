# 公開（デプロイ）のときにやること

> **今は使わない（2026-10-29、デプロイが不要になった）。公開することになったときのために残す。**

公開のときにやることを、ここに全部集める。**理由の詳しい説明は、それぞれの機能の docs に残し、ここからは参照する**（理由は、その機能の説明と一緒にあるほうが読みやすいため）。
機能の docs に「公開のときに〜」を書き足したら、ここにも1行足すこと（散らばると、公開のときに拾い集められず、必ず取りこぼす）。

どの項目にも「なぜ必要か」と「やらないとどうなるか」を書く。手順だけだと、急いでいるときに飛ばされるため。

## 本番の構成（決まっていること）

| 役割 | 使うもの | 注意 |
| --- | --- | --- |
| 画面 | Cloudflare Pages | |
| バックエンド | Render の無料枠 | メモリ 512MB。ディスクは再デプロイで消える。使われないと眠る |
| DB | Neon | 無料枠は計算の時間（CU 時間）に月の上限がある |
| 画像 | Cloudflare R2 | バケットは2つ（画像・通報の証拠）。どちらも非公開 |
| 入口 | Cloudflare | 1リクエストの上限 100MB（無料プラン） |

## まだ作っていないため、公開できないもの

- [ ] **画像の保存先を R2 にする**（ステップ1で止めた。残りは `image-storage.md` の「ステップ」の2から）
  - なぜ：Render のディスクは再デプロイで消える。今の画像・通報の証拠はディスクに置いている
  - やらないと：再デプロイのたびに、投稿の写真・プロフィール画像・DM の画像・通報の証拠がすべて消える
- [ ] **Flyway を入れ、スキーマを Flyway で作る**
  - なぜ：本番では `ddl-auto=update` を使わない（`CLAUDE.md`）。本番にはまだデータがないため、最初の1本で今のスキーマ全体を作れば済む
  - やらないと：本番の表を作る手段がない。`update` で代用すると、エンティティの変更で列が消えずに残る・制約が変わらないなど、DB が静かにずれていく

## アプリの設定（Render の環境変数）

- [ ] **`JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=60`**（Java が使えるメモリの割合。**60% から始める**）
  - なぜ：何も指定しないと、Java が使えるメモリはサーバーの 4分の1（512MB なら約128MB）になり、写真の処理が重なると足りない（`post.md`「写真の大きさ」の「メモリ」）
  - やらないと：写真10枚の投稿などが重なったときに、Java の中でメモリが足りなくなり、その処理が失敗する
  - **60% から始める理由**：高すぎるとコンテナごと強制終了され、動いていた処理も巻き添えになる。低すぎる場合は Java の中で足りなくなるだけで、その処理が失敗するにとどまる。傷の浅いほうから試す。値は、下記「起動後に確かめること」の「大きな写真10枚の投稿を2つ同時に」で決める
- [ ] **`TZ=Asia/Tokyo`**（サーバーのタイムゾーン）
  - なぜ：このアプリは、日時を**日本時間**で保存する前提で作っている（アプリの `Clock` はサーバーの既定のタイムゾーン。`admin.md`「時刻の扱い」）。手元の PC は日本時間だが、Render は UTC で動く
  - やらないと：保存する日時・画面に出る日時が9時間ずれる。利用停止の期限・180日後の証拠の削除・30日やり取りがない相談の終了の判定もずれ、定期実行（毎日 3:00 の証拠の削除）は日本時間の 12:00 に動く
- [ ] **`server.forward-headers-strategy` を設定する**（`SERVER_FORWARD_HEADERS_STRATEGY=native`）
  - なぜ：ログインの失敗回数・パスワードの再設定の回数を、接続元の IP アドレスごとに数えている（`auth.md`「IP アドレスの取り方とプロキシ」）。Render 自体がプロキシのため、設定しないと全員が Render のプロキシの IP アドレスに見える
  - やらないと：IP アドレスごとの上限がサイト全体で1つになり、誰か1人が30回失敗すると、全員がログインできなくなる
  - **プロキシがいないのに有効にすると、逆に穴になる**：`X-Forwarded-For` は誰でも書けるため、ヘッダーを書き換えるだけで IP アドレスの上限をすり抜けられる。外からの通信が必ずプロキシを通り、プロキシがこのヘッダーを付け直す構成のときだけ有効にする。**開発では設定しない**
  - **Cloudflare を挟む場合**：`X-Forwarded-For` に Cloudflare の IP アドレスが入るため、信用するプロキシ（`server.tomcat.remoteip.trusted-proxies`）に Cloudflare の IP アドレスの範囲を加えないと、全員が Cloudflare の少数の IP アドレスに見える（同じ問題が残る）。また、Render の URL（`*.onrender.com`）に直接来る通信は Cloudflare を通らない。どちらも、下記「起動後に確かめること」で実際の IP アドレスが取れているかを確かめる
- [ ] **`JWT_SECRET` を本物の値にする**（README「1. 環境変数の設定」の方法で新しく作る。開発の値を使い回さない）
  - なぜ：ログインの鍵（JWT）の署名に使う。この値を知っている人は、誰にでもなりすませる鍵を作れる
  - やらないと：開発の `.env` の値やテストの値が漏れていれば、本番の全アカウントを乗っ取られる
- [ ] **DB の接続先とパスワードを本物の値にする**（`SPRING_DATASOURCE_URL`・`DB_USER`・`DB_PASSWORD`）
  - なぜ：今の設定（`application.properties`）は、ホスト・ポート・DB 名から URL を組み立てるだけで、Neon が必要とする暗号化の指定（`sslmode=require`）を付けられない。`SPRING_DATASOURCE_URL` を環境変数で渡せば、設定ファイルより優先される
  - やらないと：接続できずに起動しない。既定のパスワード（docker-compose と同じ値）のままなら、誰でも DB に入れる
- [ ] **`spring.jpa.hibernate.ddl-auto=validate`**（`SPRING_JPA_HIBERNATE_DDL_AUTO=validate`。スキーマは Flyway で作る）
  - なぜ：本番では、アプリに表を勝手に作り変えさせない（`CLAUDE.md`）。`validate` なら、エンティティと表が食い違っていれば起動時に気づける
  - やらないと：`update` のままだと、列の削除・型の変更が反映されないまま、DB が静かにずれていく
- [ ] **`DEV_SEED_ENABLED` を設定しない**（`false` のまま）
  - なぜ：開発用のテストデータは、README に書いた共通のパスワードでログインできるアカウントを作る（README「開発用のテストデータ」）
  - やらないと：誰でも、そのアカウントでログインできる
- [ ] **`FRONTEND_ORIGIN` を画面の URL（Cloudflare Pages）にする**
  - なぜ：CORS で許可する画面の URL と、メールのリンクの土台の URL を、この値から作る（`auth.md`「本番への切り替え」）
  - やらないと：画面から API を呼べない。メールのリンク（パスワードの再設定など）が `localhost` を指し、開けない
- [ ] **`ADMIN_EMAIL` に管理者のメールアドレスを入れる**（先にそのアドレスで新規会員登録をしてから、起動し直す。README「管理者の用意」）
  - なぜ：管理者は、起動時にこのアドレスのユーザーを管理者にすることでしか作れない
  - やらないと：管理画面に誰も入れず、通報・お問い合わせに対応できない

## DB（Neon）

- [ ] **接続プールが接続を手放す設定にする**（`SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE=0`・`SPRING_DATASOURCE_HIKARI_IDLE_TIMEOUT` を短め（例：60000＝1分）・`SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE` を小さめ（例：5））
  - なぜ：Neon は、接続がない時間が続くと眠り、眠っている間は計算の時間（CU 時間）を使わない。接続プールの既定（常に10本つないだまま）では、一度も眠らない
  - やらないと：Neon が眠らず、無料枠の月100CU時間を使い切り、**月の半ばで DB が動かなくなる**（アプリ全体が止まる）
  - 定期実行（30日やり取りがない相談の終了は毎時、証拠の削除は毎日）は、そのたびに Neon を起こす。毎時なら1日24回起きるため、使う CU 時間を Neon の画面で確かめる
- [ ] **`/api/health` が DB に触らないこと**（今は `{"status":"ok"}` を返すだけで、DB に触らない。`HealthController`）
  - なぜ：Render を眠らせないために、外から定期的にこの URL を呼ぶ（下記）。ここで DB に触ると、そのたびに Neon も起きる
  - やらないと：Neon が眠らず、上と同じく月の半ばで DB が動かなくなる。**この URL に DB の確認を足さないこと**

## メール

- [ ] **送信先を Mailpit から実際の送信サービスに差し替える**（環境変数だけ：`MAIL_HOST`・`MAIL_PORT`・`MAIL_USERNAME`・`MAIL_PASSWORD`・`MAIL_SMTP_AUTH=true`・`MAIL_SMTP_STARTTLS=true`。`auth.md`「本番への切り替え」）
  - なぜ：既定は開発用の Mailpit（`localhost:1025`）で、メールは外へ出ない
  - やらないと：パスワードの再設定・メールアドレスの変更のメールが届かない（画面には「送りました」と出るため、利用者は気づけない）
- [ ] **`MAIL_FROM` を、自分で持っているドメインのアドレスにする**（既定の `no-reply@isho.local` は使えない）
  - なぜ：差出人のドメインで、送信の正しさを確かめられる（下の SPF・DKIM）
  - やらないと：受け取る側で拒否される・迷惑メールに入る
- [ ] **差出人のドメインに SPF・DKIM を設定する**
  - なぜ：受け取る側（Gmail など）は、差出人のドメインが送信を許しているか（SPF）、途中で書き換えられていないか（DKIM）を確かめる
  - やらないと：迷惑メール扱いになり、**パスワードの再設定が機能しない**（再設定のメールが届かないと、パスワードを忘れた人は二度とログインできない）

## 画像（R2）

R2 の実装はステップ1で止めた（上記「まだ作っていないため、公開できないもの」）。設計と決めたことは `image-storage.md`。

- [ ] **バケット（画像・通報の証拠）が2つとも非公開であること**（Cloudflare の画面で、r2.dev の公開 URL・独自ドメインがどちらのバケットにも付いていないこと）
  - なぜ：見えてはいけない画像（非表示の投稿の写真・利用停止中のユーザーの投稿の写真・DM の画像）を止めているのはアプリで、バケットが公開されていると、アプリを通らずに取れる（`admin.md`「非公開にした投稿の写真」・`dm.md`「画像」）
  - やらないと：URL を知っている人が、非表示の投稿の写真や DM の画像を見られる
- [ ] **証拠のバケットが公開になっていないこと**（上と同じ確認を、証拠のバケットについて必ず行う）
  - なぜ：証拠は、通報された写真・DM の画像の写しで、管理者だけが見るもの（`admin.md`「証拠の写真の配信」）。アプリは「バケットの名前が同じなら起動しない」までしか確かめない（公開の設定を読む鍵をアプリに持たせないため。設定を読める鍵をもう1つ持つこと自体が危険で、デプロイするのは1人のため、この確認で代わりとする）
  - やらないと：通報された DM の写真などが、URL を知っている人に見える
- [ ] **証拠のバケットと画像のバケットが別であること**
  - なぜ：証拠を、公開されうる画像と同じ場所に置かないため（ローカルの「フォルダが重なったら起動しない」と同じ守り）
  - やらないと：アプリが起動しない（同じ名前なら起動時に止める）
- [ ] **R2 の鍵をコミットしない**（Render の環境変数にだけ入れる。`.env` にも書かない）
  - なぜ：鍵があれば、バケットの中身をすべて読み書き・削除できる
  - やらないと：リポジトリを見られる人全員が、DM の画像・通報の証拠を読め、消せる

## 画面（Cloudflare Pages）

- [ ] **`VITE_API_BASE_URL` をバックエンドの URL にしてビルドする**
  - なぜ：画面は、ビルドしたときのこの値に API を呼びに行く（実行時には変えられない）
  - やらないと：画面が `localhost` の API を呼び、何も動かない
- [ ] **画面の途中の URL を直接開けること**（例：メールのリンクの `/reset-password#token=…`）
  - なぜ：画面は1枚のページで、`/login` などの道筋は画面の中で切り替えている。直接開いたときに、Pages が `index.html` を返す必要がある
  - やらないと：メールのリンクが 404 になり、パスワードの再設定・メールアドレスの変更ができない

## 起動後に確かめること

- [ ] **大きな写真10枚の投稿を2つ同時に送って、落ちないか**（`MaxRAMPercentage` の値をここで決める）
  - なぜ：アップロードは、画像の処理でいちばんメモリを使う（`post.md`「写真の大きさ」）。最初の 60% は見積もりで、実機で確かめていない
  - やらないと：利用者が写真を上げた時点で、落ちるかどうかが分からないまま公開することになる
  - 手順
    1. スマホで撮った大きめの写真（2,400万画素前後、1枚 9MB 以下）を10枚用意する
    2. 別々のアカウントで、2つのブラウザから、写真10枚の投稿をできるだけ同時に送る。これを数回くり返す
    3. Render のログとメトリクスを見る
  - 判断
    - 2つとも投稿できた：60% のままでよい
    - 片方が失敗し、ログに `OutOfMemoryError`（Java の中でメモリが足りない）：割合を 5〜10 ずつ上げて、もう一度試す
    - Render がメモリの使いすぎでコンテナを再起動した（イベントに出る）：割合を下げる。**この場合は、動いていたほかの処理も巻き添えになっている**
- [ ] **Render を眠らせない仕組みが動いているか**（外から定期的に `/api/health` を呼ぶ）
  - なぜ：Render の無料枠は、15分ほど使われないと眠り、次のアクセスで起きるまで待たされる。眠っている間は定期実行（証拠の削除・相談の自動終了）も動かない
  - やらないと：久しぶりに開いた人が、画面が動くまで長く待たされる。定期実行が止まり、180日を過ぎた証拠が消えない
  - 確かめ方：しばらく誰も使わない時間（夜など）の後に、Render のログに `/api/health` が呼ばれ続けているか、画面がすぐ開くかを見る
- [ ] **ログインの失敗回数が、利用者ごとの IP アドレスで数えられているか**（上記「`server.forward-headers-strategy`」）
  - なぜ：設定を間違えると、全員が同じ IP アドレスに見える・偽装できる、のどちらかになる。設定だけでは分からない
  - やらないと：誰か1人の失敗で全員がログインできなくなる、または、上限をすり抜けられる
  - 確かめ方：別々の回線（スマホの回線と家の回線など）から1回ずつわざと失敗し、ログに出る IP アドレスがそれぞれの回線のものになっているかを見る
- [ ] **日時が日本時間で保存・表示されているか**（上記「`TZ=Asia/Tokyo`」）
  - なぜ：設定が効いていないと、エラーにならずに9時間ずれるだけで、気づきにくい
  - やらないと：期限の判定・定期実行の時刻が静かにずれる
  - 確かめ方：投稿を1件作り、画面に出る投稿日時が今の日本時間と合っているかを見る
- [ ] **メールが受信箱に届くか**（迷惑メールに入っていないか）
  - なぜ：SPF・DKIM の設定の誤りは、送る側ではエラーにならない
  - やらないと：パスワードの再設定が機能しないまま公開することになる
  - 確かめ方：Gmail など、いくつかのメールサービスのアドレスで、パスワードの再設定のメールを頼み、受信箱に届くか・リンクが開けるかを見る
