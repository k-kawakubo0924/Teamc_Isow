## 詳細設定

自分のプロフィール右上の三点リーダーから遷移する。

### 仕様

メニュー項目は以下の6つ。

1. プロフィール設定 → プロフィール編集画面へ（`profile.md` 参照）
2. パスワード再設定 → ログイン中のパスワードの変更（`/settings/password`。下記「パスワード再設定（ログイン中の変更）」）
3. メールアドレス再設定 → メールアドレスの変更（`/settings/email`。下記「メールアドレスの変更」）
4. ブロック中のアカウント → ブロックした人の一覧と解除（`/settings/blocks`。`profile.md`「ブロック」）。画面画像（`design/DetailedSettings.png`）にはない項目
5. お問い合わせ → お問い合わせ画面へ（`/settings/contact`。下記「お問い合わせ」）。画面画像にはない項目
6. ログアウト

## パスワード再設定（ログイン中の変更）

ログインしている人が、今のパスワードを知っていて変える画面（`design/ResetPassword.png`）。パスワードを忘れたときの再設定（ログイン前。メールを使う）は `auth.md`「パスワードの再設定（ログイン前）」。

### 仕様

- 入力項目
  - 現在のパスワード（設計画像どおり。メールアドレスの変更とそろえて、必ず求める）
  - 新しいパスワード（8文字以上、英字と数字を含めてください。新規会員登録と同じ規則）
  - 確認用パスワード
- エラーとなる条件
  - 現在使っているパスワードが違う（欄の下に「現在のパスワードが正しくありません」）
  - 新しいパスワードと確認用パスワードが違う
  - 新しいパスワードが今と同じ
- 右上の「完了」を押したら変更が完了し、詳細設定に戻って「パスワードを変更しました。ほかの端末はログアウトしました。」と出す
- 変更すると、トークンの世代を進めて**ほかの端末をすべてログアウトさせる**（`auth.md`「トークンの世代」）。操作した端末だけは、返ってきた新しいトークンでログインしたままにする
- 登録アドレスに「パスワードが変更されました」と知らせる（`auth.md`「メールの送信」）
- API：`POST /api/users/me/password`（本文 `{"currentPassword", "newPassword"}`。200 で新しいトークン `{"token", "expiresAt"}`。入力の誤りは 400）

## メールアドレスの変更（メールアドレス再設定）

### 仕様

- 現在使っているメールアドレスはあらかじめ表示してある
- 入力項目
  - 新しいメールアドレス（入力したアドレスに確認メールを送ります）
  - 確認用メールアドレス
  - **現在のパスワード**（設計画像にない欄。下記「設計画像と変えた点」）
- エラーとなる条件
  - 新しいメールアドレスと確認用メールアドレスが違う
  - 現在のパスワードが違う
  - 新しいメールアドレスが今と同じ
- 右上の「完了」を押したら申し込みを受け付け、**新しいアドレスに確認メールを送る**。確認メールのリンクを開いて「メールアドレスの変更を完了する」を押した時点で、変更が完了する
  - 画面には「確認メールを送りました。新しいメールアドレスに届いたリンクを開くと、変更が完了します。完了するまでは、今のメールアドレスでログインできます。」と出す
- **完了するまでは、古いアドレスでログインする**

#### 設計画像と変えた点：現在のパスワードを求める

- `design/ResetMailadress.png` には現在のパスワードの欄がないが、**足した**
- 理由：メールアドレスの変更は**アカウントの所有権を移す操作**であり、開いたままの端末を触られただけで奪われるのを防ぐため
- ログイン中のパスワードの変更（上記）も、そろえて現在のパスワードを求める

#### 確認のリンク

- `purpose=email_change` の JWT（`auth.md`「パスワードの再設定」のリンクの鍵と同じ作り）。**有効期限は24時間**
- 鍵には申し込みの ID だけを入れ、**新しいアドレスは URL・鍵に入れない**（申し込みの内容は `email_change_requests` に持つ）。鍵は URL の `#` の後ろ
- 変更待ちは1人1件だけ。**新しく申し込むと、前の申し込みのリンクは使えなくなる**。完了したリンクも、もう使えない
- 申し込みの後にパスワードを変えた（トークンの世代が進んだ）ら、リンクは使えない（下記「パスワードを変えると、申し込み中の変更は完了できない」）

#### パスワードを変えると、申し込み中の変更は完了できない

- **パスワードの再設定（ログイン前）・ログイン中のパスワードの変更をすると、その前に申し込んだメールアドレスの変更は完了できなくなる**
- 理由：次の筋を閉じるため。**本人が正しく対処したのに、乗っ取りが完了してしまう**のを防ぐ
  1. 攻撃者がアカウントに入り、自分のアドレスへの変更を申し込む
  2. 本人が気づいて、パスワードを再設定・変更する（すべての端末がログアウトになる）
  3. 攻撃者が、自分のメールボックスに届いた確認リンクを押す
  4. （止めなければ）アドレスが攻撃者のものに変わり、本人は入れなくなる
- 確認の完了には**ログインが要らない**（ログインしていない端末でも完了できる作りのため）。そのため、2で攻撃者をログアウトさせても、3は止められない
- 止め方：確認のリンクの鍵に、発行した時点の**トークンの世代**を入れ、完了するときに今の世代と比べている。パスワードの再設定・変更で世代が進むため、その前に発行した確認のリンクは使えなくなる（\`AccountTokens\`・\`EmailChangeService.confirm\`）
  - 申し込みの行は変更待ちのまま残るが、リンクが使えないため完了しない（本人の手で新しく申し込めば、その行は無効になる）
- テスト（\`EmailChangeApiTest\`）で、上の1〜4の手順を、ログイン前の再設定・ログイン中の変更のそれぞれで確かめている。世代の比較を外すと、この2つのテストは「変更が完了してしまう」で失敗することも確かめた。**この比較は外さないこと**
- **ログインしていない端末でも完了できる**（鍵そのものが、新しいアドレスを受け取れる本人であることの証明になるため）。開いただけでは完了せず、ボタンを押したときだけ完了する
- 鍵が使えないときは 400：「このリンクは使えません。有効期限（24時間）が切れたか、すでに使われているか、新しい手続きで無効になりました。もう一度、変更の手続きをしてください。」

#### 新しいアドレスがすでに使われているとき

- 申し込んだ人には、**ほかの場合と同じ文言**を返す（他人の登録の有無が分からないように）
- そのアドレスの持ち主にだけ「別のアカウントから、このメールアドレスへの変更の手続きがありました。変更は行っていません」と知らせる（申し込んだアカウントのことは書かない）
- 申し込みの後、完了するまでの間にほかで登録された場合は、完了できない（400）
- ただし、新規会員登録の画面からは登録済みかどうかが分かる（`auth.md`「登録の画面との食い違い」）

#### 完了したとき

- トークンの世代を進め、**すべての端末をログアウトさせる**（乗っ取った人の端末も追い出すため）。確認の画面からログイン画面へ移り、「メールアドレスを変更しました。新しいメールアドレスでログインしてください。」と出す
- **古いアドレスに「メールアドレスが変更されました」と知らせる**（乗っ取られたときに本人が気づけるように）。新しいアドレスは書かない
- **この知らせでは「運営にご連絡ください」とは案内しない**
  - 乗っ取られた本人はログインできず、お問い合わせはログインが必要なため、**実際には連絡する手段がない**。手段がないのに案内するのは、案内しないより悪い
  - そのため、今は案内できないことを前提にした文言にした：「この変更に心当たりがない場合は、第三者にアカウントを使われた可能性があります。申し訳ありませんが、現在、このメールからアカウントを取り戻す手段はご用意できていません。同じパスワードをほかのサービスでも使っている場合は、そちらのパスワードを変更してください。」
  - 将来の直し方は下記「未確定・要確認」

#### 送りすぎを防ぐ

- 申し込みは **1時間に3回**まで（ログインしている人なので、超えたら 429 で伝える：「メールアドレスの変更の手続きは1時間に3回までです。あと約N分で、もう一度申し込めます。」）
  - N は、直近1時間で最も古い申し込みから1時間たつまでの残り時間（分。端数は切り上げ、1分に満たなくても「あと約1分」）。同じ残り時間を \`Retry-After\` ヘッダー（秒）でも返す
  - パスワードの再設定（ログイン前）は、制限にかかったことも隠す作り（同じ応答を返す）のため、残り時間は伝えない（\`auth.md\`「パスワードの再設定」）
- アプリのログにメールアドレス・鍵・パスワードを書かない（`auth.md`「メールの送信」）

#### API・テーブル

| API | 内容 |
| --- | --- |
| `POST /api/users/me/email-change` | 変更を申し込む（ログインが必要）。本文 `{"currentPassword", "newEmail", "confirmEmail"}`。202 `{"message"}`。入力の誤りは 400、回数の上限は 429 |
| `POST /api/auth/email-change/confirm` | 確認のリンクの鍵で変更を完了する。本文 `{"token"}`。204。トークンなしで呼べる。鍵が使えなければ 400 |

- テーブル `email_change_requests`：申し込み1件（ユーザー・新しいアドレス・申し込んだ日時・完了した日時・無効にした日時）。`ddl-auto=update` で自動で入る
  - 完了・無効にしたら、新しいアドレスの列を消す（行は回数の制限を数えるために残す）
- `users` に `token_version`（トークンの世代）・`password_reset_requested_at` を足した（`auth.md`）。既存の行も使えるよう、`token_version` には DB の既定値 0 を付けた

## お問い合わせ

### 仕様

- 入口は2つ
  - ログイン中：詳細設定のメニューの「お問い合わせ」（`/settings/contact`。詳細設定と同じく、下部ナビゲーションは出さない）
  - 利用停止中：利用停止の画面（`/suspended`）の「利用停止について問い合わせる」（下記「利用停止中の申し立て」）
- 入力項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 返信先メールアドレス | **任意** | ログイン中は、登録済みのアドレスを最初から入れておく。別の連絡先を使いたい場合に書き換える欄。形式を確かめる（255文字まで） |
| お問い合わせの種類 | 必須 | アプリについて／ユーザーについて／アカウントについて／その他（`design/Contact us.png` のとおり） |
| お問い合わせ内容 | 必須 | 1000文字まで（画像の「0 / 1000」）。前後の空白を除き、改行は `\n` にそろえてから数える。空白・改行だけは未入力と同じ |

- 送信ボタンを押したとき、必須項目が未記入なら欄の下に警告文を出し、送らない。1000文字を超えたら文字数を赤くし、警告を出して送らない
- 送ったら「お問い合わせを受け付けました。」と出す

#### 設計画像と変えた点：下部ナビゲーションを出さない

`design/Contact us.png` では画面の下に下部ナビゲーション（ホーム・検索・投稿・DM・プロフィール）が出ているが、**出していない**。

- 理由：お問い合わせは詳細設定から開く画面で、ほかの設定画面（詳細設定・プロフィール編集・ブロック中のアカウント）はどれも下部ナビゲーションを出さず、見出しの「戻る」で戻る作りのため。それにそろえた

#### 設計画像と変えた点：返信先メールアドレスを任意にした

`design/Contact us.png` では「返信先メールアドレス」は必須だが、**任意**にした。理由は2つ。

1. 返信はしない（下記「返信」）のに必須で集めると、**使い道のない個人情報を預かる**ことになるため
2. ログイン中の人のアドレスは**すでに持っている**ため、もう一度入力させる意味がないため

- そのため「別の連絡先を使いたい場合に入力する欄」という位置づけにする（欄の下に、その旨を書く）
- サーバーは、登録済みのアドレスと同じなら保存しない（大文字・前後の空白の違いは同じとみなす）。違うアドレスのときだけ保存する

#### 送信先

- DB（`contact_inquiries`）に保存し、管理画面で見る（`admin.md`「7. お問い合わせ」）。メールは送らない（メール送信の仕組みがまだないため）

#### 返信

- **受け取るだけで、返信はしない**（メールが送れないため。利用停止中の人には、アプリ内の通知も届かない）。返信の手段は下記「未確定・要確認」
- 返事を待ち続ける人が出ないよう、フォームの上に次を出す（送った後も出す）
  - 「現在、個別の返信は行っていません。」
  - 利用停止中の申し立てでは、あわせて「見直しの結果は、ログインできるかどうかでお知らせします。」

#### 利用停止中の申し立て

利用停止中は、すべての API が 403 になり、ログインしてもトークンが出ない（`admin.md`「6. 措置」）。そのままでは、異議を申し立てたい本人がお問い合わせを送れない。そこで、**申し立て専用の短期の鍵**を渡す。

- 利用停止の 403 の応答（ログインで、パスワードが正しいとき・有効なトークンで API を呼んだとき）に、申し立て用の鍵 `appealToken` を入れる
  - 受け取れるのは、パスワードか有効なトークンで本人と確かめられた人だけ
- 鍵は JWT で、`purpose` が `suspension_appeal`。有効期限は1時間。**そのときの利用停止（`suspended_at`）に結びつける**
- 申し立ては `POST /api/contacts/appeal` に、トークンを付けずに、鍵を本文で送る（この API はトークンなしで呼べる）。サーバーは、署名・期限・`purpose`・**今も同じ利用停止が続いていること**を確かめる
  - 鍵が正しくない・期限切れ：401（「受付の期限が切れました。もう一度ログインしてから送ってください。」）
  - 解除された・期限を過ぎた・別の利用停止になった：409（「利用停止の状態が変わったため、送信できませんでした。もう一度ログインしてください。」）
- **普通の API は、`purpose` 付きのトークンを必ず断る**（`JwtConfig` の `JwtPurpose.rejectAny()`）
  - これがないと、利用停止を解除した後に、申し立て用の鍵が**普通のログイン用のトークンとして使えてしまう**（実際に、外すと解除後の `/api/auth/me` が 200 になることをテストで確かめた）。この確かめは外さないこと
  - テスト（`ContactApiTest`）：申し立て用の鍵で普通の API を呼ぶと拒否される／利用停止を解除した後、その鍵は使えない
- 画面は、利用停止になったときに今までどおりトークンを捨てる。鍵は利用停止の情報と一緒に**メモリにだけ**持ち、localStorage には入れない。再読み込みで消えたら、もう一度ログインすれば新しい鍵を受け取れる
- 種類は「アカウントについて」を最初から選んでおく。申し立てかどうかは、種類を増やさずに受付の経路（`SUSPENDED_APPEAL`）で見分ける
- ほかに考えた案と、選ばなかった理由
  - お問い合わせの API だけ利用停止中も通し、トークンを捨てない：トークンは24時間で切れ、利用停止中はログインしても新しいトークンが出ないため、期限が切れた後・別の端末では二度と送れない（無期限の利用停止では事実上申し立てられない）
  - ログインなしで送れるようにする（案B）：本人確認ができず、いたずらを防ぐ仕組みが要る。パスワードの再設定（ログイン前）は先に作ったが、こちらは引き続き未確定（下記「未確定・要確認」）

#### いたずら・送りすぎを防ぐ方法

- 1人1日（24時間）5件まで。超えたら 429（「お問い合わせの上限に達しました。時間をおいて再度お試しください。」）。普通のお問い合わせと申し立てを合わせて、利用者ごとに数える
- **IP アドレスは残さない**（`admin.md`「管理操作のログ」と同じ方針）。この方針は「**DB とアプリのログに保存しない**」という意味とする
  - メモリの上で数分だけ数える回数制限（保存せず、時間がたてば消えるもの）は、保存にあたらないため使ってよい
  - 今回はログインした人・申し立て用の鍵を持つ人しか送れないため、回数制限は利用者ごとで足りる（IP アドレスは使っていない）
  - ログインなしで送れるようにする（案B）ときは、上の解釈のもとで、次を組み合わせる：人には見えない入力欄（おとり）、サーバーが署名した「フォームを開いた時刻」で早すぎる・古すぎる送信を断る、ログインなしの送信だけ全体の上限を別枠で設ける（ログイン中・申し立ての送信が巻き添えで止まらないように）、同じ内容の重複を断る、メモリの上で数分だけ数える IP ごとの回数制限。CAPTCHA は外部のサービスが必要なため、そのときに決める

#### 個人情報の扱い

- 内容には個人情報が書かれる前提で扱う
  - **内容とメールアドレスは、アプリのログ・管理操作のログ（`detail`）に書かない**。エラーの応答・例外の message にも入れない（テストで、送った内容とアドレスがログに出ないことを確かめている）
  - 管理画面の一覧にも出さない（開いた詳細でだけ出す。`admin.md`「7. お問い合わせ」）
  - 画面では文字として出す（HTML として扱わない）
- **保存期間は未確定。現在は自動では消えない**（消すジョブはない。下記「未確定・要確認」）

#### API

| API | 内容 |
| --- | --- |
| `POST /api/contacts` | ログイン中のお問い合わせ。本文 `{"email", "category", "body"}`（`email` は空でよい）。201 `{"status": "ACCEPTED"}`。利用停止中のトークンでは今までどおり 403 |
| `POST /api/contacts/appeal` | 利用停止中の申し立て。トークンは付けない。本文 `{"appealToken", "email", "category", "body"}`。201 `{"status": "ACCEPTED"}` |

- 入力の誤りは 400（項目名 `email`・`category`・`body`。申し立てでは `appealToken` も）
- どちらも API の棚卸し（`VisibilityInventoryTest`）に登録した（申し立ては、ログインしていなくても使える API として、利用停止の確かめから除く）
