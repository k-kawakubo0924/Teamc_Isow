## ログイン

### 仕様

- 基本情報入力
  - メールアドレス
  - パスワード
- 新規会員登録ボタン
- ログインボタン
  - 入力情報が不一致の場合、警告文を表示する
- 「パスワードをお忘れですか？」リンク（`design/Login.png`）
  - 再設定のメールを頼む画面（`/forgot-password`）へ移る（下記「パスワードの再設定（ログイン前）」）
- ログイン成功後はホーム画面へ遷移する（実装時に暫定で決定）

### 未確定・要確認

- ログイン状態の保持期間（何日でログアウトされるか）… 暫定でトークンの有効期限と同じ24時間（「認証方式」参照）
- ログインの失敗の回数に上限を設けるか（今は上限がない。パスワードの総当たりへの備え。ログイン中のパスワードの変更・メールアドレスの変更で「現在のパスワード」を確かめるところも同じ）
  - **優先度：高（次に手を入れるべき箇所）**
  - 理由：パスワードの再設定・変更、メールアドレスの変更ができるようになり、パスワードを知られると、アドレスを変えてアカウントを奪われるまでが一続きになった。そして今は、パスワードを当て続けることを何も止めていない
  - 直し方の案：アカウントごとに、一定回数の失敗で一定時間ログインを止める（止まっていることは、パスワードが正しいときと同じ応答で隠すか決める）。あわせて、メモリの上だけで数える IP アドレスごとの制限（パスワードの再設定と同じ \`InMemoryRateLimiter\`）。現在のパスワードを確かめる2か所にも同じ制限をかける

## 新規会員登録

### 仕様

- 基本情報入力
  - メールアドレス
  - 電話番号
  - パスワード
  - ユーザ名
- 記入項目確認ボタン
  - 入力情報がすでに登録されている場合、警告文を表示する
  - 入力形式が異なる場合、警告文を表示する
- 入力規則（実装時に暫定で決定。正式に決まり次第ここを更新する）
  - メールアドレス … 前後の空白を除き、小文字にそろえて保存・照合する（ログイン時も同じ）
  - ユーザ名 … 一意とする。先頭の `@` はDBに保存せず、表示時に付ける。半角英数字と `_` で1〜30文字
  - 電話番号 … 入力時のハイフンは許し、ハイフンなしで保存する。`0` 始まりの10〜11桁。重複は許す
  - パスワード … 8〜72文字で、英字と数字を含む（詳細設定のパスワード再設定画面の規則に合わせた）
- 画面の流れ（実装時に暫定で決定）
  - 「入力情報を確認」では画面側で形式のみチェックし、確認画面へ進む
  - 重複は確認画面の「新規登録」を押した時点で判明し、入力画面に戻して該当欄に警告文を表示する
  - 登録完了後はログイン画面へ遷移し、「登録が完了しました。ログインしてください。」と表示する（自動ログインはしない）

### 未確定・要確認

- 各項目の入力規則
  - いずれも仕様に暫定で記載した。正式な規則（特にユーザ名の文字種・長さ）の確認が必要
- 登録時にメールアドレスの確認メールを送るか（下記「登録の画面との食い違い」を直すには、これが必要）
- 登録直後のプロフィール（性別・身長など）の入力タイミング
  - プロフィール編集画面では「名前」のみ必須で、他は「未設定」から始まる

### 登録の画面との食い違い（今あるもの）

- **新規会員登録は、すでに使われているメールアドレスに「このメールアドレスは既に登録されています」と返している**
- 一方、パスワードの再設定（下記）とメールアドレスの変更（`settings.md`「メールアドレスの変更」）では、登録済みかどうかを外から分からないように、**登録の有無にかかわらず同じ応答**にしている
- そのため、**再設定・アドレスの変更で隠している「このアドレスが登録済みか」は、登録の画面からは分かる**。食い違いがあることを承知のうえで、今回は直していない
- 今回直さない理由：登録の画面でも隠すには、「登録を受け付けました。確認メールを送りました」と返し、メールのリンクを開いたときに登録を完了する（すでに登録済みなら、そのアドレスに「登録済みです」と知らせる）作りに変える必要がある。登録時の確認メールは範囲を超えるため、別の機会にする（上記「未確定・要確認」）

## パスワードの再設定（ログイン前）

ログイン画面の「パスワードをお忘れですか？」から、メールのリンクでパスワードを設定し直す。画面画像はない（ログイン画面の見た目に合わせた）。

### 流れ

1. 「パスワードをお忘れですか？」→ メールアドレスを入れる画面（`/forgot-password`）
2. 届いたメールのリンク → 新しいパスワードを入れる画面（`/reset-password#token=…`）。新しいパスワードと確認用を入れて押す
3. 再設定したら、この端末もログアウトしてログイン画面へ移り、「パスワードを再設定しました。新しいパスワードでログインしてください。」と出す

### 登録の有無を外から分からないようにする

- **登録されていても、いなくても、いつも同じ 202 と同じ文言**を返す：「入力したメールアドレスが登録されていれば、パスワード再設定のメールを送りました。届かない場合は、時間をおいてもう一度お試しください。」
- **応答の速さでも分からないようにする**：メールはコミットの後に別のスレッドで送り、応答を待たせない（下記「メールの送信」）
- 形式の誤り（空・アドレスでない）だけは 400（登録の有無とは関係ないため）
- 画面も、サーバーの文言をそのまま出す
- ただし、新規会員登録の画面からは分かる（上記「登録の画面との食い違い」）

### リンクの鍵

- `purpose=password_reset` の JWT（申し立て用の鍵と同じ作り。`AccountTokens`）。普通の API では使えない（`JwtConfig` が purpose 付きを断る）
- **有効期限は30分**
- **使い捨て**：発行した時点のトークンの世代（下記「トークンの世代」）を入れ、使うときに今の世代と比べる。再設定すると世代が進むので、同じ鍵は使えず、先に送った鍵もまとめて使えなくなる
- **鍵は URL の `#` の後ろ**に置く（`/reset-password#token=…`）。`#` の後ろはサーバーに送られないため、アクセスログ・リンク元の情報に鍵が残らない。画面は鍵を読んだら URL から消す
- 開いただけでは使わない（メールのリンクを自動で開く仕組みがあっても、勝手に使われないように）。入力して押したときだけ使う
- 鍵が使えないとき（期限切れ・使用済み・壊れている）は、理由を区別せずに 400：「このリンクは使えません。有効期限（30分）が切れたか、すでに使われています。もう一度、再設定のメールを送ってください。」

### 再設定したとき

- 新しいパスワードは登録と同じ規則（8〜72文字・英字と数字を含む。`PasswordRules`）
- **トークンの世代を進め、すべての端末をログアウトさせる**
- 登録アドレスに「パスワードが変更されました」と知らせる（心当たりがなければ、ログイン画面の「パスワードをお忘れですか？」から再設定するよう案内する。メールを受け取れる本人なら、これで取り戻せる）
- 利用停止中の人も再設定できる（ログインすると、今までどおり利用停止の画面と申し立てに進める）

### 送りすぎを防ぐ

- 同じアカウントには **5分に1通**まで（`users.password_reset_requested_at`）
- 同じ IP アドレスからは **10分に10回**まで。**メモリの上だけで数え、DB・アプリのログに保存しない**（「IP アドレスは残さない」の解釈。`settings.md`「いたずら・送りすぎを防ぐ方法」）
- どちらも、超えた分は**同じ応答を返して送らないだけ**（超えたことも外から分からないように）

### API

| API | 内容 |
| --- | --- |
| `POST /api/auth/password-reset/request` | 再設定のメールを頼む。本文 `{"email"}`。いつも 202 `{"message"}`（形式の誤りだけ 400） |
| `POST /api/auth/password-reset/confirm` | 新しいパスワードを設定する。本文 `{"token", "newPassword"}`。204。鍵が使えなければ 400 |

- どちらもトークンなしで呼べる（SecurityConfig で許可）。API の棚卸し（`VisibilityInventoryTest`）に、ログインしていなくても使える API として登録した

## メールの送信

パスワードの再設定・メールアドレスの変更（`settings.md`）・パスワードの変更の知らせで、メールを送る。

### 開発中の受け取り方（Mailpit）

- docker-compose に **Mailpit**（開発用のメール受信）を足した。`docker compose up -d` で PostgreSQL と一緒に立ち上がる
- アプリは開発中、`localhost:1025` に SMTP で送る。Mailpit は外へは送らずに受け取り、**`http://localhost:8025` で届いたメールを読める**（アカウントの作成・設定は不要。チーム全員が同じ手順で使える）
- ポートが重なる場合は `.env` の `MAIL_PORT`・`MAILPIT_UI_PORT` を変える。届いたメールはコンテナを止めると消える
- 外部の送信サービスのアカウントは作らない。リンクをアプリのログに出す案は、ログに鍵が残るため選ばなかった

### 本番への切り替え

- **環境変数の差し替えだけ**で、実際の SMTP サーバーに送るようになる：`MAIL_HOST`・`MAIL_PORT`・`MAIL_USERNAME`・`MAIL_PASSWORD`・`MAIL_SMTP_AUTH`・`MAIL_SMTP_STARTTLS`・`MAIL_FROM`（README「環境変数一覧」）
- **メールのリンクの土台の URL は `FRONTEND_ORIGIN` から作る。リクエストの Host ヘッダーからは作らない**（ヘッダーを偽装されると、攻撃者のサイトへのリンク入りのメールを送らされるため）

### 送り方（`MailDispatcher`）

- メールは必ず `MailDispatcher` を通して送る
- トランザクションの中で頼まれたら、**コミットした後に**送る（取り消された処理のメールは送らない）
- **別のスレッドで送る**（応答を待たせない。再設定で「登録されているときだけ送るぶん遅い」という差が出ないように）。テストでは同じスレッドで送る（`app.mail.async=false`）
- SMTP サーバーが応答しないときに止まったままにならないよう、接続・送信に待ち時間の上限を付けた
- **送れなくても、利用者への応答は変えない**（非同期のため、画面には「送りました」が見える）。画面には「届かない場合は、時間をおいてもう一度お試しください」と常に書いておく
- テストでは SMTP に送らず、送ったメールをメモリに貯める部品（`RecordingMailSender`）に差し替え、本文とリンクを確かめる

### メールの本文

- 書くもの：アプリ名・用件・リンク・有効期限・心当たりがない場合のこと・@ユーザー名（どのアカウントの件か分かるように）
- 書かないもの：電話番号・パスワード・ほかのメールアドレス
- 文字だけのメール（HTML にしない）。差出人は `MAIL_FROM`

### ログ

- **管理操作のログには残さない**（管理者の操作ではないため）
- アプリのログには「種類（`MailKind`）・ユーザー ID・成功か失敗か」だけを書く。**メールアドレス・鍵・リンク・本文は書かない**
  - 送信の例外の message・スタックトレースには宛先が入ることがあるため、例外は種類（クラス名）だけを書く
  - 未登録のアドレスへの再設定の申し込みは、何も記録しない
  - テストで、アドレスと鍵がログに出ないことを確かめている

## 認証方式（実装方針）

`CLAUDE.md` の技術スタックに基づき、Spring Security + JWT を想定。

### 仕様（実装時に暫定で決定。正式に決まり次第ここを更新する）

- JWT（HS256）。秘密鍵は環境変数 `JWT_SECRET`（32バイト以上、Base64）で管理する
- トークンの有効期限は24時間。リフレッシュは行わない（期限が切れたら再ログイン）
- トークンにはユーザーID（`sub`）のみを入れ、メールアドレスなどは入れない
- パスワードは BCrypt でハッシュ化して保存する
- ログイン失敗時は、メールアドレスが存在しない場合もパスワードが違う場合も同じ応答（401・同じ文言）を返す

- 画面側ではトークンを `localStorage` に保存する（再読み込み・ブラウザ再起動後も期限まではログイン状態を保つ。タブ間で共有する）
  - XSS でトークンを読み取られうるため、`dangerouslySetInnerHTML` は使わない（`CLAUDE.md` のルール）
- 未ログインでログインが必要な画面を開いたらログイン画面へ、ログイン済みでログイン・新規会員登録画面を開いたらホーム画面へリダイレクトする
- 有効期限切れ、またはAPIが401を返した場合は自動でログアウトする
- API の失敗の文言は種類ごとに分けている（`frontend/src/api/client.ts`）。以前は 404・500 をすべて同じ文言（「エラーが発生しました。時間をおいて再度お試しください。」）にしていたため、API が存在しないことに気づくのが遅れた。1つの文言に戻さないこと
- ログアウトは画面側でトークンを破棄するだけで、サーバーには通知しない

### トークンの世代（全端末のログアウト）

- `users.token_version`（整数）を「トークンの世代」とし、ログイン用のトークンにも入れる（`ver`）
- リクエストのたびに DB の値と比べ、違えば **401**（期限切れと同じ扱い。画面は自動でログアウトする）。確かめは、すでに毎回ユーザーを読んでいる `SuspendedUserFilter` で行い、利用停止より先に確かめる
- 世代を進めるのは、パスワードの再設定・ログイン中のパスワードの変更・メールアドレスの変更の完了のとき。それまでに発行したログイン用のトークンと、メールのリンクの鍵がすべて使えなくなる
  - ログイン中のパスワードの変更では、操作した端末だけは続けて使えるよう、新しいトークンを返す
- 時刻ではなく番号で比べるため、日本時間と UTC の9時間のずれの問題は起きない
- この仕組みの前に発行したトークン（世代が入っていない）は世代0として扱う（入れた時点でログアウトさせない）

### 未確定・要確認

- リフレッシュトークンを導入するか（24時間ごとに再ログインが必要になるため）
- 本番公開前に、トークンの保存場所を HttpOnly Cookie に変えるか（XSS 対策を強める場合。バックエンドの Cookie 発行・CSRF 対策・CORS 設定の変更が必要）
- ログアウト時にトークンをサーバー側でも無効にするか（現状は、ログアウト後も期限までは技術的に有効）
