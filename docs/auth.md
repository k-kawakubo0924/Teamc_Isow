## ログイン

### 仕様

- 基本情報入力
  - メールアドレス
  - パスワード
- 新規会員登録ボタン
- ログインボタン
  - 入力情報が不一致の場合、警告文を表示する
- 「パスワードをお忘れですか？」リンク（`design/Login.png`）
  - 現時点では未実装。押すと「この機能は準備中です」と表示するだけ
- ログイン成功後はホーム画面へ遷移する（実装時に暫定で決定）

### 未確定・要確認

- ログイン状態の保持期間（何日でログアウトされるか）… 暫定でトークンの有効期限と同じ24時間（「認証方式」参照）

- メール送信をどう実現するか（パスワードリセットのほか、メールアドレス再設定の確認メールにも関わる）

## 新規会員登録

### 仕様

- 基本情報入力
  - メールアドレス
  - 電話番号
  - パスワード
  - ユーザ名
- 記入項目確認ボタン
  - 入力情報がすでに登録されている場合、警告文を表示する
  - 入力形式が異なる場合、警告文を表示する
- 入力規則（実装時に暫定で決定。正式に決まり次第ここを更新する）
  - メールアドレス … 前後の空白を除き、小文字にそろえて保存・照合する（ログイン時も同じ）
  - ユーザ名 … 一意とする。先頭の `@` はDBに保存せず、表示時に付ける。半角英数字と `_` で1〜30文字
  - 電話番号 … 入力時のハイフンは許し、ハイフンなしで保存する。`0` 始まりの10〜11桁。重複は許す
  - パスワード … 8〜72文字で、英字と数字を含む（詳細設定のパスワード再設定画面の規則に合わせた）
- 画面の流れ（実装時に暫定で決定）
  - 「入力情報を確認」では画面側で形式のみチェックし、確認画面へ進む
  - 重複は確認画面の「新規登録」を押した時点で判明し、入力画面に戻して該当欄に警告文を表示する
  - 登録完了後はログイン画面へ遷移し、「登録が完了しました。ログインしてください。」と表示する（自動ログインはしない）

### 未確定・要確認

- 各項目の入力規則
  - いずれも仕様に暫定で記載した。正式な規則（特にユーザ名の文字種・長さ）の確認が必要
- メールアドレスの確認メール送信の有無（メールアドレス再設定画面には「入力したアドレスに確認メールを送ります」という記載がある）
- 登録直後のプロフィール（性別・身長など）の入力タイミング
  - プロフィール編集画面では「名前」のみ必須で、他は「未設定」から始まる

## 認証方式（実装方針）

`CLAUDE.md` の技術スタックに基づき、Spring Security + JWT を想定。

### 仕様（実装時に暫定で決定。正式に決まり次第ここを更新する）

- JWT（HS256）。秘密鍵は環境変数 `JWT_SECRET`（32バイト以上、Base64）で管理する
- トークンの有効期限は24時間。リフレッシュは行わない（期限が切れたら再ログイン）
- トークンにはユーザーID（`sub`）のみを入れ、メールアドレスなどは入れない
- パスワードは BCrypt でハッシュ化して保存する
- ログイン失敗時は、メールアドレスが存在しない場合もパスワードが違う場合も同じ応答（401・同じ文言）を返す

- 画面側ではトークンを `localStorage` に保存する（再読み込み・ブラウザ再起動後も期限まではログイン状態を保つ。タブ間で共有する）
  - XSS でトークンを読み取られうるため、`dangerouslySetInnerHTML` は使わない（`CLAUDE.md` のルール）
- 未ログインでログインが必要な画面を開いたらログイン画面へ、ログイン済みでログイン・新規会員登録画面を開いたらホーム画面へリダイレクトする
- 有効期限切れ、またはAPIが401を返した場合は自動でログアウトする
- ログアウトは画面側でトークンを破棄するだけで、サーバーには通知しない

### 未確定・要確認

- リフレッシュトークンを導入するか（24時間ごとに再ログインが必要になるため）
- 本番公開前に、トークンの保存場所を HttpOnly Cookie に変えるか（XSS 対策を強める場合。バックエンドの Cookie 発行・CSRF 対策・CORS 設定の変更が必要）
- ログアウト時にトークンをサーバー側でも無効にするか（現状は、ログアウト後も期限までは技術的に有効）
