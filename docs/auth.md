## ログイン

### 仕様

- 基本情報入力
  - メールアドレス
  - パスワード
- 新規会員登録ボタン
- ログインボタン
  - 入力情報が不一致の場合、警告文を表示する
  - ログインの失敗が続いたら、一時的に受け付けを止める（429。下記「ログインの失敗の回数の上限」）
- 「パスワードをお忘れですか？」リンク（`design/Login.png`）
  - 再設定のメールを頼む画面（`/forgot-password`）へ移る（下記「パスワードの再設定（ログイン前）」）
- ログイン成功後はホーム画面へ遷移する（実装時に暫定で決定）

### 未確定・要確認

- ログイン状態の保持期間（何日でログアウトされるか）… 暫定でトークンの有効期限と同じ24時間（「認証方式」参照）
- 全 IP アドレスを合わせた、メールアドレスごとの失敗の上限（下記「ログインの失敗の回数の上限」の④）を入れるか（**今は入れていない**）
  - 入れれば、IP アドレスを大量に使う攻撃（①を IP アドレスの数だけ試せる）に強くなる。ただし、他人がわざと失敗し続けることで本人も止まるようになる（締め出しに使われる）
  - 入れる場合の案：上限を高め（例：1時間に50回）にし、パスワードの再設定をしたら解除する（再設定はメールを受け取れる本人であることの証明になる）

### ログインの失敗の回数の上限

パスワードの再設定・変更、メールアドレスの変更ができるようになり、パスワードを知られると、アドレスを変えてアカウントを奪われるまでが一続きになったため、総当たりを止める。

| 単位 | 数えるもの | 上限 | 成功したとき |
| --- | --- | --- | --- |
| ① メールアドレス × IP アドレス | ログインの失敗 | 15分に5回 | 消す |
| ② IP アドレス（アドレスを問わず） | ログインの失敗 | 15分に30回 | **消さない**（成功した1回を数えないだけ） |
| ③ ユーザー | 現在のパスワードの確認の失敗（メールアドレスの変更・ログイン中のパスワードの変更で**合わせて**数える） | 15分に5回 | 消す |

- **締め出しにしない**：アカウントそのものは止めない。①で止まるのは失敗した IP アドレスからだけなので、他人のアドレスで失敗し続けても、本人は別の IP アドレスからログインできる
- **止まっている間は、パスワードを照合せずに 429** を返す（正しいパスワードでも通さない。通すと、正しいかどうかが分かってしまう）
  - 文言：「ログインの失敗が続いたため、一時的に受け付けを止めています。あと約N分で、もう一度お試しください。パスワードを忘れた場合は『パスワードをお忘れですか？』から再設定できます。」と `Retry-After`（秒）。①②どちらで止まっても同じ文言。メールアドレスの変更の「あと約N分」と同じ作り（`RetryLaterException`）
  - ③の文言：「現在のパスワードの誤りが続いたため、一時的に受け付けを止めています。あと約N分で、もう一度お試しください。」（`settings.md`）
- **文言は、ふだんエラーが出ている場所と同じところに出し、そこへ画面を動かす**（利用者の目に入るように）
  - ログイン画面：認証の失敗と同じ、上の警告文（`ErrorBanner`）。止まっただけで入力が違うとは限らないので、欄は赤くしない
  - メールアドレスの変更・パスワードの変更：フォームの上のエラー（欄の下には出さない）
  - 画面を動かす理由：設定の2画面は「完了」が上に貼り付いたヘッダーにあり、下の欄まで動かしたまま押せる。ログイン画面も、スマホでキーボードが出ていると上の警告文が隠れる。動かさないと、文言が画面の外に出たままになる
  - 画面のテスト（`RetryLaterMessage.test.tsx`）は jsdom で配置を計算しないため、「ふだんのエラーと同じ要素・同じ位置（入力欄より前）に出る」と「その要素へ画面を動かした」で確かめている。実際に目に入るかはブラウザで確かめる
- **登録の有無を漏らさない**：登録のないアドレスも、登録があるアドレスと同じように数えて止め、同じ応答を返す。文言に「このアカウントは」と書かない
- **照合の前に1回分を先に数え、成功したら戻す**（`FailureLimiter`）。照合の後に数える作りでは、照合（bcrypt）の間に同時に送れば上限を超えて照合させられるため
- **成功したときの扱いが①と②で違う。そろえないこと**（`LoginFailureLimits` のコメントと `LoginLimitApiTest` でも固定している）
  - ①は成功したら消す。本人が打ち間違えた後に入れたなら、その組み合わせで数え続ける理由がない
  - ②は成功しても消さない。消すと、アカウントを1つ持っている攻撃者が、自分のアカウントにログインするだけで IP アドレスの残り回数を戻せる（29回失敗 → 自分にログイン → また29回失敗 … が続けられる）。成功した1回を数えないのは、同じ IP アドレスを使う人たち（学校・会社など）が普通にログインするだけで止まらないようにするため
  - ③は成功したら消す。数えるのはログイン中の本人のユーザーごとで、ほかの人の成功で戻されることがないため
- **パスワードの再設定を完了したら、そのアドレスの①を（すべての IP アドレスの分）消す**。②は消さない
  - 理由：パスワードを忘れた人が、できたての新しいパスワードで15分締め出されるのは、守りではなく不便なだけ。再設定を完了できるのはメールボックスを持つ本人なので、①を消しても攻撃者に何も渡さない
  - ②を消さない理由は、ログインの成功で②を消さないのと同じ（メールボックスを1つ持っている攻撃者が、再設定をするだけで IP アドレスの残り回数を戻せてしまう）
  - 消すのは再設定が**完了した**ときだけ。メールを送った時点では消さない（`LoginLimitApiTest` で3つとも固定している）
  - **②で止まったときは、再設定しても入れない**（止まったときの文言は「再設定できます」と案内するが、②で止まった場合は再設定してもその IP アドレスからは15分入れない。②は1つの IP アドレスから別々のアドレスで30回失敗したときなので、普通の利用者がかかることはまれと考え、文言は変えていない）
- **③の上限に達しても、ログアウトはさせない**（待たせるだけ）。ログアウトさせれば置きっぱなしの端末での総当たりをより強く止められるが、自分で5回打ち間違えただけで全端末から追い出されるのは割に合わない
- **止まったことをメールでは知らせない**。知らせる作りにすると、攻撃者がわざと失敗し続けることで、本人の受信箱をメールで埋められる
- **メモリの上だけで数える**（DB・アプリのログに保存しない。パスワードの再設定の IP アドレスごとの制限と同じ）
  - DB にしなかった理由：users の行で数えると、登録のないアドレスを数えられず、止まるかどうかで登録の有無が分かる。また、失敗は例外で返すため、同じトランザクションで書いた記録はロールバックで消える
  - 日時を DB に持たないので、日本時間と UTC の9時間のずれの問題は起きない（メモリの上では時差のない時刻 `clock.millis()` で比べる）
  - サーバーを再起動すると回数は消える（攻撃者は再起動を起こせないため、得られるのは再起動1回ごとに数回分だけ）。サーバーを複数台にすると、回数が台ごとに分かれる（今は1台）
  - 覚えておくキーの数に上限（既定 1万。`app.auth.login.max-tracked-keys`）がある。攻撃者は好きなだけアドレスを作れるため。上限に達したときの捨て方は「メモリの上で数える部品が2つある」と同じ
- 回数は設定で変えられる：`app.auth.login.max-failures-per-account-and-ip`（既定 5）・`app.auth.login.max-failures-per-ip`（既定 30）
- **IP アドレスの取り方とプロキシ**（パスワードの再設定の IP アドレスごとの制限も同じ）
  - 今は接続元の IP アドレス（`getRemoteAddr()`）を使う。本番でリバースプロキシの後ろに置くと、全員がプロキシの IP アドレスに見え、②がサイト全体で1つになる（全員がログインできなくなる）
  - そのため、**本番に出すときに** `server.forward-headers-strategy` を設定し、プロキシが付ける `X-Forwarded-For` から IP アドレスを取る
  - **開発では設定しない**
  - **信用できるプロキシの後ろにいることが前提**。`X-Forwarded-For` は誰でも偽装できるため、プロキシがいない状態で有効にすると、ヘッダーを書き換えるだけで IP アドレスの制限をすり抜けられる（設定するのは、外からの通信が必ずそのプロキシを通り、プロキシが `X-Forwarded-For` を付け直す構成のときだけ）

### 直した課題：ログのテストが、ほかのテストの失敗に巻き込まれて落ちる（2026-10-19 修正済み）

ログインの失敗の回数の上限の作業中に見つかった。ブラウザでの確認の途中に見つかったため、確認が終わってから直した（直すとビルドで `target/classes` が書き換わり、動いているバックエンドと中身が食い違うため）。

- **何が起きていたか**
  - `LoginLimitApiTest`「アプリのログに_メールアドレスとIPアドレスを書かない」が、同じクラスのほかのテストが失敗したときに、一緒に落ちていた
  - アプリのログにアドレスが出たわけではない。MockMvc は、失敗したテストのリクエストを（本文も含めて）標準出力に書く（「Body = {"email":"login-limit-user@example.com", …}」）。このテストは `CapturedOutput` の `getAll()` で出力をまるごと見ており、先に走って失敗したテストの MockMvc の出力まで含めて「アドレスがない」ことを確かめていたため、それを漏れと見なして落ちていた
- **直した理由**
  - このテストが他人の失敗で何度も赤くなると、本当に漏れたときも「またあれか」で流されるようになる。狼少年になったテストは、ないのと同じになる
- **直し方**
  - アプリのログだけを見るようにして、MockMvc の出力を対象から外した。テスト用の共通の部品 `AppLog`（`backend/src/test/.../common/AppLog.java`）が、テストごとに、このアプリのロガー（`com.teamc.isow` とその下）が書いたログだけを集める。使うときは、クラスに `@ExtendWith(AppLogExtension.class)` を付け、テストの引数に `AppLog appLog` を取って `appLog.text()` を見る
    - ロガーから直接集めるので、MockMvc の出力（ロガーを通らず標準出力に書く）は入らない
    - 例外のスタックトレースの中身も入る（例外の message にアドレスなどを入れていないかも確かめられる）
    - ほかのライブラリ（Spring・Hibernate など）のロガーが書いたログは入らない。見張るのはこのアプリのログだけ
  - MockMvc の出力を止める（`spring.test.mockmvc.print`）案は選ばなかった。失敗したときの手がかりがなくなるため
  - 同じ確かめ方をしていた `PasswordResetApiTest`・`EmailChangeApiTest`・`PasswordChangeApiTest`・`ContactApiTest`・`AdminContactApiTest` も、同じ部品に置き換えた（どれも「`CapturedOutput output` を `AppLog appLog` に、`output.getAll()` を `appLog.text()` に」の機械的な置き換えで済んだ）
  - `MailDispatcherTest`・`EvidencePurgerTest` は `getAll()` のまま。MockMvc を使わない部品のテストで、巻き込まれる元（失敗したリクエストの出力）がないため
- **確かめたこと**（`LoginLimitApiTest` で）
  - ほかのテストをわざと失敗させても、このテストは落ちない：先に走る「四回までは止まらず_正しいパスワードでログインできる」の期待を誤りにした。MockMvc の出力に `"email":"login-limit-user@example.com"` が出たうえで、落ちたのはわざと壊したテストだけだった
  - アプリのログにアドレスをわざと書くと、このテストは落ちる：`AuthService.login` にアドレスと IP アドレスを書く1行を足すと、このテストだけが落ちた（見張りとして働いている）
  - アプリのコードのロガーは、どれもクラス名（`com.teamc.isow` の下）で作られており、標準出力に直接書くところもない（あれば見張りの外になる）。新しくログを書くときも、`LoggerFactory.getLogger(〇〇.class)` で作る

## 新規会員登録

### 仕様

- 基本情報入力
  - メールアドレス
  - 電話番号
  - パスワード
  - ユーザ名
- 記入項目確認ボタン
  - 入力情報がすでに登録されている場合、警告文を表示する
  - 入力形式が異なる場合、警告文を表示する
- 入力規則（実装時に暫定で決定。正式に決まり次第ここを更新する）
  - メールアドレス … 前後の空白を除き、小文字にそろえて保存・照合する（ログイン時も同じ）
  - ユーザ名 … 一意とする。先頭の `@` はDBに保存せず、表示時に付ける。半角英数字と `_` で1〜30文字
  - 電話番号 … 入力時のハイフンは許し、ハイフンなしで保存する。`0` 始まりの10〜11桁。重複は許す
  - パスワード … 8〜72文字で、英字と数字を含む（詳細設定のパスワード再設定画面の規則に合わせた）
- 画面の流れ（実装時に暫定で決定）
  - 「入力情報を確認」では画面側で形式のみチェックし、確認画面へ進む
  - 重複は確認画面の「新規登録」を押した時点で判明し、入力画面に戻して該当欄に警告文を表示する
  - 登録完了後はログイン画面へ遷移し、「登録が完了しました。ログインしてください。」と表示する（自動ログインはしない）

### 未確定・要確認

- 各項目の入力規則
  - いずれも仕様に暫定で記載した。正式な規則（特にユーザ名の文字種・長さ）の確認が必要
- 登録時にメールアドレスの確認メールを送るか（下記「登録の画面との食い違い」を直すには、これが必要）
- 登録直後のプロフィール（性別・身長など）の入力タイミング
  - プロフィール編集画面では「名前」のみ必須で、他は「未設定」から始まる

### 登録の画面との食い違い（今あるもの）

- **新規会員登録は、すでに使われているメールアドレスに「このメールアドレスは既に登録されています」と返している**
- 一方、パスワードの再設定（下記）とメールアドレスの変更（`settings.md`「メールアドレスの変更」）では、登録済みかどうかを外から分からないように、**登録の有無にかかわらず同じ応答**にしている
- そのため、**再設定・アドレスの変更で隠している「このアドレスが登録済みか」は、登録の画面からは分かる**。食い違いがあることを承知のうえで、今回は直していない
- 今回直さない理由：登録の画面でも隠すには、「登録を受け付けました。確認メールを送りました」と返し、メールのリンクを開いたときに登録を完了する（すでに登録済みなら、そのアドレスに「登録済みです」と知らせる）作りに変える必要がある。登録時の確認メールは範囲を超えるため、別の機会にする（上記「未確定・要確認」）

## パスワードの再設定（ログイン前）

ログイン画面の「パスワードをお忘れですか？」から、メールのリンクでパスワードを設定し直す。画面画像はない（ログイン画面の見た目に合わせた）。

### 流れ

1. 「パスワードをお忘れですか？」→ メールアドレスを入れる画面（`/forgot-password`）
2. 届いたメールのリンク → 新しいパスワードを入れる画面（`/reset-password#token=…`）。新しいパスワードと確認用を入れて押す
3. 再設定したら、この端末もログアウトしてログイン画面へ移り、「パスワードを再設定しました。新しいパスワードでログインしてください。」と出す

### 登録の有無を外から分からないようにする

- **登録されていても、いなくても、いつも同じ 202 と同じ文言**を返す：「入力したメールアドレスが登録されていれば、パスワード再設定のメールを送りました。届かない場合は、時間をおいてもう一度お試しください。」
- **応答の速さでも分からないようにする**：メールはコミットの後に別のスレッドで送り、応答を待たせない（下記「メールの送信」）
- 形式の誤り（空・アドレスでない）だけは 400（登録の有無とは関係ないため）
- 画面も、サーバーの文言をそのまま出す
- ただし、新規会員登録の画面からは分かる（上記「登録の画面との食い違い」）

### リンクの鍵

- `purpose=password_reset` の JWT（申し立て用の鍵と同じ作り。`AccountTokens`）。普通の API では使えない（`JwtConfig` が purpose 付きを断る）
- **有効期限は30分**
- **使い捨て**：発行した時点のトークンの世代（下記「トークンの世代」）を入れ、使うときに今の世代と比べる。再設定すると世代が進むので、同じ鍵は使えず、先に送った鍵もまとめて使えなくなる
- **鍵は URL の `#` の後ろ**に置く（`/reset-password#token=…`）。`#` の後ろはサーバーに送られないため、アクセスログ・リンク元の情報に鍵が残らない。画面は鍵を読んだら URL から消す
- 開いただけでは使わない（メールのリンクを自動で開く仕組みがあっても、勝手に使われないように）。入力して押したときだけ使う
- 鍵が使えないとき（期限切れ・使用済み・壊れている）は、理由を区別せずに 400：「このリンクは使えません。有効期限（30分）が切れたか、すでに使われています。もう一度、再設定のメールを送ってください。」

### 再設定したとき

- 新しいパスワードは登録と同じ規則（8〜72文字・英字と数字を含む。`PasswordRules`）
- **トークンの世代を進め、すべての端末をログアウトさせる**
- 登録アドレスに「パスワードが変更されました」と知らせる（心当たりがなければ、ログイン画面の「パスワードをお忘れですか？」から再設定するよう案内する。メールを受け取れる本人なら、これで取り戻せる）
- 利用停止中の人も再設定できる（ログインすると、今までどおり利用停止の画面と申し立てに進める）
- ログインの失敗の回数のうち、そのアドレスの分（①）を消す。IP アドレスごとの分（②）は消さない（「ログインの失敗の回数の上限」）

### 送りすぎを防ぐ

- 同じアカウントには **5分に1通**まで（`users.password_reset_requested_at`）
- 同じ IP アドレスからは **10分に10回**まで。**メモリの上だけで数え、DB・アプリのログに保存しない**（「IP アドレスは残さない」の解釈。`settings.md`「いたずら・送りすぎを防ぐ方法」）
- どちらも、超えた分は**同じ応答を返して送らないだけ**（超えたことも外から分からないように）
- IP アドレスごとの記録は、**覚えておく IP アドレスの数に上限**（既定 1万。`app.auth.password-reset.max-tracked-ips`）がある
  - 「IP アドレスなので増えにくい」とは言えないため。IPv6 なら攻撃者が使えるアドレスは大量にあり、将来プロキシの後ろに置けば、ヘッダー由来の値がキーになる
  - 定期的な掃除ではなく上限にしたのは、掃除より速く作られたら追いつかないため
  - 上限に達したら、新しい IP アドレスを数えずに通すのではなく、古い記録を1つ捨てて数える。捨てる順は、期限の過ぎた記録しかないもの → 止まっていないもののうち最後の記録が最も古いもの → （すべて止まっているときだけ）止まり終わりが最も近いもの。止まっている IP アドレスを、ほかの IP アドレスを大量に作るだけで追い出せないようにするため（`InMemoryRateLimiterTest` で固定）

### メモリの上で数える部品が2つある

- `InMemoryRateLimiter`（パスワードの再設定の IP アドレスごとの制限）と `FailureLimiter`（ログインの失敗の回数の上限）は、どちらも「メモリの上だけで数え、キーの数に上限があり、同じ順で捨てる」部品で、似ている
- **まとめていない**。数えるものと、必要な機能が違うため
  - `InMemoryRateLimiter` は「頼まれた回数」を数え、通すか断るかだけを返す
  - `FailureLimiter` は「失敗の回数」を数える。照合の前に1回分を先に数え（同時に送られても上限を超えて照合させないため）、成功したら戻す（`release`・`reset`）。止まっているときは、もう一度試せるまでの残り時間を返す（「あと約N分」に使う）
- まとめるのは別の作業とする。まとめるまでは、**捨てる順や上限の考え方を変えるときは、2つともそろえて直す**こと（テストも `InMemoryRateLimiterTest`・`FailureLimiterTest` の両方にある）

### API

| API | 内容 |
| --- | --- |
| `POST /api/auth/password-reset/request` | 再設定のメールを頼む。本文 `{"email"}`。いつも 202 `{"message"}`（形式の誤りだけ 400） |
| `POST /api/auth/password-reset/confirm` | 新しいパスワードを設定する。本文 `{"token", "newPassword"}`。204。鍵が使えなければ 400 |

- どちらもトークンなしで呼べる（SecurityConfig で許可）。API の棚卸し（`VisibilityInventoryTest`）に、ログインしていなくても使える API として登録した

## メールの送信

パスワードの再設定・メールアドレスの変更（`settings.md`）・パスワードの変更の知らせで、メールを送る。

### 開発中の受け取り方（Mailpit）

- docker-compose に **Mailpit**（開発用のメール受信）を足した。`docker compose up -d` で PostgreSQL と一緒に立ち上がる
- アプリは開発中、`localhost:1025` に SMTP で送る。Mailpit は外へは送らずに受け取り、**`http://localhost:8025` で届いたメールを読める**（アカウントの作成・設定は不要。チーム全員が同じ手順で使える）
- ポートが重なる場合は `.env` の `MAIL_PORT`・`MAILPIT_UI_PORT` を変える。届いたメールはコンテナを止めると消える
- 外部の送信サービスのアカウントは作らない。リンクをアプリのログに出す案は、ログに鍵が残るため選ばなかった

### 本番への切り替え

- **環境変数の差し替えだけ**で、実際の SMTP サーバーに送るようになる：`MAIL_HOST`・`MAIL_PORT`・`MAIL_USERNAME`・`MAIL_PASSWORD`・`MAIL_SMTP_AUTH`・`MAIL_SMTP_STARTTLS`・`MAIL_FROM`（README「環境変数一覧」）
- **メールのリンクの土台の URL は `FRONTEND_ORIGIN` から作る。リクエストの Host ヘッダーからは作らない**（ヘッダーを偽装されると、攻撃者のサイトへのリンク入りのメールを送らされるため）

### 送り方（`MailDispatcher`）

- メールは必ず `MailDispatcher` を通して送る
- トランザクションの中で頼まれたら、**コミットした後に**送る（取り消された処理のメールは送らない）
- **別のスレッドで送る**（応答を待たせない。再設定で「登録されているときだけ送るぶん遅い」という差が出ないように）。テストでは同じスレッドで送る（`app.mail.async=false`）
- SMTP サーバーが応答しないときに止まったままにならないよう、接続・送信に待ち時間の上限を付けた
- **送れなくても、利用者への応答は変えない**（非同期のため、画面には「送りました」が見える）。画面には「届かない場合は、時間をおいてもう一度お試しください」と常に書いておく
- テストでは SMTP に送らず、送ったメールをメモリに貯める部品（`RecordingMailSender`）に差し替え、本文とリンクを確かめる

### メールの本文

- 書くもの：アプリ名・用件・リンク・有効期限・心当たりがない場合のこと・@ユーザー名（どのアカウントの件か分かるように）
- 書かないもの：電話番号・パスワード・ほかのメールアドレス
- 文字だけのメール（HTML にしない）。差出人は `MAIL_FROM`

### ログ

- **管理操作のログには残さない**（管理者の操作ではないため）
- アプリのログには「種類（`MailKind`）・ユーザー ID・成功か失敗か」だけを書く。**メールアドレス・鍵・リンク・本文は書かない**
  - 送信の例外の message・スタックトレースには宛先が入ることがあるため、例外は種類（クラス名）だけを書く
  - 未登録のアドレスへの再設定の申し込みは、何も記録しない
  - テストで、アドレスと鍵がログに出ないことを確かめている

## 認証方式（実装方針）

`CLAUDE.md` の技術スタックに基づき、Spring Security + JWT を想定。

### 仕様（実装時に暫定で決定。正式に決まり次第ここを更新する）

- JWT（HS256）。秘密鍵は環境変数 `JWT_SECRET`（32バイト以上、Base64）で管理する
- トークンの有効期限は24時間。リフレッシュは行わない（期限が切れたら再ログイン）
- トークンにはユーザーID（`sub`）のみを入れ、メールアドレスなどは入れない
- パスワードは BCrypt でハッシュ化して保存する
- ログイン失敗時は、メールアドレスが存在しない場合もパスワードが違う場合も同じ応答（401・同じ文言）を返す

- 画面側ではトークンを `localStorage` に保存する（再読み込み・ブラウザ再起動後も期限まではログイン状態を保つ。タブ間で共有する）
  - XSS でトークンを読み取られうるため、`dangerouslySetInnerHTML` は使わない（`CLAUDE.md` のルール）
- 未ログインでログインが必要な画面を開いたらログイン画面へ、ログイン済みでログイン・新規会員登録画面を開いたらホーム画面へリダイレクトする
- 有効期限切れ、またはAPIが401を返した場合は自動でログアウトする
- API の失敗の文言は種類ごとに分けている（`frontend/src/api/client.ts`）。以前は 404・500 をすべて同じ文言（「エラーが発生しました。時間をおいて再度お試しください。」）にしていたため、API が存在しないことに気づくのが遅れた。1つの文言に戻さないこと
- ログアウトは画面側でトークンを破棄するだけで、サーバーには通知しない

### トークンの世代（全端末のログアウト）

- `users.token_version`（整数）を「トークンの世代」とし、ログイン用のトークンにも入れる（`ver`）
- リクエストのたびに DB の値と比べ、違えば **401**（期限切れと同じ扱い。画面は自動でログアウトする）。確かめは、すでに毎回ユーザーを読んでいる `SuspendedUserFilter` で行い、利用停止より先に確かめる
- 世代を進めるのは、パスワードの再設定・ログイン中のパスワードの変更・メールアドレスの変更の完了のとき。それまでに発行したログイン用のトークンと、メールのリンクの鍵がすべて使えなくなる
  - ログイン中のパスワードの変更では、操作した端末だけは続けて使えるよう、新しいトークンを返す
- 時刻ではなく番号で比べるため、日本時間と UTC の9時間のずれの問題は起きない
- この仕組みの前に発行したトークン（世代が入っていない）は世代0として扱う（入れた時点でログアウトさせない）

### 未確定・要確認

- リフレッシュトークンを導入するか（24時間ごとに再ログインが必要になるため）
- 本番公開前に、トークンの保存場所を HttpOnly Cookie に変えるか（XSS 対策を強める場合。バックエンドの Cookie 発行・CSRF 対策・CORS 設定の変更が必要）
- ログアウト時にトークンをサーバー側でも無効にするか（現状は、ログアウト後も期限までは技術的に有効）
