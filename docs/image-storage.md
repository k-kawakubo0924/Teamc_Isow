# 画像の保存先（Cloudflare R2 への移行）

> **ステップ1まで実施し、ステップ2以降は未実施（2026-10-29 に止めた）。理由：デプロイが不要になったため。**
> 公開することになったら、下記「ステップ」の2から再開する。調べた内容・決めたことは、そのときのために残す。
> 今の画像の守りは、以前と同じく「配るところで止める」（`PublicImageAccess`）のまま。下記「署名付き URL の弱点」は、ステップ2を入れるまでは生じていない（非表示にした瞬間に 404 になる）

公開のサーバー（Render の無料枠）は、再デプロイでディスクが消える。そのため、画像（投稿の写真・プロフィール画像・DM の画像）と通報の証拠を、Cloudflare R2 に移す。
公開のときにやることは `deploy.md` にまとめる。ここには、設計・決めたこと・その理由・作業の進み具合を書く。

## 一番の問題：「配るところで止める」守りが効かなくなる

今は、画像を `/uploads/**` で配るときに、配ってよいかを DB で確かめている（`PublicImageAccess`。`admin.md`「非公開にした投稿の写真」）。これで、次を 404 にしている。

- 非公開にした投稿の写真
- 利用停止中のユーザーの投稿の写真
- どこからも参照されていないファイル

画像を R2 から直接配ると、画像がアプリを通らなくなり、この確かめが働かない。また、DM の画像も今は公開の画像と同じ置き場にあり、`/uploads/**` から取れないのは許可リストに入れていないことだけによる（`dm.md`「画像」）。公開のバケットに一緒に置くと、DM の画像も URL を知っていれば誰でも見られる。

## 方式（2026-10-28 決定）

| 画像 | 方式 |
| --- | --- |
| 投稿の写真・プロフィール画像 | **全部を非公開のバケットに置き、短い期限（10分）の署名付き URL を出す**。応答を作るときに、見えてよい画像にだけ URL を出す |
| DM の画像・通報の証拠 | 今と同じく、認証付きの API がアプリを通して中身を返す（中継） |
| バケット | 画像用と証拠用の2つ。**どちらも非公開** |

### 考えた案と、採らなかった理由

- **全部を非公開のバケットに置き、アプリが中継する**：今の判定がそのまま使え、見えてはいけないものは一切漏れない。ただし、画像の通信がすべて Render を通り、`no-store` のため Cloudflare でキャッシュもできない。一覧が元の写真を読む作り（縮小画像を作る前）では、タイムラインを開くたびに数十MB が Render を通る。DM と証拠だけに使う
- **公開と非公開でバケットを分け、非表示にしたらファイルを移す**：移す処理の失敗・遅れの間は公開のまま。利用停止は期限が来ると自動で解けるため、戻すための定期実行が要る。いちばん大きな穴は「どこからも参照されていないファイル」で、削除に失敗したファイルが、ずっと公開のまま残る（今は 404 で守っている）。作る量もいちばん多い
- **Cloudflare Workers でバケットの前で判定する**：見え方の判定を JavaScript でもう一度書くことになり、Java と2か所で揃え続ける必要がある

### 署名付き URL の弱点（承知で採用した）

- **今は非表示にした瞬間に 404 になるが、これからは、すでに発行済みの URL を控えた人は期限（10分）まで開ける。守りが弱くなる点を承知で採用した**（通信を Render に通さないため）。黙って弱くしない
  - 非表示・利用停止にした後は、新しい URL を出さない。弱くなるのは「すでに出した URL」が期限まで有効なことだけ
  - どこからも参照されていないファイルには、URL を出さない（今と同じく見えない）
- URL を出し忘れた場所は「画像が壊れて出る」だけで、漏れない（バケットが非公開のため、失敗しても見えない側に倒れる）

## 決めたこと（2026-10-28）

1. **方式**：上記のとおり（投稿・プロフィールは署名付き URL、DM と証拠は中継、バケットは2つとも非公開）。署名付き URL の弱点を docs に明記する
2. **署名付き URL の期限は10分**
3. **ブラウザに覚えさせてよい。ただし覚えさせる時間は URL の期限を超えない**。超えなければ、漏れる範囲は2（10分）より広がらない
4. **Cloudflare の API 用の鍵は増やさない**。アプリは「証拠と画像のバケットの名前が同じなら起動しない」までを確かめ、バケットが公開になっていないかは公開前の確認項目（`deploy.md`）で代わりとする
   - 理由：設定を読める鍵をもう1つ持つこと自体が危険で、デプロイするのは1人。公開前の確認項目で代わりとする
5. **DM の画像はアップロードのときに縮める**（長辺 2048px 程度）。「元の大きさのまま」は決定ではなく、直していなかった問題のため。投稿の写真・プロフィール画像もあわせて縮めることにした（`post.md`「写真の大きさ」。済み）
6. **DB はキーに変える。列の名前も `image_key` にする**（ステップ1。済み）
   - 理由：ホスト名入りの URL を DB に持っているのが元々の間違い
7. **署名する前に `PublicImageAccess` で確かめ直す（守りを2段にする）**。画像の枚数分の SQL は、まとめて1本にする
   - 理由：署名付き URL では、守りが「応答を絞る」1段になる。棚卸しのテスト（`VisibilityInventoryTest`）が実際に2つの穴を見つけた経緯があるので、最後の瞬間にもう一度確かめる
8. **アップロードの上限を下げる・縮める**のは、R2 より前に独立した変更として行う（済み。`post.md`「写真の大きさ」）。表示用の縮小画像（一覧のサムネイル）は、後の別の作業にする
9. **Docker が要るテスト（R2 のエミュレータにつなぐもの）は、普段の `mvnw test` に入れない**
   - 理由：環境のせいで落ちるテストは、やがて「また環境か」で流される（ログのテストで狼少年の話をしたのと同じ）
10. **本番の表の作り方は、今回は扱わない**。本番にデータがないため、Flyway を入れるときに最初の1本で今のスキーマ全体を作る。Flyway は公開前に必ず入れる（`deploy.md`）

## ステップ

どのステップも、テストを先に書き、実装前に正しい理由で失敗することを確かめてから実装する。

1. **DB にはキーだけを持ち、応答のところで URL に変える**（ローカルのまま）…… 済み（下記）
2. （未実施）ローカルで署名付き URL にする（`/uploads/{キー}?exp=…&sig=…`。署名の前に `PublicImageAccess` でまとめて確かめる。画面は期限切れの画像を取り直す）
3. （未実施）書き込みの入口を絞り（`prepare()` を通らずに保存できないようにする）、読み出しを流す形（ストリーム）にする
4. （未実施）R2 の実装（画像）。保存・読み出し・削除の約束ごとのテストを、ローカルの実装と、エミュレータ上の R2 の実装の両方で流す（エミュレータのテストは普段の `mvnw test` に入れない）
5. （未実施）R2 の実装（証拠）。R2 の中でのコピー、起動時の守り（バケットの名前が同じなら起動しない）
6. （未実施）本番の設定、本物の R2 での確認、docs の書き直し（`admin.md`「非公開にした投稿の写真」・`dm.md`「画像」・`post.md` の CDN の記述・`CLAUDE.md` の `PublicImageAccess` の決まり）

## ステップ1：DB にはキーだけを持つ（2026-10-28）

- 画像を指す列を、キーの列に変えた（列の名前も変えた）

| 以前 | 今 |
| --- | --- |
| `post_images.image_url`（URL） | `post_images.image_key` |
| `users.profile_image_url`（URL） | `users.profile_image_key` |
| `messages.image_url`（URL） | `messages.image_key` |

- キーは、保存するときに付ける名前（乱数32桁 + `.jpg`・`.png`。`ImageKeys`）。以前の URL（`http://localhost:8081/uploads/…`）の最後の部分と同じ
- `ImageStorage` は、キーで保存・読み出し・削除する（`store` はキーを返す）
- **ブラウザに渡す URL は、応答を作るときに `ImageUrls` でキーから組み立てる**。応答に画像の URL を入れるところ（ブロック一覧・DM の一覧の相手・フォロー一覧・通知・一覧のカード・投稿の詳細・プロフィール・ユーザー検索）は、すべてここを通す。ステップ2で署名付き URL にするときは、ここだけを変える
  - キーの形でない値（以前の URL が残った DB など）を渡すと、`ImageUrls` は例外を投げる（壊れた URL を黙って返さない）
- 応答の項目名（`imageUrls`・`thumbnailUrl`・`profileImageUrl`）は変えていない（画面は変更なし）
- `PublicImageAccess` は、URL の最後のファイル名で探す代わりに、キーが一致するかで探す（以前の「DB の URL の先頭が今の設定と違っても見つける」ための作りは要らなくなった）
- テスト
  - 投稿の写真・プロフィール画像・DM の画像で、DB にはキーだけが入り、応答はキーから組み立てた URL になること（`PostCreateApiTest`・`ProfileEditApiTest`・`MessageImageApiTest`）
  - 画像を指す列がキーの列だけで、URL の列が残っていないこと（`ImageKeyColumnsTest`）
  - テストで DB に入れる画像の値は、読みやすい名前から `ImageTestSupport.key("first.jpg")` で作り、応答の URL は `ImageTestSupport.url("first.jpg")` で比べる
  - 棚卸しのテスト（`VisibilityInventoryTest`）は、以前は写真の URL に投稿の題名が入っていたため、題名を目印に、写真の URL だけが出る応答（通知の投稿など）の漏れも見つけていた。キーには題名が入らないため、**題名から作った写真のキーも目印にした**（見つける力を落とさないため）

### チームへの連絡（ステップ1を develop に入れるとき）

- **pull した後、`docker compose down -v` で DB を作り直す**（列の名前を変えたため。`ddl-auto=update` は古い列（`image_url` など。NOT NULL のものがある）を消さないため、作り直さないと、写真付きの投稿・DM が保存できない）
- **`backend/uploads/` と `backend/evidence/` の中身を消す**（DB を作り直すと、どこからも参照されないファイルになる）。開発用のテストデータは、起動時に作り直される（README「開発用のテストデータ」）
- 新しい環境変数はない。R2 の鍵も要らない（開発は今までどおりローカルの保存先）
