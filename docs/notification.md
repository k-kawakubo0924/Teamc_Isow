## 仕様

### 通知一覧の画面（/notifications）

- ホーム画面左上のベルから開く。ベルには未読件数のバッジを出す。件数は「未読の通知」と「未読のお知らせ」の合計（タブにはそれぞれを出す）
  - 未読の通知には、メッセージの通知を含めない（DM のバッジで数えるため。両方で数えると同じ未読が2回出る）
  - 件数を取り直すタイミングは DM のバッジと同じ（画面の移動・ブラウザのタブに戻ったとき・1分ごと・既読などの操作の直後）
- 通知を種別で分ける
  - 「いいね・フォロー」タブ … すべての通知（相談・メッセージも含む）を新しい順に表示する。未読の通知の件数をバッジで表示する（メッセージの通知は含めない）
  - 「お知らせ」タブ … 管理者が管理画面から発行した、運営からのお知らせを表示する（下記「お知らせ」）。未読のお知らせの件数をバッジで表示する
  - ベルの件数は2つのタブの合計のため、片方のタブを読み終えても、もう片方に未読があればベルの数字は残る
- 通知がどのくらい前にきたかわかる（例：5分前、32分前、2時間前、昨日、3日前、1週間前）
- 未読・既読は色を変え、見やすくする（未読は白、既読は暗めの背景）
- 3点リーダーを押すと「未読に戻す」（既読の通知のみ）・「通知を削除」が選択可能
- 通知が1件もないときは「通知はありません」と、補足文「いいねやフォローがあるとここに表示されます」を表示する
- 「すべて既読」は、今は画面にボタンがない（API `POST /api/notifications/read-all` だけがある）
  - 対象は通知だけで、お知らせは既読にならない。押した後もお知らせの未読があればベルの数字は残る
  - ボタンを置くときは、「押したのに消えない」と感じさせないよう、次の2つを守る
    - 「いいね・フォロー」タブの中（タブの切り替えより下、一覧の上）に置き、「お知らせ」タブを開いているときは出さない。画面の見出し（「通知」の横）には置かない（両方のタブに効くように見えるため）
    - ラベルは「いいね・フォローをすべて既読にする」のように対象を書く（「すべて既読」だけにしない）

#### 通知の文面

文面は画面側で組み立てる（`frontend/src/pages/notification/notificationText.ts`）。サーバーは種類と相手のユーザー名を返す。

| 種類 | 文面 |
| --- | --- |
| いいね | @◯◯ さんがあなたの投稿にいいねしました |
| フォロー | @◯◯ さんがあなたをフォローしました |
| 相談が届いた | @◯◯ さんから相談が届いています |
| 相談が承認された | @◯◯ さんが相談を承認しました |
| 相談が拒否された | @◯◯ さんへの相談は承認されませんでした（「拒否」より柔らかい言い方にする） |
| メッセージが届いた | @◯◯ さんからメッセージが届いています |
| 運営が投稿を非公開にした | 運営 があなたの投稿を非公開にしました |
| 運営が投稿を公開に戻した | 運営 があなたの投稿の非公開を解除しました |

- 運営からの通知は「誰が」（した人）がないため、@ユーザー名の代わりに「運営」と出し、アイコンは空にする（`admin.md`「6. 措置」）

#### タップしたときの遷移先

タップしたら既読にしてから遷移する。

| 種類 | 遷移先 |
| --- | --- |
| いいね | いいねされた投稿の詳細画面（`/posts/{id}`。`post.md`「投稿の詳細画面」） |
| 運営が投稿を非公開にした・公開に戻した | その投稿の詳細画面（投稿者本人には、非公開でも見える） |
| フォロー | 相手のプロフィール |
| 相談・承認・拒否・メッセージ | その会話のチャット（拒否された会話も、当事者は読める。`dm.md`） |

### 通知を作るタイミング

| きっかけ | 通知を作る条件 |
| --- | --- |
| いいね | 新しくいいねを登録したとき。同じ人・同じ投稿の通知がすでにあれば作らない（取り消して再度いいねしても、通知は溜まらない） |
| フォロー | 新しくフォローの行を作ったとき。解除から5分以内の再フォロー（元の行に戻す）では作らない（`profile.md`） |
| 相談の申込 | 申し込んだとき。申込時の一言メッセージは、メッセージの通知にはしない |
| 相談の承認・拒否 | 承認・拒否したとき |
| メッセージ | 送ったとき。相手宛ての、その会話の通知があれば日時を更新して未読に戻す |
| 会話の終了 | 作らない |
| 管理者が投稿を非公開にした・公開に戻した | 措置が確定したとき（`admin.md`「6. 措置」）。利用停止・解除では作らない（本人は使えない間に見られないため。利用停止の画面で伝える） |

- 自分の操作では通知を作らない（自分の投稿に自分でいいね など。自分へのフォロー・相談の申込はそもそもできない）
- 通知は、いいね・フォローなどの処理が確定（コミット）した後に、別のトランザクションで作る
  - 通知の作成に失敗しても、いいね・フォローなどは成功のままにする（失敗はログに出すだけ）
  - いいね・フォローなどが失敗した場合は、通知も作らない

- ブロックした時点で、2人の間の通知（受け取る人と、した人がブロックした人・された人のもの）を削除する。ブロック中はいいね・フォロー・相談ができないため、新しい通知もできない（`profile.md`「ブロック」）

### 通知の保存（テーブル `notifications`）

- 1件ごとに、受け取る人・通知の種類・関連するユーザー（した人）・関連する投稿／会話・作成日時・通知日時・既読日時を持つ

| 種類（定数名） | 内容 | 受け取る人 | 関連するユーザー | 関連 |
| --- | --- | --- | --- | --- |
| `LIKED` | いいねされた | 投稿者 | いいねした人 | 投稿 |
| `FOLLOWED` | フォローされた | フォローされた人 | フォローした人 | なし |
| `CONSULTATION_REQUESTED` | 相談が届いた | 申し込まれた人 | 申し込んだ人 | 会話 |
| `CONSULTATION_APPROVED` | 相談が承認された | 申し込んだ人 | 承認した人 | 会話 |
| `CONSULTATION_REJECTED` | 相談が拒否された | 申し込んだ人 | 拒否した人 | 会話 |
| `MESSAGE_RECEIVED` | メッセージが届いた | 送った人の相手 | 送った人 | 会話 |
| `POST_HIDDEN` | 運営が投稿を非公開にした | 投稿者 | なし（NULL） | 投稿 |
| `POST_UNHIDDEN` | 運営が投稿を公開に戻した | 投稿者 | なし（NULL） | 投稿 |

- 種類は定数名を文字列で保存する（プロフィールの性別・年代と同じ。種類を増やしても保存できなくならないようにするため）
- DB の検査制約でも、受け取る人と関連するユーザーが同じ行（自分の操作の通知）を防ぐ
- 関連するユーザー（`actor_id`）は、運営からの通知では NULL にする（措置を作ったときに NULL を許すようにした。既存の DB では作り直しか `ALTER TABLE` が要る。`admin.md`「6. 措置」）
  - 検査制約は NULL の行を通すため、変えていない
- 関連するユーザーが、見ている人から見えない（ブロックの間柄・利用停止中）通知は、一覧にも未読の件数にも出さない（行は消さない。利用停止を解除すると戻る）
- メッセージの通知は会話ごと・受け取る人ごとに1件にまとめる
  - 同じ会話で新しいメッセージが届いたら、新しい行を作らずに通知日時を更新する
  - 既読にした後で届いた場合は、未読に戻す
  - 一覧の並び順・「〇分前」の表示には通知日時を使う（作成日時は変えない）
- 相談の通知（届いた・承認・拒否）は会話ごとに1件。相談は申し込むたびに新しい会話になるため、再申請では別の通知になる
- いいねの通知は、同じ人・同じ投稿で1件まで。既存の通知の日時・既読の状態も変えない
- いいねの通知は、投稿を削除すると一緒に削除する（DB の外部キーの `ON DELETE CASCADE`。`post.md`「投稿の削除」）
  - 削除された分、未読の件数も減る
  - 削除の前から開いていた通知の一覧で、その通知を押した場合は、投稿の詳細画面が「投稿が見つかりません」を出す

### API

すべて認証が必要。自分の通知だけを扱い、他人の通知・存在しない通知はどちらも同じ 404（「通知が見つかりません。」）にする。

| API | 内容 |
| --- | --- |
| `GET /api/notifications?page=&size=` | 自分の通知一覧。通知日時の新しい順（同じなら ID の大きい順）。ページで区切り、`hasNext` を返す。メッセージの通知も含む |
| `GET /api/notifications/summary` | 未読件数。`unreadCount`（通知。メッセージの通知は含めない。DM のバッジで別に数えるため）と `unreadAnnouncementCount`（お知らせ。下記「お知らせ」）を別々に返す。ベルには画面側で合計を出す |
| `POST /api/notifications/{id}/read` | 既読にする（204）。すでに既読なら最初に既読にした日時のまま |
| `POST /api/notifications/{id}/unread` | 未読に戻す（204） |
| `DELETE /api/notifications/{id}` | 削除する（204） |
| `POST /api/notifications/read-all` | 自分の未読の通知をすべて既読にする（204。メッセージの通知も含む。お知らせは含まない） |

- 一覧の1件：`id`・`type`（種類の定数名）・`actor`（`id`・`username`・`profileImageUrl`。運営からの通知は null）・`post`（いいね・運営からの投稿の通知のみ。`id`・`thumbnailUrl`）・`conversationId`（相談・メッセージのみ）・`notifiedAt`・`read`
- 文面はサーバーで組み立てない。画面側で `type` と `actor.username` から組み立てる（後から文面を変えやすくするため）

### お知らせ（「お知らせ」タブ）

管理者が管理画面から発行した、全利用者向けのお知らせ（発行・取り消しは `admin.md`「お知らせの発行」）。デザイン画像はないため、通知のカードに見た目を合わせる。

#### 画面

- 一覧は発行日時の新しい順。1件には題名と発行日（例：`2026/10/08`）だけを出し、本文は閉じておく
  - 古いお知らせも残るため、「〇日前」ではなく日付で出す
- 押すと、その場で本文を開く（折りたたみ）。もう一度押すと閉じる
  - 別の画面に移らないのは、タブを画面の中の状態で持っているため、戻ると「いいね・フォロー」タブに戻ってしまうから
  - 本文は一覧と一緒に読み込んであるため、開くときに通信しない
- 本文は文字のまま出し（HTML として扱わない。`dangerouslySetInnerHTML` は使わない）、改行はそのまま表示する（`white-space: pre-wrap`）
- 未読は白、既読は暗めの背景（通知と同じ）
- 未読のお知らせを開いたら既読にし、未読件数を取り直す。既読にする通信が失敗しても本文は開いたままにする（次に一覧を開いたときに未読のまま出る）
- 「未読に戻す」「削除」のメニューは出さない（全員に同じものを出す共有のお知らせのため）
- お知らせが1件もないときは「お知らせはありません」を表示する（補足文は出さない）

#### 既読・未読

- お知らせごと・利用者ごとに既読を記録する（テーブル `announcement_reads`）。開いた時点で1行作る
  - 発行したときに全員分の行は作らない。行があれば既読、なければ未読
  - 何度開いても1行で、最初に開いた日時のまま
- **登録より前に発行されたお知らせも一覧に出すが、既読として扱い、未読件数に数えない**
  - 隠すと、登録の前日に出た「来週のメンテナンス」のお知らせなどが見られなくなる
  - 未読にすると、登録した直後からバッジが溜まった状態になる
- 取り消されたお知らせは、一覧にも未読件数にも出さない。既読にしようとしても、存在しないものと同じ 404

#### テーブル `announcement_reads`

| 項目 | 列 | 内容 |
| --- | --- | --- |
| 読んだ人 | `user_id` | ユーザーを削除すると、一緒に削除する（`ON DELETE CASCADE`） |
| お知らせ | `announcement_id` | アプリではお知らせの行を消さないが、手作業で消すときに邪魔をしないよう、一緒に削除する（`ON DELETE CASCADE`） |
| 開いた日時 | `read_at` | 最初に開いた日時 |

- 主キーは `user_id` と `announcement_id` の組み合わせ（列の順番は Hibernate が決め、今は `announcement_id`, `user_id` の順）。一覧・未読件数とも2つの列で探すため、どちらの順番でもこの主キーが使える

#### API

すべて認証が必要。

| API | 内容 |
| --- | --- |
| `GET /api/announcements?page=&size=` | 取り消していないお知らせの一覧。発行日時の新しい順（同じなら ID の大きい順）。ページで区切り、`hasNext` を返す |
| `POST /api/announcements/{id}/read` | 既読にする（204）。すでに既読なら最初の日時のまま。存在しない・取り消したお知らせは 404（「お知らせが見つかりません。」） |

- 一覧の1件：`id`・`title`・`body`・`publishedAt`・`read`。管理者側の情報（発行者・取り消し）は返さない
- SQL の本数は件数に関係なく一定（一覧は既読の記録を一緒に読み込んで1本、未読件数は1本）
- **一覧の応答に本文を含めるため、お知らせの件数が増えるほど通信量が増える**
  - 今は本文が最大2000文字 × 1ページ20件で、約40KB。問題のない量
  - 将来お知らせが大量に増えて重くなったら、一覧は題名・日付だけにして、本文は開いたときに別の API で取る形に見直す
