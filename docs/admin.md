## 仕様

### 方針（決定事項）

- 管理者画面は、利用者アプリと同じプロジェクトに `/admin` として作る
  - バックエンドの API は `/api/admin/**`、フロントエンドの画面は `/admin` 以下に置く
- 管理者アカウントは画面から作れないようにする（下記「管理者アカウントの用意」）
- DM の中身を管理者が自由に読める機能は作らない
  - 通報対応（後の段階）で必要になったときも、**通報されたメッセージとその前後だけ**に限定する
- 管理画面は PC で使う前提とする（利用者アプリはスマホ前提）
  - 下部ナビゲーションは出さず、PC の画面幅に合わせたレイアウトにする。スマホでの見やすさは考慮しない
- 通報機能は未実装のため、今回の範囲に含めない。後から足せる形にしておく（下記「後の段階で作るもの」）

### 作る範囲

#### 第1段階（今回）

| | 内容 |
| --- | --- |
| 1 | 権限の仕組み（`users` への列の追加、`/admin` と `/api/admin/**` の出し分け） |
| 2 | マスタの管理（ファッションの種類・骨格タイプ・パーソナルカラー・公式タグの追加・無効化・有効に戻す） |
| 3 | お知らせの発行 |
| 4 | 管理操作のログ（誰がいつ何をしたか） |

#### 後の段階で作るもの

以下は**後で作る**。第1段階では作らない。

- 通報の一覧と対応（通報機能そのものも未実装。`dm.md`・`profile.md` 参照）
- 投稿の非公開化・削除

- 権限のチェックを `/api/admin/**` 全体にかける（新しい管理 API を足すだけで守られる）
- 管理操作のログの「操作の種類」「対象」は、マスタ・お知らせ以外も入れられる形にする（下記「管理操作のログ」）

### 1. 権限の仕組み

#### 現状（調査結果）

- `users` テーブルに、権限（管理者かどうか）を表す列はない
- ログインのトークン（JWT）には、ユーザー ID（`sub`）・発行日時・有効期限しか入っていない（`JwtTokenService`）
- `SecurityConfig` は「疎通確認・新規会員登録・ログイン・保存した画像の表示だけ認証なし、それ以外はすべて認証が必要」で、権限で分ける仕組みはない
- フロントエンドにも、権限で画面を出し分ける仕組みはない

#### users への列の追加

- `users` に `role`（権限）の列を追加する
  - 値は `USER`（一般の利用者）と `ADMIN`（管理者）
  - プロフィールの性別・年代・通知の種類と同じく、enum の定数名を文字列で保存する（`@Enumerated` は使わない。
    Hibernate が値の一覧の検査制約を付け、ddl-auto=update では更新されず、段階を増やしたときに保存できなくなるため）
  - 空にできない列とし、DB 側の既定値を `USER` にする（ddl-auto=update で既存の行がある表に列を足すため。既存の利用者は全員 `USER` になる想定）
- 新規会員登録で作られるユーザーは、常に `USER`
- `role` を変える API・画面は作らない（下記「管理者アカウントの用意」）

> **注意（重要）：既存の行の `role` が NULL になる可能性がある**
>
> - `role` の列は後から足すため、ddl-auto=update で作った各自の開発用 DB では、既存の行が NULL になる可能性がある
>   （DB の種類や列の足し方によっては、既定値が既存の行に入らない。空にできない制約も、既存の表には付かないことがある）
> - そのため、**管理者かどうかの判定は、必ず「`role` が `ADMIN` と一致するか」で行う**
>   - 「`USER` でなければ管理者」のような書き方をしない
>   - NULL や想定外の値（`admin` のような小文字、存在しない段階の名前など）は、**管理者として扱わない**（安全側に倒す）
> - 実装するときに、この性質を確かめるテストを入れる（`role` が `ADMIN`・`USER`・NULL・想定外の値の4通りで、管理者として通るのは `ADMIN` だけであること）
> - `role` は NOT NULL なので、DB を作り直した後は DB 上で NULL になり得ないが、コード側でも NULL を管理者として扱わない**二重の守り**にしている
>   - NULL は DB に書き込めないため、`User.isAdmin()` の単体テスト（DB を使わない）で確かめる
>   - 想定外の値（`admin`・`SUPER_ADMIN` など）は DB に直接書き込み、`SecurityConfigTest` で通しで確かめる

#### 権限のチェックは必ずサーバー側で行う

- **画面を隠すだけでは守れない**。フロントエンドのコードは誰でも読めて、API は画面を通さずに直接呼べるため
- 管理者かどうかは、**リクエストのたびに DB の `users.role` で確かめる**
  - トークンには権限を入れない。トークンの中身は誰でも読めるうえ、入れると、管理者から外してもトークンの有効期限（24時間）まで管理者のまま使えてしまうため
  - DB で確かめるため、管理者から外した時点で、そのトークンでは管理 API を使えなくなる

#### /api/admin/** の守り方（SecurityConfig）

- `SecurityConfig` の `authorizeHttpRequests` に、`anyRequest().authenticated()` より前に `/api/admin/**` の規則を足す
  - 認証済みであることに加えて、トークンの `sub` のユーザーの `role` が `ADMIN` であることを、DB で確かめる（専用の判定処理を作り、`access(...)` で使う）
  - URL の前方一致で `/api/admin/**` 全体を守るため、管理 API を足すときに個別の設定は要らない
- 念のため、管理 API のサービスでも管理者であることを確かめる（設定の書き間違いで穴が開かないよう、二重に守る）
- 応答（管理者でない場合）

| 状態 | 応答 |
| --- | --- |
| トークンなし・不正・期限切れ | 401（他の API と同じ） |
| ログイン済みで、管理者でない | **404**（存在しない URL と同じ応答。下記） |
| 管理者 | 通常どおり |

- **既存の「存在を漏らさないために 404 を返す」方針に揃える**（他人の会話・通知は、存在しない場合と同じ 404 にしている。`dm.md`・`notification.md`）
  - 管理者でない人に 403 を返すと、「ここに管理用の何かがある」ことが分かってしまうため、存在しない URL と見分けが付かない 404 にする
- `SecurityConfigTest` に、管理者向けの検証を足す
  - トークンなしで `/api/admin/**` を呼ぶと 401
  - 一般の利用者のトークンで呼ぶと 404（存在しない URL と同じ応答であること）
  - 管理者のトークンで呼ぶと通れる
  - 管理者から `USER` に戻したユーザーの、戻す前に発行したトークンでは 404（DB で確かめていること）
  - `role` が NULL・想定外の値のユーザーのトークンでは 404（上記「注意」）
  - 認証なしで許可している URL（ログインなど）と、一般の API の動きが変わっていないこと

#### 管理者でない人が /admin を開いたとき（画面）

- 利用者アプリと同じく「ページが見つかりません」を表示する（API の 404 と揃え、管理画面の存在を見せない）
  - 今の利用者アプリには、存在しない URL を開いたときの画面がない（何も表示されない）。合わせて「ページが見つかりません」の画面を作る
- 管理者かどうかは、画面を開いたときにサーバーに問い合わせて決める（画面側の判定は表示の切り替えのためだけで、守りはサーバー側で行う）
- 一般の利用者の画面（下部ナビゲーションなど）には、管理画面への導線を置かない

#### 管理者アカウントの用意

- 管理者アカウントは**画面から作れない**（登録画面・管理画面のどちらにも、管理者にする操作を置かない）
- 最初の管理者は、**起動時の処理で、環境変数 `ADMIN_EMAIL` に指定されたメールアドレスの登録済みユーザーを `ADMIN` にする**
  - マスタの初期データの投入（`MasterDataSeeder`）と同じく、起動時の処理（`ApplicationRunner`）で行う
  - チーム全員が、各自の開発環境で自分のアカウントを管理者にして、管理画面を開けるようにするため
  - 手順：通常の新規会員登録でアカウントを作る → `.env` の `ADMIN_EMAIL` にそのメールアドレスを書く → バックエンドを再起動する
  - メールアドレスはコードに書かない（`CLAUDE.md` のルール「接続情報やキーは環境変数で管理し、コードに直接書かない」）
  - `.env.example` に `ADMIN_EMAIL` の項目を足す（値は空にし、説明を書く）
  - `ADMIN_EMAIL` が空、または指定したメールアドレスのユーザーがいない場合は、何もしない（起動は止めない。ユーザーがいない場合はログに出す）
  - 既存の管理者を `USER` に戻す処理はしない（`ADMIN_EMAIL` を書き換えても、前に指定したユーザーは管理者のまま）
  - メールアドレスの比較は、新規会員登録と同じく前後の空白を除き、小文字にそろえて行う（`auth.md`）
  - 管理者にしたら、管理操作のログに「操作した人＝システム」として残す（下記「管理操作のログ」）。アプリのログにも「誰を管理者にしたか」を出す
    - ログには、メールアドレスではなくユーザー名だけを書く
    - ログを残せなかった場合は管理者にもしない。起動時はその失敗をアプリのログにエラーとして出すだけで、**起動は続ける**（次の起動でもう一度試みる）

### 2. マスタの管理

#### 現状（調査結果）

| マスタ | テーブル | 有効・無効 | 補足 |
| --- | --- | --- | --- |
| ファッションの種類 | `fashion_categories` | `is_active` | 共通の作り `MasterEntity`（名前は重複不可・並び順 `display_order`・登録日時） |
| 骨格タイプ | `body_types` | `is_active` | 同上 |
| パーソナルカラー | `personal_colors` | `is_active` | 同上 |
| タグ | `tags` | `is_active` | 公式タグ（`is_official = true`）と手入力のタグを1つのテーブルで持つ。重複の判定は正規化した名前（`normalized_name`、一意）。並び順は公式タグだけ |

- 無効（`is_active = false`）の選択肢は、画面の選択肢に出さない。今は、無効にする・名前を変える API や画面はなく、DB を直接書き換えるしかない
- 初期データは起動時に `MasterDataSeeder` が登録する。投入済みかどうかは `master_seed_history` に「種類:名前」（例：`fashion_category:きれいめ`）で記録している
  - 既存の行は更新しないため、名前を直したり無効にしたりしても、起動のたびに元へ戻ることはない
  - 同じ名前の行がすでにあれば、行は追加せず履歴だけを記録する（README「マスタデータ（選択肢）の追加」）

#### できる操作（第1段階）

- 一覧：無効のものも含めて、並び順で表示する（有効・無効が分かるようにする）
- 追加：名前を入力して追加する。追加したものは末尾に並ぶ（並び順は、そのマスタの既存の値より大きい値を自動で付ける。並び順の変更は後で作る。上記「後の段階で作るもの」）
  - 名前が重複する場合は追加しない（同じマスタ内で一意）
  - 公式タグは、タグ名の正規化（表記ゆれをそろえる。`post.md`）をしたうえで重複を判定する。
    同じ名前の手入力のタグがすでにある場合は、新しい行を作らず、そのタグを公式タグにする（既存の投稿のタグをそのまま公式タグとして扱うため）
    - このときは、管理者の画面に「既存のタグを公式にしました」と表示する（新しく追加したのではないことが分かるようにするため）
- 無効化：選択肢に出さないようにする
- 有効に戻す：無効にした選択肢を、再び選択肢に出す（間違えて無効にした場合などに戻せるようにするため）
- 名前の変更は、第1段階では作らない
  - なくても困らず、名前を変えると過去の投稿・プロフィールの表示まで遡って変わるため、別途検討が必要

#### 削除はせず、無効化だけにする

- マスタの行は**削除しない**。既存の投稿・プロフィールがマスタの行を参照しているため
  - 投稿はファッションの種類・タグを、プロフィールは骨格タイプ・パーソナルカラーを ID で参照している。削除すると、参照している投稿・プロフィールが壊れる（外部キーの制約で削除できないか、表示できなくなる）
- 無効にした選択肢は、新しく選べなくなるだけで、すでに付いている投稿・プロフィールの表示はそのまま
  - 設定済みの選択肢は、無効になっても編集画面でそのまま保存できる（今の仕様。`profile.md`）
- 初期データの選択肢を無効にしても、`MasterDataSeeder` は既存の行を更新しないため、起動のたびに有効へ戻ることはない

### 4. 管理操作のログ

- 管理者の操作（データを変える操作）はすべて記録する。一覧を見るだけの操作は記録しない
- 起動時の管理者への昇格のように、人が操作していないものは「システム」の操作として記録する
- テーブル `admin_operation_logs`（エンティティ `AdminOperationLog`）。記録する項目

| 項目 | 列 | 内容 |
| --- | --- | --- |
| 操作した人 | `operator_id` | 管理者のユーザー ID。システムの操作なら NULL。**外部キーは張らない**（下記） |
| 操作した人の名前 | `operator_username` | **操作した時点の**ユーザー名。システムの操作なら「システム」（ユーザー名は半角英数字と `_` だけのため、実在するユーザー名とは重ならない） |
| 日時 | `operated_at` | 操作した日時 |
| 操作の種類 | `action` | `USER_PROMOTED_TO_ADMIN`（起動時の昇格）・`MASTER_CREATED`（マスタの追加）・`TAG_MADE_OFFICIAL`（既存の手入力のタグを公式にした）・`MASTER_DEACTIVATED`（マスタの無効化）・`MASTER_ACTIVATED`（マスタを有効に戻す）・`ANNOUNCEMENT_PUBLISHED`（お知らせの発行） |
| 対象 | `target_type`・`target_id` | 対象の種類（`USER`・`FASHION_CATEGORY`・`BODY_TYPE`・`PERSONAL_COLOR`・`TAG`・`ANNOUNCEMENT`）と、その ID。対象の表がいろいろなため、外部キーは張らない |
| 内容 | `detail` | 操作の中身が後から分かる短い説明（例：追加した名前、お知らせの題名）。1000文字まで |

- 操作した人の名前を、操作した時点の値として列に持つ。理由は2つ
  - 将来ユーザーを物理削除する機能を作ったとき、外部キーのせいでログが消える、または削除が失敗するのを避けるため（そのため `operator_id` にも外部キーを張らない）
  - ユーザー名が変わっても、過去のログの表示が遡って変わらないようにするため
  - 一覧を表示するときも、ユーザーの表と結合しない
- **`detail` に個人を特定する情報（メールアドレス・電話番号など）を書かない**
  - 例：起動時の昇格では、メールアドレスではなくユーザー名だけを書く
  - ログは保存期間を定めず削除もしないため、個人情報を書くと消せないまま残り続ける
- 操作の種類・対象の種類は、enum の定数名を文字列で保存する（上記 `role` と同じ理由。後の段階で種類を増やせるように）
- ログは、操作と**同じトランザクションで**記録する
  - ログを残せなかった場合は、操作も取り消す（記録のない操作が起きないようにするため）
  - 通知の作成は「失敗しても本体の処理を続ける」方針で、それとは逆だが、通知は利便性のため、ログは責任の記録のためなので、意図的に逆にしている（`notification.md`）
  - 記録の窓口 `AdminOperationLogger` は、操作のトランザクションの中でしか呼べない（外で単独で呼ぶとエラーになる）
- ログは追記だけとし、画面・API から変更・削除できないようにする
  - エンティティは保存後に変更されない作り（`@Immutable`、全列を変更不可）。リポジトリにも保存と読み込みのメソッドしか持たせない
- 接続元の IP アドレスは残さない（個人情報を増やす割に使い道がないため）
- 保存期間は定めず、古いログも削除しない
- 管理画面で、ログを新しい順に一覧できる（誰がいつ何をしたかを確かめるため）
  - API：`GET /api/admin/operation-logs?page=&size=`（新しい順。同じ日時なら ID の大きい順）。ページで区切り、`hasNext` を返す
  - `size` の上限は 50。範囲外の `page`・`size` はエラーにせず、`page` は 0 以上、`size` は 1〜50 に丸める（ホームの一覧・通知一覧と同じ）。応答の `size` は丸めた後の値

> **注意：ユーザーを削除する機能を将来作るときは、管理操作のログが消えないようにすること**
>
> - ログの `operator_id` には外部キーを張っていないため、ユーザーの行を物理削除しても、ログは残り、削除も失敗しない
> - ユーザーの削除に合わせて、ログを一緒に消す処理（連鎖削除など）を足さないこと。ログは責任の記録で、操作した人が退会した後も残す必要がある
> - 操作した人の名前は `operator_username` に残っているため、削除後も「誰が操作したか」は分かる
- 後の段階（ユーザーの利用停止・投稿の削除・通報の対応など）の操作も、同じ形で記録する
  - 通報対応で DM のメッセージを確認した場合は、そのこと（見た通報・見た範囲）も記録する

## 未確定・要確認

- 管理者画面のデザイン画像がない
  - 画面の構成・見た目は、作るときに決める（PC で使う前提）
- 管理者を複数人にするか、権限の段階を分けるか
  - 例：すべての操作ができる管理者と、お知らせの発行だけができる担当者を分けるか
  - 段階を分ける場合は、`role` の値を増やす（文字列で保存しているため、列の作りは変えずに増やせる）
  - 本番の環境で、2人目以降の管理者をどう増やすか（`ADMIN_EMAIL` は1つのメールアドレスを指定する作りのため）
- お知らせの表示場所と、利用者側の見え方
  - 通知一覧の「お知らせ」タブだけに出すか、ホームなどにも出すか
