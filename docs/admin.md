## 仕様

### 方針（決定事項）

- 管理者画面は、利用者アプリと同じプロジェクトに `/admin` として作る
  - バックエンドの API は `/api/admin/**`、フロントエンドの画面は `/admin` 以下に置く
- 管理者アカウントは画面から作れないようにする（下記「管理者アカウントの用意」）
- DM の中身を管理者が自由に読める機能は作らない
  - 通報対応でも、**通報されたメッセージとその前後だけ**に限定する（前後5件ずつ。下記「5. 通報」）
- 管理画面は PC で使う前提とする（利用者アプリはスマホ前提）
  - 下部ナビゲーションは出さず、PC の画面幅に合わせたレイアウトにする。スマホでの見やすさは考慮しない
- 通報の受付と、管理者が通報を見る画面は作った（下記「5. 通報」）
- 措置は、投稿の非公開化とユーザーの利用停止を作った（下記「6. 措置」）。管理者による投稿の削除はまだない
- お問い合わせ（利用停止中の申し立てを含む）を受け付け、管理者が見る画面を作った（下記「7. お問い合わせ」。受付の仕様は `settings.md`「お問い合わせ」）

### 作る範囲

#### 第1段階（今回）

| | 内容 |
| --- | --- |
| 1 | 権限の仕組み（`users` への列の追加、`/admin` と `/api/admin/**` の出し分け） |
| 2 | マスタの管理（ファッションの種類・骨格タイプ・パーソナルカラー・公式タグの追加・無効化・有効に戻す） |
| 3 | お知らせの発行・取り消し |
| 4 | 管理操作のログ（誰がいつ何をしたか） |

#### 後の段階で作るもの

以下は**後で作る**。第1段階では作らない。

- 管理者による投稿の削除（通報の受付・状態の記録は「5. 通報」、投稿の非公開化・利用停止は「6. 措置」で作った）
- 非公開にした投稿の写真を、URL を知っていても見られないようにする（下記「6. 措置」の「既知の限界」）
  - 今は、非公開にしても、写真の URL（`/uploads/...`）を知っている人は写真を見られる
  - ファッションのアプリでは、問題になるのは写真そのものであることが多いため、このままでは非公開化の効き目が半分になる
  - 直し方の案：通報の証拠のために作った「公開されない場所に置く仕組み」（`EvidenceStorage`。`/uploads/**` では配信しない）を使い、非公開にしたら写真をそちらへ移し、公開に戻したら元へ戻す。投稿者本人には、管理者向けの証拠の写真と同じく、認証つきの API から返す
- 利用状況の数字（登録者数・投稿数など）
- マスタの並び順の変更（新しく追加したマスタは末尾に並べば足り、並べ替えの操作は作る手間に対して得るものが小さいため。下記「マスタの管理」）
- 手入力のタグを管理画面から無効にする手段（今は公式タグしか無効にできない）
  - 利用者が不適切なタグを手入力した場合に、今は対応できない
  - 通報機能を作るときに、あわせて検討する

後から足すときに作りを変えずに済むよう、第1段階では次のようにしておく。

- 権限のチェックを `/api/admin/**` 全体にかける（新しい管理 API を足すだけで守られる）
- 管理操作のログの「操作の種類」「対象」は、マスタ・お知らせ以外も入れられる形にする（下記「管理操作のログ」）

### 1. 権限の仕組み

#### 作る前の状態（調査結果）

- `users` テーブルに、権限（管理者かどうか）を表す列はない
- ログインのトークン（JWT）には、ユーザー ID（`sub`）・発行日時・有効期限しか入っていない（`JwtTokenService`）
- `SecurityConfig` は「疎通確認・新規会員登録・ログイン・保存した画像の表示だけ認証なし、それ以外はすべて認証が必要」で、権限で分ける仕組みはない
- フロントエンドにも、権限で画面を出し分ける仕組みはない

これを受けて、以下のとおり作った（`Role`・`User.isAdmin()`・`AdminAuthorizationManager`・`AdminAccess`・`AdminAccountInitializer`）。

#### users への列の追加

- `users` に `role`（権限）の列を追加する
  - 値は `USER`（一般の利用者）と `ADMIN`（管理者）
  - プロフィールの性別・年代・通知の種類と同じく、enum の定数名を文字列で保存する（`@Enumerated` は使わない。
    Hibernate が値の一覧の検査制約を付け、ddl-auto=update では更新されず、段階を増やしたときに保存できなくなるため）
  - 空にできない列とし、DB 側の既定値を `USER` にする（ddl-auto=update で既存の行がある表に列を足すため。既存の利用者は全員 `USER` になる想定）
- 新規会員登録で作られるユーザーは、常に `USER`
- `role` を変える API・画面は作らない（下記「管理者アカウントの用意」）

> **注意（重要）：既存の行の `role` が NULL になる可能性がある**
>
> - `role` の列は後から足すため、ddl-auto=update で作った各自の開発用 DB では、既存の行が NULL になる可能性がある
>   （DB の種類や列の足し方によっては、既定値が既存の行に入らない。空にできない制約も、既存の表には付かないことがある）
> - そのため、**管理者かどうかの判定は、必ず「`role` が `ADMIN` と一致するか」で行う**
>   - 「`USER` でなければ管理者」のような書き方をしない
>   - NULL や想定外の値（`admin` のような小文字、存在しない段階の名前など）は、**管理者として扱わない**（安全側に倒す）
> - 実装するときに、この性質を確かめるテストを入れる（`role` が `ADMIN`・`USER`・NULL・想定外の値の4通りで、管理者として通るのは `ADMIN` だけであること）
> - `role` は NOT NULL なので、DB を作り直した後は DB 上で NULL になり得ないが、コード側でも NULL を管理者として扱わない**二重の守り**にしている
>   - NULL は DB に書き込めないため、`User.isAdmin()` の単体テスト（DB を使わない）で確かめる
>   - 想定外の値（`admin`・`SUPER_ADMIN` など）は DB に直接書き込み、`SecurityConfigTest` で通しで確かめる

#### 権限のチェックは必ずサーバー側で行う

- **画面を隠すだけでは守れない**。フロントエンドのコードは誰でも読めて、API は画面を通さずに直接呼べるため
- 管理者かどうかは、**リクエストのたびに DB の `users.role` で確かめる**
  - トークンには権限を入れない。トークンの中身は誰でも読めるうえ、入れると、管理者から外してもトークンの有効期限（24時間）まで管理者のまま使えてしまうため
  - DB で確かめるため、管理者から外した時点で、そのトークンでは管理 API を使えなくなる

#### /api/admin/** の守り方（SecurityConfig）

- `SecurityConfig` の `authorizeHttpRequests` に、`anyRequest().authenticated()` より前に `/api/admin/**` の規則を足す
  - 認証済みであることに加えて、トークンの `sub` のユーザーの `role` が `ADMIN` であることを、DB で確かめる（専用の判定処理を作り、`access(...)` で使う）
  - URL の前方一致で `/api/admin/**` 全体を守るため、管理 API を足すときに個別の設定は要らない
- 念のため、管理 API のサービスでも管理者であることを確かめる（設定の書き間違いで穴が開かないよう、二重に守る）
- 応答（管理者でない場合）

| 状態 | 応答 |
| --- | --- |
| トークンなし・不正・期限切れ | 401（他の API と同じ） |
| ログイン済みで、管理者でない | **404**（存在しない URL と同じ応答。下記） |
| 管理者 | 通常どおり |

- **既存の「存在を漏らさないために 404 を返す」方針に揃える**（他人の会話・通知は、存在しない場合と同じ 404 にしている。`dm.md`・`notification.md`）
  - 管理者でない人に 403 を返すと、「ここに管理用の何かがある」ことが分かってしまうため、存在しない URL と見分けが付かない 404 にする
- `SecurityConfigTest` に、管理者向けの検証を足す
  - トークンなしで `/api/admin/**` を呼ぶと 401
  - 一般の利用者のトークンで呼ぶと 404（存在しない URL と同じ応答であること）
  - 管理者のトークンで呼ぶと通れる
  - 管理者から `USER` に戻したユーザーの、戻す前に発行したトークンでは 404（DB で確かめていること）
  - `role` が NULL・想定外の値のユーザーのトークンでは 404（上記「注意」）
  - 認証なしで許可している URL（ログインなど）と、一般の API の動きが変わっていないこと

#### 管理者でない人が /admin を開いたとき（画面）

| 開いた人 | 表示 |
| --- | --- |
| 未ログイン | 利用者アプリの他の画面と同じく、ログイン画面へ移る（管理者かどうかは確かめない） |
| ログイン済みの一般利用者 | 存在しない URL を開いたときと**まったく同じ**「ページが見つかりません」の画面 |
| 管理者 | 管理画面の枠 |

- 「ページが見つかりません」は API の 404 と揃え、管理画面の存在を見せないためのもの。本来守りたい相手は、ログイン済みの一般利用者
- 存在しない URL を開いたときの画面（`NotFoundPage`）を作った。それまでは何も表示されなかった
  - ログイン中に存在しない URL を開くと「ページが見つかりません」と「ホームへ戻る」を出す。下部ナビゲーションは出さない
  - 未ログインで存在しない URL を開くと、ログインが必要な画面と同じくログイン画面へ移る（未ログインの人に、`/admin` とそれ以外の存在しない URL の違いが見えないように）
  - 一般の利用者に出す画面と同じものを使うため、この画面には管理画面に関わる文言・部品を入れない
- 管理者かどうかは、画面を開いたときにサーバーに問い合わせて決める（`GET /api/admin/me`。画面側の判定は表示の切り替えのためだけで、守りはサーバー側で行う）
  - 問い合わせている間は何も表示しない（一般の利用者に管理画面の枠が一瞬見えないように）
  - 接続できないなどで確かめられなかったときは、管理画面に関わる文言を含まないエラーの文だけを出す
- 一般の利用者の画面（下部ナビゲーションなど）には、管理画面への導線を置かない。管理者は URL を直接開く（「管理者という仕組みがある」ことを画面から漏らさないため）

#### 管理画面の枠

- URL は `/admin` 以下。`/admin` を開くと、最初の項目（マスタ管理）を開く
- PC で使う前提のレイアウト（幅 960px 以上）。左に行き先（「マスタ管理」`/admin/masters`・「お知らせ」`/admin/announcements`・「操作ログ」`/admin/operation-logs`）と、ログイン中の管理者のユーザー名、「アプリに戻る」を置く
- 利用者アプリの下部ナビゲーションは出さない
- 管理画面の中の存在しない URL は、枠の中に「ページが見つかりません」を出す（管理者には枠を見せてよいため）
- CSS のクラス名は `admin-*`（ファイルは `frontend/src/pages/admin/`）

#### 管理者アカウントの用意

- 管理者アカウントは**画面から作れない**（登録画面・管理画面のどちらにも、管理者にする操作を置かない）
- 最初の管理者は、**起動時の処理で、環境変数 `ADMIN_EMAIL` に指定されたメールアドレスの登録済みユーザーを `ADMIN` にする**
  - マスタの初期データの投入（`MasterDataSeeder`）と同じく、起動時の処理（`ApplicationRunner`）で行う
  - チーム全員が、各自の開発環境で自分のアカウントを管理者にして、管理画面を開けるようにするため
  - 手順：通常の新規会員登録でアカウントを作る → `.env` の `ADMIN_EMAIL` にそのメールアドレスを書く → バックエンドを再起動する
  - メールアドレスはコードに書かない（`CLAUDE.md` のルール「接続情報やキーは環境変数で管理し、コードに直接書かない」）
  - `.env.example` に `ADMIN_EMAIL` の項目を足す（値は空にし、説明を書く）
  - `ADMIN_EMAIL` が空、または指定したメールアドレスのユーザーがいない場合は、何もしない（起動は止めない。ユーザーがいない場合はログに出す）
  - 既存の管理者を `USER` に戻す処理はしない（`ADMIN_EMAIL` を書き換えても、前に指定したユーザーは管理者のまま）
  - メールアドレスの比較は、新規会員登録と同じく前後の空白を除き、小文字にそろえて行う（`auth.md`）
  - 管理者にしたら、管理操作のログに「操作した人＝システム」として残す（下記「管理操作のログ」）。アプリのログにも「誰を管理者にしたか」を出す
    - ログには、メールアドレスではなくユーザー名だけを書く
    - ログを残せなかった場合は管理者にもしない。起動時はその失敗をアプリのログにエラーとして出すだけで、**起動は続ける**（次の起動でもう一度試みる）

### 2. マスタの管理

#### マスタの作り（作る前の調査結果）

| マスタ | テーブル | 有効・無効 | 補足 |
| --- | --- | --- | --- |
| ファッションの種類 | `fashion_categories` | `is_active` | 共通の作り `MasterEntity`（名前は重複不可・並び順 `display_order`・登録日時） |
| 骨格タイプ | `body_types` | `is_active` | 同上 |
| パーソナルカラー | `personal_colors` | `is_active` | 同上 |
| タグ | `tags` | `is_active` | 公式タグ（`is_official = true`）と手入力のタグを1つのテーブルで持つ。重複の判定は正規化した名前（`normalized_name`、一意）。並び順は公式タグだけ |

- 無効（`is_active = false`）の選択肢は、画面の選択肢に出さない。管理画面ができる前は、無効にする API や画面がなく、DB を直接書き換えるしかなかった（無効化・有効に戻す API は下記「API」）
- 初期データは起動時に `MasterDataSeeder` が登録する。投入済みかどうかは `master_seed_history` に「種類:名前」（例：`fashion_category:きれいめ`）で記録している
  - 既存の行は更新しないため、名前を直したり無効にしたりしても、起動のたびに元へ戻ることはない
  - 同じ名前の行がすでにあれば、行は追加せず履歴だけを記録する（README「マスタデータ（選択肢）の追加」）

#### できる操作（第1段階）

- 一覧：無効のものも含めて、並び順で表示する（有効・無効が分かるようにする）
- 追加：名前を入力して追加する。追加したものは末尾に並ぶ（並び順は、そのマスタの既存の値より大きい値を自動で付ける。並び順の変更は後で作る。上記「後の段階で作るもの」）
  - 名前が重複する場合は追加しない（同じマスタ内で一意）
  - 公式タグは、タグ名の正規化（表記ゆれをそろえる。`post.md`）をしたうえで重複を判定する。
    同じ名前の手入力のタグがすでにある場合は、新しい行を作らず、そのタグを公式タグにする（既存の投稿のタグをそのまま公式タグとして扱うため）
    - このときは、管理者の画面に「既存のタグを公式にしました」と表示する（新しく追加したのではないことが分かるようにするため）
- 無効化：選択肢に出さないようにする
- 有効に戻す：無効にした選択肢を、再び選択肢に出す（間違えて無効にした場合などに戻せるようにするため）
- 名前の変更は、第1段階では作らない
  - なくても困らず、名前を変えると過去の投稿・プロフィールの表示まで遡って変わるため、別途検討が必要
- 状態を変える操作（追加・公式にする・無効化・有効に戻す）は、すべて管理操作のログに残す（下記「4. 管理操作のログ」）
  - すでに無効なものを無効にする・すでに有効なものを有効に戻すときは、何も変わらないため、ログも残さない（エラーにもしない）

#### API

ファッションの種類・骨格タイプ・パーソナルカラーは同じ作り（`MasterEntity`）のため、種類を URL で指定して同じ処理（`AdminMasterService`）を使う。
公式タグは手入力のタグと同じ表で持ち、追加のときに手入力のタグを公式にすることがあるため、別に作る（`AdminOfficialTagService`）。

| 操作 | ファッションの種類・骨格タイプ・パーソナルカラー | 公式タグ |
| --- | --- | --- |
| 一覧 | `GET /api/admin/masters/{kind}` | `GET /api/admin/official-tags` |
| 追加 | `POST /api/admin/masters/{kind}`（本文 `{"name": "…"}`。201） | `POST /api/admin/official-tags`（本文 `{"name": "…"}`。新しく作ったら 201、手入力のタグを公式にしたら 200） |
| 無効化 | `POST /api/admin/masters/{kind}/{id}/deactivate` | `POST /api/admin/official-tags/{id}/deactivate` |
| 有効に戻す | `POST /api/admin/masters/{kind}/{id}/activate` | `POST /api/admin/official-tags/{id}/activate` |

- `{kind}` は `fashion-categories`（ファッションの種類）・`body-types`（骨格タイプ）・`personal-colors`（パーソナルカラー）。それ以外・存在しない ID は 404
- 一覧は `{"items": [{"id", "name", "displayOrder", "active"}, …]}`（無効なものも含めて並び順・ID 順）。公式タグの一覧に手入力のタグは含めない
- 無効化・有効に戻すは、操作後の1件（`{"id", "name", "displayOrder", "active"}`）を返す
- 公式タグの追加は `{"tag": {…1件…}, "madeOfficial": true/false}` を返す。`madeOfficial` が true なら、同じ名前の手入力のタグを公式にした（画面で「既存のタグを公式にしました」と出す）
- 手入力のタグの ID を公式タグの API に渡した場合は、存在しないものと同じ 404（手入力のタグは管理の対象外）
- 管理者でなければ 404、トークンなしは 401（上記「1. 権限の仕組み」）

#### 画面（`/admin/masters`）

- 上のタブで4種類（ファッションの種類・骨格タイプ・パーソナルカラー・公式タグ）を切り替える。選んでいる種類は URL（`?kind=`）に持つ
  - 呼び名は、利用者アプリ・API と同じ「ファッションの種類」にそろえる
- 一覧：無効なものも出す。無効な行は、状態の欄に「無効」と出し、名前を薄く・取り消し線で表示する
- 追加：名前を入れて「追加」。送信中・名前が空のときは「追加」を押せない（連打で2回送らないように）
  - 重複・文字数の超過は、サーバーが返す理由（例：「同じ名前の骨格タイプがすでにあります（無効にしているものも含みます）」「名前は50文字以内で入力してください」）を入力欄の下にそのまま出す。入力した名前は消さない
  - 成功したら「「○○」を追加しました」。公式タグで手入力のタグを公式にしたときは「既存のタグを公式にしました（「○○」）」
- 無効化：各行の「無効にする」を押すと、すぐには実行せず、その行の下に確認を出す（ブラウザの確認ダイアログは使わない）
  - 確認の文：無効にすると利用者が新しく選べなくなること、既存の投稿・プロフィールの表示はそのままであること、あとで有効に戻せること
  - 確認では、最初に「やめる」を選んだ状態にする（続けて押しても実行しないように）
- 有効に戻す：各行の「有効に戻す」を押すと、確認なしで戻す（影響が小さく、間違えても無効にし直せるため）
- 操作が成功したら、一覧を読み直さずに、その行（追加なら末尾）をその場で新しい状態にする。失敗したらエラーを画面に出し、一覧は変えない

#### 追加するときの名前の扱い

- 名前の表記ゆれは、タグ名と共通の仕組み（`NameNormalizer`）でそろえる
  - 全角英数字を半角・半角カナを全角にし、前後の空白を除き、途中の連続した空白を1つにまとめた形で保存する
  - 現状：途中でまとめるのは半角スペース（全角スペースは NFKC で半角になるため含む）の連続だけで、タブや改行はまとめない（タグ名・マスタ名の両方。前後のタブ・改行は除く）
  - 先頭の `#` を除くのはタグだけ（`TagNameNormalizer`。ハッシュタグとして入力されるため。`post.md`）。マスタの名前では `#` も意味のある文字として残す（例：`＃ストリート` は `#ストリート` として保存し、`ストリート` とは別の名前として扱う）。公式タグの追加はタグの仕組みを使うため、先頭の `#` を除く
  - 重複は、さらに大文字小文字をそろえて判定する（例：`ＭＯＤＥ` と `mode` は同じ名前として扱う）
  - 無効にしているものと同じ名前も重複とする（同じ名前の選択肢が2つできないように。無効のものを使いたいときは有効に戻す）
  - 重複・空・長すぎる名前は 400（項目名 `name`）
- 名前の文字数の上限は、ファッションの種類・骨格タイプ・パーソナルカラーが50文字（列の長さ）、公式タグが30文字（投稿時に手入力できるタグと同じ）
- 並び順は、そのマスタの既存の最大値（無効なものも含む）に 10 を足した値（初期データと同じく、後から間に入れられるよう 10 ずつ空ける）
- 公式タグを追加するとき、同じ名前の手入力のタグがあれば、同じ行のまま公式タグにする
  - 行を作り直さないため、そのタグを付けた投稿との関連付け（`post_tags`）はそのまま残り、既存の投稿のタグも公式タグとして表示される
  - 表示名は、手入力のタグが最初に登録されたときの表記のまま（管理者が入力した表記には変えない。例：`Y2K` があるところに `ｙ２ｋ` を追加しても `Y2K` のまま）
  - 手入力のタグが無効になっていた場合は、有効に戻す（選択肢に出すために公式にするため）
  - ログの操作の種類は `TAG_MADE_OFFICIAL`（新しく作った場合は `MASTER_CREATED`）

#### 削除はせず、無効化だけにする

- マスタの行は**削除しない**。既存の投稿・プロフィールがマスタの行を参照しているため
  - 投稿はファッションの種類・タグを、プロフィールは骨格タイプ・パーソナルカラーを ID で参照している。削除すると、参照している投稿・プロフィールが壊れる（外部キーの制約で削除できないか、表示できなくなる）
- 無効にした選択肢は、新しく選べなくなるだけで、すでに付いている投稿・プロフィールの表示はそのまま
  - 設定済みの選択肢は、無効になっても編集画面でそのまま保存できる（今の仕様。`profile.md`）

#### 無効化の意味

- 無効化は「**これから選べなくする**」操作であり、「過去をなかったことにする」操作ではない
  - そのため、無効にしたタグが付いている既存の投稿は、そのタグ名で検索すると今も見つかる。既存の投稿・プロフィールの表示もそのまま
- 不適切な内容を隠すのは、通報・投稿の非公開化の役目であり、マスタの無効化とは別の機能である（上記「後の段階で作るもの」）
- **無効にした公式タグは、同じ名前を手入力しても付けられない**（意図した仕様）
  - 管理者が使わせないと決めたタグに、手入力の抜け道を作らないため
  - 表記ゆれだけが違う名前（例：大文字小文字・全角半角の違い）も同じタグとして扱うため、表記を変えても付けられない
- 初期データの選択肢を無効にしても、`MasterDataSeeder` は既存の行を更新しないため、起動のたびに有効へ戻ることはない

#### 無効にしたときの利用者側への影響（調査結果）

- すでに付いている投稿・プロフィールの表示：壊れない
  - 投稿の詳細・一覧、プロフィールは、マスタの有効・無効を見ずに、参照している行の名前をそのまま表示する
- 利用者側の選択肢：無効なものは出ない
  - 選択肢の一覧（`GET /api/masters`）は有効なものだけを返す
  - 投稿の作成で、無効なファッションの種類・無効なタグを選ぶと 400。無効にした公式タグは、同じ名前を手入力しても付けられない（上記「無効化の意味」）
  - 投稿の編集でも、設定済みの無効なファッションの種類・タグはそのまま保存できる（プロフィールの編集に合わせた。設定済みかどうかは DB の値で判定する。`post.md`「投稿の編集」）
  - プロフィールの編集で、無効な骨格タイプ・パーソナルカラーは選べない。ただし、設定済みの値は無効になってもそのまま保存できる（今の仕様。`profile.md`）
- 無効にしたタグについて
  - 無効にしたタグを付けた既存の投稿は、タグ名で検索すると引き続き見つかる（検索は投稿に付いているタグを見るため。上記「無効化の意味」のとおり意図した動き）
  - 無効にしたタグは、タグの入力候補・検索の候補ワードには出ない

### 3. お知らせの発行

- 管理者が、全利用者向けのお知らせ（運営からのお知らせ）を発行する
  - 通知一覧の「お知らせ」タブに出す。発行するとすぐにすべての利用者に表示される（利用者側の見え方・既読は `notification.md`「お知らせ」）
- 1件ごとに、題名・本文・発行日時・発行した管理者を持つ
- 本文は文字だけとし、改行はそのまま表示する。HTML は使わない（利用者の画面でも `dangerouslySetInnerHTML` は使わない。`CLAUDE.md`）
  - サーバーは題名・本文を受け取った文字のまま保存し、HTML の解釈・無害化はしない（`<b>` なども文字として保存・表示する）
- 発行は管理操作のログに残す（操作の種類 `ANNOUNCEMENT_PUBLISHED`、内容は「題名：…」）。ログを残せなければ発行も取り消す
- 発行後の**訂正（編集）は作らない**。**取り消しだけ**ができる（下記「取り消し」）
  - 誤りがあったときは、取り消してから正しい内容で発行し直す
  - 訂正を作らない理由：訂正前の本文を残す場所がない（ログの内容は1000文字までで、本文2000文字が入らない）。訂正したら未読に戻すかなど、決めることも増える

#### 取り消し

- 行は消さず、取り消した日時と取り消した管理者を残す（管理操作のログの対象 ID が残るように）
- 取り消したお知らせは、利用者側の一覧にも未読件数にも出さない。利用者の既読の記録は残すが、使わない
- 取り消しは元に戻せない（取り消しを取り消す操作はない）
- 取り消しは管理操作のログに残す（操作の種類 `ANNOUNCEMENT_WITHDRAWN`、内容は「題名：…」）。ログを残せなければ取り消しも元に戻す
- すでに取り消したものをもう一度取り消すと 409（「このお知らせはすでに取り消されています。」）。ログも残さない
  - 2人の管理者が同時に取り消しても1回だけになるよう、行をロックしてから確かめる

#### 文字数の上限

| 項目 | 上限 | 理由 |
| --- | --- | --- |
| 題名 | 100文字 | 投稿の題名と同じ。一覧で1行に収まる短い見出しを想定 |
| 本文 | 2000文字 | 投稿説明と同じ。メンテナンスの日時や不具合の説明など、運営からの連絡に足りる長さ |

- 題名・本文とも必須。前後の空白は除いてから判定する（空白・改行だけは未入力と同じ）
- 本文の改行は `\n` にそろえてから数える（`\r\n` を2文字と数えない。投稿の作成と同じ）

#### テーブル

テーブル `announcements`（エンティティ `Announcement`）

| 項目 | 列 | 内容 |
| --- | --- | --- |
| 題名 | `title` | 100文字まで |
| 本文 | `body` | 2000文字まで。文字だけ |
| 発行日時 | `published_at` | 発行した日時 |
| 発行者 | `publisher_id`・`publisher_username` | 発行した管理者のユーザー ID と、**発行した時点の**ユーザー名。管理操作のログと同じ理由で、外部キーは張らない（下記「4. 管理操作のログ」） |
| 取り消し | `withdrawn_at`・`withdrawn_by_id`・`withdrawn_by_username` | 取り消した日時・管理者のユーザー ID・**取り消した時点の**ユーザー名。取り消していなければ NULL。発行者と同じ理由で外部キーは張らない |

- 行を削除する処理は持たせない（リポジトリにも削除のメソッドを置かない）。変えられるのは取り消しの列だけ
- 利用者ごとの既読の記録（テーブル `announcement_reads`）は `notification.md`「お知らせ」

#### API

| 操作 | API |
| --- | --- |
| 発行 | `POST /api/admin/announcements`（本文 `{"title": "…", "body": "…"}`。201 で発行した1件を返す） |
| 発行済みの一覧 | `GET /api/admin/announcements?page=&size=`（新しい順。同じ日時なら ID の大きい順。取り消したものも含む） |
| 取り消し | `POST /api/admin/announcements/{id}/withdraw`（本文なし。200 で取り消した後の1件を返す。存在しなければ 404、取り消し済みなら 409） |

- 1件は `{"id", "title", "body", "publishedAt", "publisherId", "publisherUsername", "withdrawnAt", "withdrawnById", "withdrawnByUsername"}`（取り消していなければ取り消しの3つは null）
- 一覧は `{"items": [...], "page", "size", "hasNext"}`。`size` の上限は 50。範囲外の `page`・`size` はエラーにせず丸める（管理操作のログの一覧と同じ）
- 入力の誤りは 400（項目名 `title`・`body`）。管理者でなければ 404、トークンなしは 401
- 利用者側でお知らせを見る API は `/api/announcements`（`notification.md`「お知らせ」）

#### 画面（`/admin/announcements`）

- 上に発行のフォーム（題名・本文）、下に発行済みの一覧
- 題名・本文の下に文字数（例：`12 / 100`）を出す。上限を超えると赤くする
- 題名か本文が空のとき、送信中は「発行する」を押せない（連打で2回送らないように）
- 「発行する」を押すと、すぐには送らず、画面の中で確かめる（ブラウザの確認ダイアログは使わない）
  - 先に文字数を確かめ、上限を超えていれば確認を出さずに、どの欄が何文字までかを欄の下に出す
  - 確認には、発行する題名・本文と、「発行するとすぐにすべての利用者に表示される」「あとから訂正はできない。誤りがあったときは、取り消してから正しい内容で発行し直す」ことを書く
  - 確認では、最初に「戻って直す」を選んだ状態にする。「戻って直す」では送らず、入力をそのまま残す
- サーバーで弾かれた場合は、サーバーが返す理由を欄の下に出し、入力を残す
- 発行したら、一覧を読み直さずに、その場で一覧の先頭に出し、入力欄を空に戻す
- 一覧：新しい順に、題名・発行日時・発行者（発行した時点のユーザー名）・本文を出す。20件ずつで、続きは「もっと見る」
  - 本文は文字のまま出し（HTML として扱わない）、改行はそのまま表示する（CSS の `white-space: pre-wrap`）
- 一覧の取り消していないものには「取り消す」を出す。押すと、すぐには送らず、そのお知らせの中で確かめる（ブラウザの確認ダイアログは使わない）
  - 確認には、題名と、「利用者の画面から消える（「お知らせ」タブに出なくなり、未読の件数にも数えない）」「元に戻せない」「この一覧には『取り消し済み』として残る」ことを書く
  - 最初は「やめる」を選んだ状態にする。送信中はボタンを押せない（連打で2回送らないように）
  - 取り消したら、一覧を読み直さずに、その場で「取り消し済み」に変える
  - 失敗したとき（ほかの管理者が先に取り消した 409 など）は、サーバーが返す理由を出す
- 取り消したものは、薄い背景にして「取り消し済み（取り消した日時・取り消した管理者）」を出し、「取り消す」は出さない

### 4. 管理操作のログ

- 管理者の操作（データを変える操作）はすべて記録する。一覧を見るだけの操作は記録しない
- 起動時の管理者への昇格のように、人が操作していないものは「システム」の操作として記録する
- テーブル `admin_operation_logs`（エンティティ `AdminOperationLog`）。記録する項目

| 項目 | 列 | 内容 |
| --- | --- | --- |
| 操作した人 | `operator_id` | 管理者のユーザー ID。システムの操作なら NULL。**外部キーは張らない**（下記） |
| 操作した人の名前 | `operator_username` | **操作した時点の**ユーザー名。システムの操作なら「システム」（ユーザー名は半角英数字と `_` だけのため、実在するユーザー名とは重ならない） |
| 日時 | `operated_at` | 操作した日時 |
| 操作の種類 | `action` | `USER_PROMOTED_TO_ADMIN`（起動時の昇格）・`MASTER_CREATED`（マスタの追加）・`TAG_MADE_OFFICIAL`（既存の手入力のタグを公式にした）・`MASTER_DEACTIVATED`（マスタの無効化）・`MASTER_ACTIVATED`（マスタを有効に戻す）・`ANNOUNCEMENT_PUBLISHED`（お知らせの発行）・`ANNOUNCEMENT_WITHDRAWN`（お知らせの取り消し）・`REPORT_*`（通報の状態の記録・DM の表示。下記「5. 通報」）・`CONTACT_*`（お問い合わせの状態の記録。下記「7. お問い合わせ」） |
| 対象 | `target_type`・`target_id` | 対象の種類（`USER`・`FASHION_CATEGORY`・`BODY_TYPE`・`PERSONAL_COLOR`・`TAG`・`ANNOUNCEMENT`・`REPORT`・`CONTACT`）と、その ID。対象の表がいろいろなため、外部キーは張らない |
| 内容 | `detail` | 操作の中身が後から分かる短い説明（例：追加した名前、お知らせの題名）。1000文字まで |

- 操作した人の名前を、操作した時点の値として列に持つ。理由は2つ
  - 将来ユーザーを物理削除する機能を作ったとき、外部キーのせいでログが消える、または削除が失敗するのを避けるため（そのため `operator_id` にも外部キーを張らない）
  - ユーザー名が変わっても、過去のログの表示が遡って変わらないようにするため
  - 一覧を表示するときも、ユーザーの表と結合しない
- **`detail` に個人を特定する情報（メールアドレス・電話番号など）を書かない**
  - 例：起動時の昇格では、メールアドレスではなくユーザー名だけを書く
  - ログは保存期間を定めず削除もしないため、個人情報を書くと消せないまま残り続ける
- 操作の種類・対象の種類は、enum の定数名を文字列で保存する（上記 `role` と同じ理由。後の段階で種類を増やせるように）
- ログは、操作と**同じトランザクションで**記録する
  - ログを残せなかった場合は、操作も取り消す（記録のない操作が起きないようにするため）
  - 通知の作成は「失敗しても本体の処理を続ける」方針で、それとは逆だが、通知は利便性のため、ログは責任の記録のためなので、意図的に逆にしている（`notification.md`）
  - 記録の窓口 `AdminOperationLogger` は、操作のトランザクションの中でしか呼べない（外で単独で呼ぶとエラーになる）
- ログは追記だけとし、画面・API から変更・削除できないようにする
  - エンティティは保存後に変更されない作り（`@Immutable`、全列を変更不可）。リポジトリにも保存と読み込みのメソッドしか持たせない
- 接続元の IP アドレスは残さない（個人情報を増やす割に使い道がないため）
- 保存期間は定めず、古いログも削除しない
- 管理画面で、ログを新しい順に一覧できる（誰がいつ何をしたかを確かめるため）
  - API：`GET /api/admin/operation-logs?page=&size=`（新しい順。同じ日時なら ID の大きい順）。ページで区切り、`hasNext` を返す
  - `size` の上限は 50。範囲外の `page`・`size` はエラーにせず、`page` は 0 以上、`size` は 1〜50 に丸める（ホームの一覧・通知一覧と同じ）。応答の `size` は丸めた後の値
  - 1件は `{"id", "operatedAt", "operatorId", "operatorUsername", "system", "action", "targetType", "targetId", "detail"}`。一覧は `{"logs": [...], "page", "size", "hasNext"}`

#### 画面（`/admin/operation-logs`）

- 新しい順の表で、日時（秒まで）・操作した人・操作の種類・対象・内容を出す。20件ずつ「前へ」「次へ」でページを移る
- システムの操作は、操作した人の欄に「システム（自動）」の印を出し、行の色を変えて、人の操作と見分けられるようにする
- 操作の種類・対象の種類は、英語の定数名ではなく日本語で出す。対象は「種類（ID: …）」の形

| 操作の種類（`action`） | 表示 |
| --- | --- |
| `USER_PROMOTED_TO_ADMIN` | 管理者にした |
| `MASTER_CREATED` | 追加した |
| `TAG_MADE_OFFICIAL` | 手入力のタグを公式タグにした |
| `MASTER_DEACTIVATED` | 無効にした |
| `MASTER_ACTIVATED` | 有効に戻した |
| `ANNOUNCEMENT_PUBLISHED` | お知らせの発行 |
| `ANNOUNCEMENT_WITHDRAWN` | お知らせの取り消し |
| `REPORT_RESOLVED` | 通報を対応済みにした |
| `REPORT_DISMISSED` | 通報を却下した |
| `REPORT_REOPENED` | 通報を未対応に戻した |
| `REPORT_DM_VIEWED` | 通報された DM を表示した |

| 対象の種類（`target_type`） | 表示 |
| --- | --- |
| `USER` | ユーザー |
| `FASHION_CATEGORY` | ファッションの種類 |
| `BODY_TYPE` | 骨格タイプ |
| `PERSONAL_COLOR` | パーソナルカラー |
| `TAG` | タグ |
| `ANNOUNCEMENT` | お知らせ |
| `REPORT` | 通報（対象ごとのまとまり） |

- 後の段階で操作の種類・対象の種類を増やし、画面の表示名をまだ足していないときは、表示が消えないよう定数名のまま出す。種類を増やすときは、画面（`AdminOperationLogsPage.tsx`）の表示名と、この表も足すこと

> **注意：ユーザーを削除する機能を将来作るときは、管理操作のログが消えないようにすること**
>
> - ログの `operator_id` には外部キーを張っていないため、ユーザーの行を物理削除しても、ログは残り、削除も失敗しない
> - ユーザーの削除に合わせて、ログを一緒に消す処理（連鎖削除など）を足さないこと。ログは責任の記録で、操作した人が退会した後も残す必要がある
> - 操作した人の名前は `operator_username` に残っているため、削除後も「誰が操作したか」は分かる
- 後の段階（ユーザーの利用停止・投稿の削除・通報の対応など）の操作も、同じ形で記録する
  - 通報対応で DM のメッセージを確認した場合は、そのこと（見た通報・見た範囲）も記録する

### 5. 通報

利用者が投稿・ユーザー・DM のメッセージを通報し、管理者が一覧と詳細で確かめて、状態を記録する。画面画像はないため、見た目は暫定。

> **「対応済み」にしても、投稿やユーザーには何も起きない**。状態を記録するだけ。管理画面の通報の詳細の上にも、このことを書いている。
> 投稿の非公開化・利用停止は、通報の詳細の「措置」から行う（下記「6. 措置」）。

#### 通報できるもの

| 対象 | 通報する場所 | 理由 |
| --- | --- | --- |
| 投稿 | 他人の投稿の詳細画面の「…」→「通報」 | 不適切な写真・文章、他人の写真の無断転載。投稿がこのアプリの中心のため |
| ユーザー | 相手のプロフィールの⋮ →「通報」 | 名前・プロフィール画像、なりすまし、1つの投稿に限らないふるまい |
| DM のメッセージ | チャット画面で相手のメッセージを押す →「このメッセージを通報」 | 嫌がらせは DM で起きやすく、管理者はほかの方法で DM を見られないため |

- 自分自身・自分の投稿・自分のメッセージは通報できない（400）
- 当事者でない会話のメッセージ・存在しない対象は 404
- 相手にブロックされている場合は、その相手（投稿・ユーザー）を通報できない（存在しないものと同じ 404。ブロックされたことが分からないように）。自分がブロックした相手は通報できる（ブロックと通報は一緒に行われることが多いため）
- 1人が1日（24時間）にできる通報は30件まで（429）。大量の通報で証拠のコピーが溜まらないようにするため
- 他人の投稿の「…」には「通報」と「ブロック」を置く（ブロックは `profile.md`「ブロック」と同じ部品）

#### 理由

固定の選択肢とし、管理画面から増やす仕組み（マスタ）は作らない。理由は管理者の対応の方針や件数の集計と結びつくため、増やすときはコードを直す（バックエンドの `ReportReason` と、画面の `api/reports.ts` の両方）。

| 理由（定数名） | 表示 | 選べる対象 |
| --- | --- | --- |
| `SPAM` | スパム・宣伝 | すべて |
| `HARASSMENT` | 嫌がらせ・誹謗中傷 | すべて |
| `SEXUAL` | 性的な内容 | すべて |
| `VIOLENCE` | 暴力・危険な内容 | すべて |
| `PERSONAL_INFO` | 個人情報の掲載 | すべて |
| `IMPERSONATION` | なりすまし | ユーザーだけ |
| `UNAUTHORIZED_PHOTO` | 他人の写真の無断転載 | 投稿だけ |
| `OTHER` | その他 | すべて（詳しい内容が必須） |

- 詳しい内容（自由記述）は任意、500文字まで。「その他」のときは必須
- 詳しい内容は、管理者の詳細画面にだけ出す。**操作ログ・ログには書かない**（通報した人が個人の情報を書くことがあるため）

#### 通報した後に起きること

- 通報された人には何も伝えない（通知を作らない）。誰が通報したかも、通報されたことも分からない
- 管理者には、通報した人のユーザー名を見せる（虚偽の通報・仕返しの通報に気づけるように）
- 自動ではブロックしない。通報とブロックは別の操作。通報の完了の画面で「@◯◯ さんをブロックする」を案内する（押すとブロックの確認を出す）
  - 自動でブロックしないのは、関係を切らずに通報したい場合（写真の無断転載など）もあり、勝手にブロックされると驚くため

#### 同じ対象への通報

- 対象ごとにまとめる（テーブル `report_cases`）。未対応の間は、同じ対象への通報は1つのまとまりに加わる（テーブル `reports` に1人1行）
- 同じ人が同じ対象をもう一度通報しても、1件のまま（200 で「すでに通報済みです」と出す）
- 対応を終えた（対応済み・却下）後に同じ対象が通報されたら、新しいまとまりを作り、証拠もコピーし直す（管理者が改めて確かめられるように）

#### 証拠（通報した時点の内容のコピー）

投稿は「本当に消す」設計のため（`post.md`「投稿の削除」）、通報された投稿を利用者が消すと、そのままでは管理者は何も見られなくなる。そのため、**最初の通報のときに内容をコピーする**。

| 対象 | コピーするもの |
| --- | --- |
| 投稿 | 題名・ファッションの種類・タグ・着用アイテム・投稿説明・参考情報・投稿者のユーザー名・投稿日時と、写真すべて |
| ユーザー | ユーザー名・表示名と、プロフィール画像 |
| DM | 通報したメッセージと前後5件ずつ（本文・送った人・送った日時）と、その中の画像 |

- 文字は JSON で `report_cases.evidence_json` に、写真は証拠の保存先に複製して、そのファイル名を `report_evidence_files` に記録する
- 写真は、すでに `prepare()` を通して保存されているファイルを、中身を変えずに複製する（`prepare()` を再度通さない理由は `CLAUDE.md`）
- 同じ対象のまとまりに後から加わった通報では、コピーし直さない（最初の通報の時点のまま）
- 管理者の詳細画面では、対象の今の状態（今もある・通報の後に編集された・削除された）も出す
- 考えた案と、採らなかった理由
  - ID だけを持つ：投稿を消すと証拠が消え、消せば逃げられる。編集で内容も変わる
  - 文字だけをコピーする：このアプリでは写真そのものが問題になることが多い
  - 通報された投稿を消せなくする：投稿を「本当に消す」設計を崩し、「消す予定」の条件をあちこちに書くことになる（ブロック・投稿の削除で避けた、書き忘れの問題）

#### 証拠の写真の配信（重要）

- **証拠の写真は `/uploads/**` では配信しない**。公開の画像のフォルダ（`app.image.local.dir`）とは別のフォルダ（`app.evidence.local.dir`、既定は `backend/evidence/`）に置き、このフォルダを配信する設定は作らない
  - 2つのフォルダが重なる（片方がもう片方の中にある）設定では、サーバーが起動しない（重なると `/uploads/**` から取得できてしまうため）
  - ファイル名は、元の写真とは別の推測できない乱数の名前にする
- 配信は管理者向けの API（`GET /api/admin/reports/{id}/evidence-files/{fileId}`）だけが行う。管理者であることをサーバーで確かめてから中身を返す
  - ログインしていない人は 401、一般の利用者（通報した人・された人も）は 404
  - 別の通報の写真を、ID の組み合わせで取ることはできない（404）
  - ブラウザ・途中のサーバーに残さないよう、キャッシュさせない（`Cache-Control: no-store`）
- 管理画面では、`<img>` のタグに認証のヘッダーを付けられないため、API から中身を取得して一時的な URL（`URL.createObjectURL`）にして表示する
- 利用者が投稿を削除した後も、証拠の写真は一般の経路（`/uploads/**`）からは取得できず、管理者だけが見られることをテスト（`EvidenceAccessTest`）で確かめている
- 公開時にクラウドストレージにする場合は、証拠は**公開しない（非公開の）**入れ物に置く（`EvidenceStorage` の実装を差し替える）

#### 証拠の保存期間（対応を終えてから180日）

- 対応を終えた（対応済み・却下にした）日時から**180日**を過ぎたら、証拠（文字のコピー・写真のファイル・一覧の要約）を消す。未対応の通報の証拠は消さない
  - 通報の行（理由・状態・日時）と、まとまりの状態は残す（管理者の詳細では「証拠は削除しました」と出す）
  - 消した後は、未対応に戻せない（409）
- **180日の理由**
  - 決定を見直す余地を残すため：対応の後に、通報した人・された人から問い合わせがあったり、同じ相手の別の通報で過去の判断を見直したりすることがある。そのとき、元の内容を確かめられる必要がある
  - 消した内容を持ち続けないため：利用者が削除した投稿を、運営がいつまでも持ち続けることは、投稿を「本当に消す」方針（`post.md`）と相いれない。期間を区切って消す
  - 180日（約半年）は、この2つの間を取った値。通報の件数・問い合わせの実態を見て見直す（下記「未確定・要確認」）
- 消す処理（`EvidencePurger`）は、毎日 3:00 に定期実行（`EvidencePurgeJob`。設定 `app.report.evidence-purge-cron`）。このアプリで最初の定期実行
  - 今の時刻は `Clock` から読む（テストで差し替えられる）。テストでは、180日を1分過ぎたものは消え、1分前のものは残ることを確かめている
  - **消すのは、`report_evidence_files` に記録した正確なファイル名だけ**。パターン・ワイルドカード・フォルダの一覧から探して消す処理は使わない（名前の形も確かめ、フォルダの外は指せない）
  - 失敗したとき
    - ファイルを消せなかったら、そのファイルの記録を残し、そのまとまりは「消した」にしない（文字のコピーも残す）。翌日の実行で消し直す
    - 警告のログに、まとまりの ID とファイル名を残す（内容・ユーザー名は書かない）
    - 1つのまとまりの失敗で、ほかのまとまりを止めない（まとまりごとに別のトランザクション）
    - ファイルを先に消し、DB の記録は後で消す。DB の更新に失敗しても、翌日にファイルを消し直し（存在しなければ何もしない）、記録も消える
    - 予期しない失敗でも定期実行そのものは止めず、エラーのログに残す
  - 実行のたびに、対象の件数・消した件数・消せなかったファイルの件数を情報のログに残す
  - サーバーを複数台で動かす場合は、同じ処理が同時に動く（行をロックしてから消すため壊れはしない）。そのときは1台だけで動かす仕組み（ShedLock など）を検討する

#### DM の範囲（前後5件ずつ）

- 管理者が見られるのは、**通報されたメッセージと、その前後5件ずつ（最大11件）だけ**（上記「方針」の「通報されたメッセージとその前後だけ」の件数を決めた）
  - 嫌がらせかどうかは、たいてい数往復のやり取り（何に対して送られたか・相手がどう返したか）で判断できる
  - 5件ずつは、スマホのチャット画面でおおよそ1画面分。それより多いと「会話を読む」ことになり、方針に反する
  - 時刻ではなく件数で区切る（短い時間にたくさん送られても範囲が広がらない）
- 範囲は通報した時点で決め、通報の後に送られたメッセージは含めない。「もっと見る」は作らない
- 管理者の詳細では、11件のうち**通報されたメッセージを枠と「通報されたメッセージ」の文字で示す**
- 一覧には DM の本文を出さない（「@◯◯ のメッセージ」とだけ出す）。詳細を開いたときだけ出し、**開いたことを操作ログに残す**（`REPORT_DM_VIEWED`。ログを残せなければ中身も返さない）

#### 管理画面（`/admin/reports`）

- 左の行き先に「通報」を足した
- 一覧：対象ごとに1行。状態・対象の種類・内容（投稿の題名・「@ユーザー名」・「@ユーザー名 のメッセージ」）・通報の数・理由の内訳・最新の通報の日時
  - 既定は未対応だけを、新しく通報された順に出す。状態・対象の種類で絞れる。20件ずつ「もっと見る」
- 詳細（`/admin/reports/{id}`）
  - 上に「対応済みにしても措置は行われない。措置は下の『措置』から行う」ことを書く
  - 措置（投稿の非公開化・利用停止。下記「6. 措置」）
  - 状態（対応した管理者・終えた日時）、対象の種類と ID、通報の数、今の状態
  - 証拠（文字は HTML として扱わず、改行はそのまま出す。写真は管理者向けの API から取得）
  - 通報した人・理由・詳しい内容・日時
  - 状態の記録：未対応なら「対応済みにする」「却下する」、終えていれば「未対応に戻す」。メモ（任意、1000文字まで）を一緒に記録できる
- 状態

| 状態（定数名） | 表示 | 意味 |
| --- | --- | --- |
| `OPEN` | 未対応 | まだ確かめていない |
| `RESOLVED` | 対応済み | 確かめて対応した（措置は「措置」から。措置のときに一緒に対応済みにもできる） |
| `DISMISSED` | 却下 | 問題がないと判断した |

- すでにその状態にする・同じ対象に新しい未対応の通報があるのに古い通報を未対応に戻す・証拠を消した後に未対応に戻す、は 409
- メモは管理者にだけ見せる。**操作ログには書かない**（ログの内容は「状態：対応済み」のように状態だけ）

#### 管理操作のログ

| 操作の種類（`action`） | 表示 | 内容（`detail`） |
| --- | --- | --- |
| `REPORT_RESOLVED` | 通報を対応済みにした | 状態だけ |
| `REPORT_DISMISSED` | 通報を却下した | 状態だけ |
| `REPORT_REOPENED` | 通報を未対応に戻した | 状態だけ |
| `REPORT_DM_VIEWED` | 通報された DM を表示した | 表示した件数だけ（本文・ユーザー名は書かない） |

- 対象の種類は `REPORT`（ID はまとまりの ID）
- DM を見たことは、データを変えないが記録する（上記「方針」）。ほかの通報の詳細を見ただけでは記録しない

#### テーブル

| テーブル | 内容 |
| --- | --- |
| `report_cases` | 対象ごとのまとまり。対象の種類・ID、通報された人の ID、状態、通報の数、最初・最新の通報日時、一覧の要約、証拠の文字（JSON）、証拠を消した日時、対応を終えた日時、対応した管理者（ID と、その時点のユーザー名）、メモ |
| `reports` | 1人分の通報。まとまり・通報した人・理由・詳しい内容・日時。同じまとまりに同じ人は1行まで |
| `report_evidence_files` | 証拠の写真。まとまり・表示順・ファイル名・MIME タイプ・（DM の画像なら）メッセージの ID |

- 同じ対象の未対応のまとまりは1つまで（`open` 列と一意制約。フォローの `active` と同じ作り）
- 対象・通報された人・対応した管理者には外部キーを張らない（対象が消えても、証拠と記録を残すため）

#### API

| API | 内容 |
| --- | --- |
| `POST /api/reports` | 通報する。本文 `{"targetType", "targetId", "reason", "comment"}`。新しく受け付けたら 201（`ACCEPTED`）、すでに通報済みなら 200（`ALREADY_REPORTED`） |
| `GET /api/admin/reports?status=&targetType=&page=&size=` | 一覧（管理者だけ） |
| `GET /api/admin/reports/{id}` | 詳細（管理者だけ。DM は見たことをログに残す） |
| `POST /api/admin/reports/{id}/status` | 状態の記録（管理者だけ）。本文 `{"status", "memo"}` |
| `GET /api/admin/reports/{id}/evidence-files/{fileId}` | 証拠の写真の中身（管理者だけ） |

- 通報の API は、ブロックの API の棚卸し（`VisibilityInventoryTest`）にも登録している

### 6. 措置

管理者が投稿を非公開にし、ユーザーを利用停止にする。通報の詳細の「措置」か、措置の画面（`/admin/moderation`）から行う。画面画像はないため、見た目は暫定。

#### 決めたこと

1. 投稿は**非公開にするだけ**。管理者による削除は作らない（下記「未確定・要確認」）
2. 利用停止中のユーザーは、ほかの人からは**存在しないユーザーと同じ**（404。一覧・件数からも除く）
3. 申請中・進行中の相談は、利用停止にしたときに**終了する**
4. 利用停止の期限は、ジョブで解除せず、**使うたびに今の時刻と比べる**（下記「期限の扱い」）
5. 運営からの通知は「誰が」を空にする（`notifications.actor_id` を NULL にできるようにした）
6. 利用停止の画面から、本人が申し立てられる（下記「7. お問い合わせ」、`settings.md`「利用停止中の申し立て」）

ほかは今までの方針のまま。

- 措置の API は `/api/admin/**` に置き、権限はサーバー側で確かめる（`AdminAccess.requireAdmin`）
- すべての措置は、同じトランザクションで操作ログに残す（残せなければ措置も取り消す）。ログに個人を特定する情報を書かない
- 管理者は、利用者向けの API（`/api/posts/**`）からは他人の投稿を編集・削除できないまま。措置は管理者向けの API からだけ行う

#### 投稿の非公開化

- ほかの人からは、存在しない投稿と同じになる
  - ホーム・プロフィール・検索・お気に入りの一覧と件数から除く。詳細・いいね・お気に入り・通報は 404
- 投稿者本人には見える。詳細の上に「この投稿は運営により非公開になっています」と理由を出す（`post.md`）
- 投稿者に通知が届く（非公開にした・公開に戻した。`notification.md`）
- いいね・お気に入りの行は消さない（公開に戻すと、そのまま戻る）
- 理由は通報の理由から選ぶ（投稿に使えない「なりすまし」は選べない）。すでに非公開・公開中のものを公開に戻す、は 409

> **非公開にしても、投稿の内容と写真はサーバーに残る**。投稿者本人はまだ見られる。
> また、写真の URL を知っている人は、非公開にした後も写真を開ける（下記「既知の限界」）。
> 第三者の個人情報（無断で撮られた写真・住所など）が含まれる投稿で、非公開にするだけで足りるかは、
> 管理者による削除とあわせて今後決める（下記「未確定・要確認」）。

#### 既知の限界：非公開にした投稿の写真は、URL を知っていれば見られる

- 投稿の写真は `/uploads/**` から認証なしで配信している。非公開にしても写真のファイルは同じ場所に残るため、写真の URL を知っている人（非公開にする前に開いていた人・URL を控えていた人）は、非公開にした後も写真を開ける
- ファッションのアプリでは、問題になるのは写真そのもの（無断で撮られた写真・他人の写真の転載など）であることが多い。そのため、**このままでは非公開化の効き目が半分になる**
- 直し方の案（上記「後の段階で作るもの」に残した）
  - 通報の証拠のために作った「公開されない場所に置く仕組み」（`EvidenceStorage`。`/uploads/**` では配信せず、認証つきの API からだけ返す。上記「5. 通報」）を使う
  - 非公開にしたら、写真をそちらへ移す（元の URL では開けなくなる）。公開に戻したら、元の場所へ戻す
  - 投稿者本人には、認証つきの API から写真を返す
  - 移すのは、すでに `prepare()` を通して保存されたファイルをそのまま動かすだけのため、`prepare()` は通さない（CLAUDE.md の注記と同じ扱い）
  - ブラウザや CDN に残ったキャッシュまでは消せない

#### 利用停止

- 期間は 1日・3日・7日・30日・無期限から選ぶ（画面の既定は1日）。管理者（自分自身を含む）は利用停止にできない（409）。すでに利用停止中も 409
- 利用停止にすると
  - **すべての API が 403** になる（本文の `reason` は `ACCOUNT_SUSPENDED`。理由と期限と、申し立て用の鍵 `appealToken` も返す。`settings.md`「利用停止中の申し立て」）
    - トークンを確かめた直後の1か所（`SuspendedUserFilter`）で止めるため、API ごとに確かめを書く必要はない
    - トークンは失効させないが、リクエストのたびに DB のユーザーを読むため、ログイン中の端末もすぐ使えなくなる
    - ログインは、パスワードが正しいときだけ 403 を返す（違えば今までどおり 401。他人が利用停止中かどうかを探れないように）
  - 画面は、どの画面にいてもログアウトして、利用停止の画面（`/suspended`）に移る。理由・期限（無期限なら「無期限」）・「利用停止について問い合わせる」（申し立て）を出す
  - ほかの人からは、存在しないユーザーと同じになる。プロフィールは 404、その人の投稿・フォロー一覧・検索・その人からの通知も出さない（件数も同じ）
  - 申請中・進行中の相談は終了する（終了した人は記録しない）。過去のメッセージは今までの終了と同じく両方から読める（`dm.md`）
  - フォロー・いいね・お気に入り・通知の行は消さない（解除すると、そのまま戻る）
- 解除するとすぐ使えるようになる。ただし、**利用停止のときに終了した相談は戻らない**
  - 戻すと、利用停止の間に相手が受けた相談と合わせて、相手の受付の上限を超えることがあるため。必要なら、もう一度申し込んでもらう
- 本人への通知は送らない（使えない間に届いても見られないため）。次に使おうとしたときに、利用停止の画面で伝える

#### 期限の扱い（ジョブを作らない理由）

- 期限を過ぎたら解除するジョブは作らない。**見えるかどうかを決めるたびに、今の時刻と期限を比べる**。そのため、期限を過ぎたその時点から使える（ずれはない）
- 一覧・件数の SQL（`VisibilityConditions`）にはアプリの今の時刻（`:now`）を渡して比べる。DB の現在時刻（`CURRENT_TIMESTAMP`）は使わない
  - DB の時刻は UTC、アプリが保存する日時は日本時間のため、DB の現在時刻と比べると9時間ずれる
  - 今の時刻はアプリの `Clock` から渡す（テストで差し替えられる）
  - `:now` を渡し忘れると、Spring Data が起動時に失敗する（`@Query` の引数が足りないため）。渡し忘れは起動・テストで分かる
- 期限を過ぎた利用停止の行（`suspended_at` など）は、そのまま残る。管理画面の一覧・状態は、期限を過ぎたものを利用停止中として扱わない（解除の操作は 409、もう一度利用停止にはできる）

#### 時刻の扱い（重要：DB の現在時刻に置き換えないこと）

- このアプリは、日時を**日本時間**で保存している（アプリの `Clock` の時刻をそのまま保存する）
- 一方、DB（PostgreSQL）は**UTC** として扱う。そのため、DB の現在時刻（`now()`・`CURRENT_TIMESTAMP` など）と保存した日時を比べると、**9時間ずれる**
  - 例：期限が日本時間の 10:00 の利用停止は、DB の現在時刻で比べると、日本時間の 19:00 まで解けない
- そのため、見えるかどうかを判定する SQL（`VisibilityConditions` を使うすべての SQL）には、**アプリの今の時刻を `:now` として渡している**
- **`:now` を DB の現在時刻に置き換えてはいけない**
  - `:now` を引数で渡すのは冗長に見えるが、置き換えても、コンパイルは通り、エラーも出ないまま、期限の判定だけが静かに9時間ずれる（テストの DB は H2 で、PostgreSQL と時刻の扱いが同じとは限らないため、テストで気づけるとも限らない）
  - また、`:now` で渡すことで、テストで時刻を固定できる
- 新しく時刻と比べる SQL を書くときも、同じくアプリの時刻を引数で渡すこと（`profile.md` の「日時の扱い」も参照）

#### 見えなくする条件（`VisibilityConditions`）

- ブロックの共通の条件（`BlockConditions`）を `VisibilityConditions` に改名し、ブロック・利用停止・非公開の条件を1か所にまとめた（`profile.md`「ブロック」）
  - 一覧・件数の SQL は `POST_VISIBLE`・`USER_VISIBLE` を使う。1人・1件を対象にする API は `UserVisibility` を通す
  - 他人の投稿一覧と投稿数が共通の条件を使っていなかったため、あわせて直した（プロフィールの投稿一覧と件数も `POST_VISIBLE` を使う）
- 棚卸しのテスト（`VisibilityInventoryTest`）に、次を足した
  - 非公開の投稿・利用停止中のユーザーが、登録したどの API からも漏れないこと
  - 利用停止中のトークンで、登録したすべての API が 403 になること（ログイン・新規会員登録・ヘルスチェック・申し立て（`POST /api/contacts/appeal`）を除く。申し立てはトークンを付けずに送る）

#### 通報との結びつき

- 通報の詳細に「措置」を出す
  - 投稿の通報：投稿の非公開化（投稿が残っている場合）と、投稿者の利用停止
  - ユーザー・DM のメッセージの通報：通報された人の利用停止
- 措置にその通報を結びつける（措置の履歴に通報の ID が残る）。別の対象の通報を結びつけようとすると 400 で、措置もしない
- 「この通報を『対応済み』にする」を選ぶと、同じトランザクションで通報を対応済みにする（操作ログに `REPORT_RESOLVED` も残る）。選ばなければ未対応のまま
- 非公開の投稿・利用停止中のユーザーは、ほかの人から新しく通報できない（存在しないものと同じ 404）。DM のメッセージは、今までどおり会話の当事者なら通報できる

### 7. お問い合わせ

利用者が送ったお問い合わせ（利用停止中の申し立てを含む）を、管理者が見て、状態を記録する。受付の仕様（入力項目・申し立て用の鍵・回数の上限・返信をしないこと）は `settings.md`「お問い合わせ」。画面画像はないため、見た目は暫定（通報の画面と同じ作り）。

#### 詳細を見たことはログに残さない（DM と違う理由）

- 通報された DM は、見たことを操作ログに残している（`REPORT_DM_VIEWED`）。お問い合わせの詳細は、**見ても残さない**
- 理由：DM は**当事者同士のもの**で、運営に宛てたものではない。管理者が読むこと自体が例外的な行為のため、読んだことを記録する必要がある
- お問い合わせは、**本人が運営に宛てて送ったもの**で、管理者が読むこと自体が目的。読むたびに記録しても、責任の記録としての意味がない
- **「DM とそろっていない」と考えて、記録を足さないこと**（データを変える操作（状態の記録）は、ほかの管理操作と同じく記録する）
