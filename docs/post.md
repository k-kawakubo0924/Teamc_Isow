## 仕様

### 投稿時の入力内容

| 項目 | 必須 | 補足 |
| --- | --- | --- |
| 写真 | 必須 | 1枚以上10枚以下 |
| 題名 | 必須 | |
| ファッションの種類 | 必須 | 別のページに移動して、あらかじめ登録してあるファッションの種類を選択する。1投稿につき1つ |
| タグ | 必須 | 別のページに移動して選択する点は同じ。違うところは手入力で設定できるところがある点 |
| 着用アイテム | 任意 | 自由記述のテキスト（複数行可） |
| 投稿説明 | 必須 | |
| 参考情報 | 任意 | どこのサイトで売っているかを乗せることができる。URLを1つ設定する |

### 文字数の上限（暫定）

チームで正式な値を決めるまでの**暫定値**。決まったら更新する。

| 項目 | 上限（暫定） |
| --- | --- |
| 題名 | 100文字 |
| 着用アイテム | 1000文字 |
| 投稿説明 | 2000文字 |
| 参考情報のURL | 2048文字 |
| タグの数 | 1投稿につき10個まで |
| タグの文字数 | 1つあたり30文字以内 |

### 投稿の流れ

```
入力画面 ──「確認」──▶ 確認画面 ──「投稿する」──▶ 投稿の詳細画面（投稿した投稿）
```

| 画面 | 画像 | ボタン |
| --- | --- | --- |
| 入力画面 | `design/Post Creation Screen.png` | 「確認」：入力チェックを行い、問題がなければ確認画面へ |
| 確認画面 | `design/Check post content.png` | 「戻る」：入力内容を保ったまま入力画面へ／「投稿する」：投稿を登録し、その投稿の詳細画面へ |

- 画面画像の「下書き保存」は、下書きの仕様が未確定のため置かない（確認画面では代わりに「戻る」を置く）
- 投稿したら、その投稿の詳細画面へ移る。ブラウザの「戻る」で送信済みの入力画面に戻らないよう、履歴を置き換える
- 投稿に失敗した場合
  - 入力内容の誤り・写真のサイズ超過：入力画面に戻し、上部と該当する欄に警告文を出す
  - 接続できない・サーバーのエラー：直す項目がないため、確認画面のまま上部に警告文を出し、もう一度「投稿する」を押せるようにする

> **完了画面を削除した（記録）**：投稿の詳細画面ができるまでの暫定として、投稿後に「完了画面」を表示していた
> （投稿した内容の要約と「続けて投稿する」「ホームへ」のボタン。画面画像はなかった）。
> 詳細画面ができたため、完了画面は削除し、投稿後は投稿した投稿の詳細画面へ移る形にした。
> 「続けて投稿する」ボタンは詳細画面には置かない（続けて投稿する場合は、下部ナビゲーションの「投稿」から）。

### 投稿の詳細画面（/posts/{id}）

詳細画面の画面画像はないため、項目の並びは確認画面（`design/Check post content.png`）に合わせている（暫定の見た目）。

- 開き方
  - 投稿のカードの写真を押す（ホーム・プロフィールの投稿一覧とお気に入り・検索結果。1列・2列・3列のどれでも）
  - いいねの通知を押す（`notification.md`）
  - 投稿した直後（上記「投稿の流れ」）
- 表示する項目（上から順に）

| 項目 | 補足 |
| --- | --- |
| 写真 | 1枚ずつ表示し、2枚以上なら「1 / 3」の枚数と ‹ › のボタンで切り替える。1枚のときは枚数表示もボタンも出さない（確認画面と同じ部品 `PostPhotoViewer`） |
| 投稿者 | アイコン・@ユーザー名・身長。押すと投稿者のプロフィールへ。身長は任意の項目のため、未設定なら身長の部分そのものを出さない（「nullcm」などと出さない。ホームの一覧・プロフィールも同じ） |
| いいね・お気に入り | ボタン。いいねは件数つき。ホームの一覧と同じく、その場で押せる（自分の投稿にも押せる） |
| 題名 | |
| ファッション | ファッションの種類 |
| タグ | チップで並べる。ID 順（下記「未確定・要確認」参照） |
| 着用アイテム | 未入力なら行ごと出さない。改行はそのまま表示する |
| 投稿説明 | 改行はそのまま表示する |
| 参考情報 | 未入力なら行ごと出さない。http・https の URL だけリンクにし、別タブで開く（`rel="noopener noreferrer nofollow"`） |
| 投稿日 | 「2026年10月8日」の形。投稿者が編集した投稿は、横に「編集済み」を出す（下記「投稿の編集」） |

- 改行は CSS（`white-space: pre-wrap`）で表示する（`dangerouslySetInnerHTML` は使わない）
- 自分の投稿にだけ、見出しの右に「…」のメニュー（「編集」「削除」の順）を出す（下記「投稿の編集」「投稿の削除」）。それ以外の表示は自分の投稿と他人の投稿で変えない。
  フォローボタンは置かない（投稿者の行からプロフィールへ移ってフォローする）
- 投稿が見つからない場合（削除された・ID が正しくない）は「投稿が見つかりません」と「ホームへ」を表示する
  - ID が数字でない場合は API を呼ばずに同じ表示にする。通信の失敗は「もう一度読み込む」を出して区別する
- API：`GET /api/posts/{id}`（投稿の作成・自分の投稿一覧と同じ形 `PostResponse`）
  - 存在しない投稿は 404（「投稿が見つかりません。」）。数字でない ID も 404
  - 投稿者（`author`）は `id`・`username`・`profileImageUrl`・`heightCm`（未設定は null）
  - `ownedByMe`：ログイン中のユーザーの投稿か。画面で編集・削除のメニューを出すかの判断だけに使う（編集・削除できるかはサーバーが確かめる）
  - `editedAt`：投稿者が最後に編集した日時。編集していなければ null（「編集済み」の表示に使う）
  - 写真の枚数・タグの数に関係なく、SQL は7本で一定（ログイン確認1、投稿・投稿者・ファッションの種類1、写真1、タグ1、いいね・お気に入り3）。
    写真とタグは一緒に読み込まない（両方をまとめると「写真の枚数 × タグの数」の行が返るため）

### 投稿の編集

自分の投稿の**文字の情報だけ**を編集できる。**写真は編集できない**。編集の画面画像はないため、投稿作成の画面に合わせている（暫定の見た目）。

#### 編集できる項目

| 項目 | 編集 | 補足 |
| --- | --- | --- |
| 写真 | できない | 追加・削除・並べ替えのどれもできない（下記「写真を編集できない理由」） |
| 題名・投稿説明・着用アイテム・参考情報 | できる | 入力チェック・文字数の上限は投稿の作成と同じ |
| ファッションの種類 | できる | 選び直せる。設定済みのものが無効にされていても、そのまま保存できる（下記「無効にされた選択肢」） |
| タグ | できる | 付け外し・手入力の追加ができる。規則は投稿の作成と同じ（1〜10個、1つ30文字以内、表記ゆれは同じタグ）。設定済みのタグは無効にされていても残せる |

- いいね・お気に入り・投稿日時は変わらない。編集しても通知は作らない
- 外したタグ（手入力のタグも）は、投稿から外れるだけで、タグそのものは残る（投稿の削除と同じ）
- タグの並び順は今までどおり ID 順（付けた順は保存していない）

#### 写真を編集できない理由

- いいね・お気に入りを押した後に、写真が別のものに変わらないようにするため（既存のアプリも同じ作り）。ほかの人のお気に入り一覧・いいねの通知・検索結果のサムネイルも、後から別の写真に変わってしまう
- 写真を変えられるようにすると、どの写真を残すか・並び順をどう送るか・外した写真のファイルをいつ消すか（投稿の削除と同じく、コミットの後に消す必要がある）を決めて作る必要があり、作業量が大きい
- **写真の写り込みなどを直したいときは、投稿を削除して投稿し直す。その場合、いいね・お気に入りは失われる**（引き継ぐ方法はない）
  - 編集画面の写真の下にも、このことを書いている
  - 写真の削除だけをできるようにする案は「未確定・要確認」

#### 画面（`/posts/{id}/edit`）

```
投稿の詳細画面「…」→「編集」──▶ 入力画面 ──「確認」──▶ 確認画面 ──「保存する」──▶ 投稿の詳細画面
```

- 投稿の詳細画面の「…」メニュー（自分の投稿のときだけ）の「編集」から開く。「削除」の上に置く
- 投稿作成と同じ画面・部品（`PostPage`・`PostConfirm`）を使う。違いは次のとおり
  - 見出しは「投稿の編集」、確認画面は「編集内容の確認」、ボタンは「保存する」
  - 入力欄には投稿の今の内容が入っている
  - 写真は表示するだけ（`PostPhotoViewer`）。写真の下に「写真は変更できません。写真を変えたいときは、この投稿を削除して投稿し直してください（いいねは引き継がれません）。」と書く
- **編集でも確認画面を挟む**
  - 投稿作成と同じ流れにして部品を使い回しているが、誤字を1文字直すだけでも確認を通ることになる。煩わしければ後で見直す余地がある
- 保存したら、その投稿の詳細画面へ移る。「戻る」で送信済みの入力画面に戻らないよう、履歴を置き換える
- 失敗した場合は投稿の作成と同じ（入力の誤りは入力画面に戻して該当する欄に、それ以外は確認画面のまま上部に出す）
- 他人の投稿・存在しない投稿の `/posts/{id}/edit` を開いた場合は、入力欄を出さずに「この投稿は編集できません」「投稿が見つかりません」を出す（表示を分けるだけで、守りはサーバーで行う）
- 編集の途中で画面を離れても、確かめずに入力を捨てる（投稿作成と同じ）

#### 無効にされた選択肢（`admin.md` の宿題の決定）

**設定済みのものは、無効にされていてもそのまま保存できる**（プロフィールの編集と同じ）。

- 無効化は「これから選べなくする」操作で、過去をなかったことにする操作ではないため（`admin.md`「無効化の意味」）。
  選び直させると、題名の誤字を直すだけでもファッションの種類やタグを変えなければならなくなる
- ファッションの種類
  - 設定済みのものは、無効でもそのまま保存できる。それ以外に変える場合は、有効なものだけを選べる
  - 画面：設定済みの種類が選択肢にない（無効にされた）場合は、選択肢の末尾に「（現在は選べません）」と添えて出す
- タグ
  - 設定済みのタグは、無効でも残せる（表記ゆれで送っても同じタグとして残る）
  - 新しく付けるタグは投稿の作成と同じ。無効なタグは、手入力でも付けられない
  - 保存した後に外した無効なタグは、もう付け直せない
- **「すでに設定されているか」は、クライアントから送られた値ではなく、DB から読んだ投稿の値で判定する**
  - クライアントの値で判定すると、無効にしたタグ・種類を、それが付いていないどの投稿にも付けられてしまうため
  - ほかの投稿に付いている無効なタグも、この投稿に付いていなければ付けられない

#### 「編集済み」の表示

- 投稿者が編集した投稿は、詳細画面の投稿日の横に「編集済み」を出す。一覧のカードには出さない
- いつ・何を変えたかの履歴は持たない（編集前の内容は残らない）
- 編集した日時は、新しく足した列 `posts.edited_at` に入れる（編集していなければ NULL）
  - **`updated_at` を使わない理由**
    - タグだけを変えた編集では、投稿の行そのものは更新されないため、`updated_at` を入れる仕組み（`@PreUpdate`）が動かない
    - 将来、投稿者の編集以外（管理者の操作など）でも `updated_at` は変わりうる。そのたびに「編集済み」が出てしまう
  - 列を足しただけのため、既存の投稿は NULL（編集していない）になる。DB を作り直す必要はない

#### API

`PUT /api/posts/{id}`（JSON。成功は 200 で、編集した後の投稿 `PostResponse` を返す）

```json
{ "title": "…", "fashionCategoryId": 1, "tags": ["古着", "冬コーデ"], "wornItems": "…", "description": "…", "referenceUrl": "…" }
```

- 写真は受け取らない（写真の項目を送っても無視する）
- 入力チェック・文字の整え方（前後の空白を除く・改行を `\n` にそろえる・任意の項目は空なら未設定）は投稿の作成と同じ

| 応答 | 場合 |
| --- | --- |
| 200 | 編集した |
| 400（項目名は作成と同じ） | 入力の誤り。無効な選択肢（設定済みのものを除く）を含む |
| 403（「この投稿は編集できません。」） | 他人の投稿（何も変えない） |
| 404（「投稿が見つかりません。」） | 存在しない、または削除された |
| 401 | ログインしていない |

- 他人の投稿に 403 を返す理由は、投稿の削除と同じ（投稿はもともと誰でも見られるため、404 で隠しても得るものがない）
- 他人の投稿を編集できないことは、サーバーで確かめる（1つのトランザクションの中で、投稿を読み、投稿者とトークンのユーザーを比べてから書き換える）。メニューを出さないのは表示の都合だけ。
  管理者も、この API で他人の投稿は編集できない
- 同じ投稿を2つの画面で編集した場合は、後から保存した方が残る（投稿者本人しか編集できないため、版の確認はしない）
- SQL の本数は、タグを変えなければタグの数に関係なく一定（タグ1個と10個で同じ）。
  タグを付け外しした場合は、付け外ししたタグの数だけ `post_tags` の追加・削除が出る（投稿の作成と同じ）

### 投稿の削除

自分の投稿だけを削除できる。削除の画面画像はないため、見た目は暫定。

- 本当に削除する（「削除したこと」にして行を残す方式にはしない）
  - 自分の写真を載せるアプリのため、利用者が削除したものをこちらで持ち続けない
  - 行を残す方式では、一覧・検索・プロフィール・お気に入り・件数・通知のすべての SQL に「削除済みを除く」条件が要り、
    1か所でも漏れると削除した投稿が見えてしまう
  - 元に戻すことはできない。通報の仕組みができたときに、通報された投稿をどこまで残すかは別に決める
- 画面
  - 投稿の詳細画面の見出しの右に「…」のボタンを出し、押すと「削除」を選べる（自分の投稿のときだけ。同じメニューの「削除」の上に「編集」がある）
  - 「削除」を押すと、画面の中に確認を出す（ブラウザの確認ダイアログは使わない）
    - 「この投稿を削除しますか？」「写真・いいね・お気に入りも削除され、元に戻せません。」と「キャンセル」「削除する」
    - 通信中は「削除しています...」にし、どちらのボタンも押せなくする
  - 削除できたら、自分のプロフィール（`/profile`）へ移る。履歴を置き換えるため、「戻る」で削除した投稿には戻らない
  - 失敗したら、確認の中にエラーを出して画面に留まる。すでに削除されていた（404）場合は、削除できたものとしてプロフィールへ移る
- API：`DELETE /api/posts/{id}`（成功は 204、本文なし）

| 応答 | 場合 |
| --- | --- |
| 204 | 削除した |
| 403（「この投稿は削除できません。」） | 他人の投稿（何も削除しない） |
| 404（「投稿が見つかりません。」） | 存在しない、またはすでに削除された。数字でない ID も 404 |
| 401 | ログインしていない |

- **他人の投稿に 403 を返す理由（404 に直さないこと）**：
  会話・通知・管理画面では、他人のもの（管理画面では、管理者でない人にとっての管理画面そのもの）の存在を漏らさないために 404 を返している。
  しかし投稿はもともとログインしていれば誰でも見られるため、404 で隠しても得るものがない。
  そのため、削除の権限がないことを素直に 403 で返す。ほかの場所と方針が違うのは意図したもの
- 他人の投稿を消せないことは、サーバーで確かめる（投稿者とトークンのユーザーを比べる）。メニューを出さないのは表示の都合だけで、守りにはしない。
  管理者も、この API で他人の投稿は削除できない（管理者による削除が必要になったら `/api/admin/**` に別に作る）
- 一緒に消えるもの・残るもの

| 対象 | 扱い |
| --- | --- |
| 写真（`post_images`）・タグとのつながり（`post_tags`） | 一緒に削除する（JPA が投稿と一緒に削除する） |
| いいね・お気に入り・いいねの通知 | 一緒に削除する（DB の外部キーの `ON DELETE CASCADE`）。ほかの人のお気に入り一覧からも消え、通知の未読の件数も減る |
| タグ（`tags`） | 残す。手入力のタグは、使う投稿がなくなっても残る（使われていないタグの整理は、手入力のタグを無効にする仕組みとあわせて考える。`admin.md`） |

- 削除の後に、前から開いていた画面から操作した場合
  - 通知の一覧から開く・一覧のカードから開く：詳細画面は「投稿が見つかりません」を出す（上記「投稿の詳細画面」）
  - いいね・お気に入りを押す：404 になる（ホームの一覧と同じく、押す前の表示に戻して失敗を知らせる）
- 写真のファイル
  - 投稿と一緒に、保存先のファイルも削除する（残すと、URL を知っている人が削除後も写真を見られるため）
  - 対象は、その投稿の `post_images` に記録されていた URL そのものだけ。1件ずつ削除する。
    **パターンやワイルドカード、フォルダの一覧から探して消すことはしない**（ほかの投稿・プロフィール・DM の画像を消さないため）。
    ローカルの保存先は、保存先フォルダの直下のファイル以外は削除しない（`../` などでフォルダの外を指せない）
  - 順番：1つのトランザクションで、投稿を読み、投稿者を確かめ、写真の URL を控えてから DB の行を削除してコミットする。
    **コミットの後に**ファイルを削除する
  - ファイルの削除に失敗しても、DB の削除は戻さない（投稿は削除済みとして 204 を返す）。
    失敗した URL はログ（warn）に残し、手で削除する。ほかの写真の削除は続ける
    - 先にファイルを消す、またはトランザクションの中で消すと、DB の削除が失敗したときに「写真だけがない投稿」が残り、
      ファイルは DB のように元に戻せない。コミットの後に消せば、最悪でも「誰からも参照されないファイルが残る」だけで済む
  - 削除できないもの：すでに見た人のブラウザのキャッシュに残った写真。
    公開時にクラウドストレージ（CDN つき）にする場合は、CDN のキャッシュも消す必要がある（クラウドの実装で対応する）
  - 残ってしまったファイルを探して消す仕組みは、今はない
- ログ：削除したときに、投稿の ID・ユーザーの ID・写真の枚数を残す（題名などの内容は残さない）

### ファッションの種類とタグの違い

- **ファッションの種類** … あらかじめ登録してある選択肢からのみ選ぶ
- **タグ** … あらかじめ登録してある選択肢から選べるほか、手入力でも設定できる

### ファッションの種類・タグの管理

- ファッションの種類はDBのマスタテーブルで管理し、後から追加できるようにする
  - 初期データ：きれいめ / カジュアル / モード / ストリート
- タグも1つのテーブルで管理する
  - 運営が登録した公式タグと、ユーザーが手入力したタグを `official` フラグで区別する
  - 選択肢として表示するのは公式タグ
- 使わなくなった選択肢は削除せず非表示にする（過去の投稿が壊れないようにするため）

### 写真のメタデータ（位置情報など）の削除

スマホの写真には撮影場所などが埋め込まれているため、保存する前に取り除く。
投稿の写真・プロフィール画像・DM の画像のすべてで同じ処理を通す（`ImageUploadService` → `ImageMetadataStripper`）。

- 画像をピクセルに展開し、メタデータを付けずに新しいファイルとして保存し直す。元のファイルの付加情報は引き継がない
  - 消えるもの：EXIF（位置情報（GPS）・撮影日時・端末のメーカーと機種・撮影設定）、XMP・IPTC、埋め込みのサムネイル、コメント、
    ファイルの後ろに付いた追加データ（スマホの深度マップなど）
  - 残すもの：色の情報（ICC プロファイル）。広い色域で撮った写真の色を正しく出すために必要で、位置情報や撮影日時は含まない
- 写真の向き（EXIF の Orientation）は、消す前にその値どおりにピクセル自体を回転・反転する（スマホの縦写真が横向きにならないように）
  - 8通りの向きすべてに対応する。画素を並べ替えるだけのため、画質は落ちない
- 画質
  - JPEG は品質 0.95 で保存し直す（保存し直す前後の色の差は平均で 1/255 未満）。ファイルサイズは元より少し増えることがある
  - PNG は可逆圧縮のため、画素は1つも変わらない
- 処理に失敗した場合
  - 向きの情報が壊れていて読めない：そのままの向きとして扱い、メタデータは消して保存を続ける（写真が横向きになることはあっても、情報は残らない）
  - 色の情報（ICC プロファイル）を読めない・付けられない：付けずに保存を続ける（色が少しずれることはあっても、情報は残らない）
  - 展開・回転・書き出しに失敗：**元の画像は保存せずに 400 で断る**（「画像を処理できませんでした。別の画像を選択してください。」）。
    メタデータが付いたまま公開されることを防ぐため。投稿は全部の写真の処理が通ってから保存するため、1枚も保存されない
- この処理を入れる前に保存した画像は対象外（処理し直す場合は別途対応が必要）

  - 編集でも確認画面を挟むことの見直し（上記「投稿の編集」の「画面」。誤字を1文字直すだけでも確認を通るため、煩わしければ見直す）
